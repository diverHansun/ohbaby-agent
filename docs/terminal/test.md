# Terminal 测试设计

> 第五份模块设计文档。测试围绕 [goals-duty](goals-duty.md) 的职责和 [dfd-interface](dfd-interface.md) 的交互边界，而不是围绕文件结构。仓库没有独立的测试规范文档，沿用现有约定：按文件后缀分为 `*.unit.test.ts(x)`、`*.contract.test.ts`、`*.integration.test.ts(x)`，用 Vitest 运行。

## 1. Test Scope（测试范围）

**覆盖：**

- 终端核心：数量上限、启动配置、快照与后续输出的衔接、是否有程序在运行的判断、关闭流程、积压断开、node-pty 不可用时的降级。
- 终端路由：REST 和 WebSocket 的鉴权、loopback 限制、错误码、关闭码。
- 横切改动：Host 头校验，以及它对现有接口没有误伤；serve 停止时结束全部终端。
- 浏览器：新建终端 tab、终端 tab 同步、关闭确认、重连行为、右侧面板登记。

**不覆盖：**

- xterm.js 本身的渲染正确性和 node-pty 本身的行为，这些是依赖库的职责。
- shell 配置文件（`~/.zprofile` 等）的内容是否正确。
- 跨浏览器的像素级显示效果。

## 2. Critical Scenarios（关键场景）

以下场景出错就不可接受：

| # | 场景 | 预期 | 对应 |
| --- | --- | --- | --- |
| S1 | 第 17 次新建（分属不同 workspace 也一样） | 返回 `TERMINAL_LIMIT_REACHED`，已有 16 个终端都不受影响；关掉一个后可以再建 | D2 |
| S1a | 已有 15 个终端，两个新建请求同时到达；第一个仍在加载 PTY | 只有一个获得名额，另一个返回上限错误；创建失败清理完后名额可再次使用 | D2、F2 |
| S1b | 点击新建终端，分别验证请求等待中、成功、失败三种情况 | 等待时保留原页面，无“正在创建”、转圈或占位 tab；成功打开并选中真实终端，失败只提示原因 | D1、F1 |
| S1c | 面板收起或正在查看其他标签时同步终端列表；重复同步相同列表 | 只补缺少的标签，不重复添加，不展开面板、不切换已有选中项、不抢输入焦点；各标签显示终端图标和对应目录名；已显示退出码的标签不被同步改写 | D9、F1b |
| S2 | 断开后重新连接 | 先收到快照，快照反映接回时的服务端画面（包括断开期间的新输出）；之后的输出既不重复也不缺漏，包括“接回排队期间到达的输出” | D9、F3 |
| S2a | 输出尚未解析完时，依次收到 resize、接回请求和新输出 | 按入队顺序执行；旧输出按旧尺寸解析，快照的内容与尺寸属于同一时刻，新输出不重复、不缺漏 | D9、F3–F5 |
| S2b | 浏览器正在恢复快照时，容器尺寸变化且收到实时输出 | 先按快照尺寸完成恢复，尺寸变化和输出再按本地队列顺序处理；合并输出不跨过尺寸变化 | D6、D9、F3 |
| S3 | 全屏程序（如 vim）运行中接回 | 快照恢复出备用屏幕的画面，而不是乱码；退出 vim 后原来的普通屏幕内容还在 | D9 |
| S4 | 有程序在运行时关闭（不带强制），前台程序和 `sleep 999 &` 这样的后台任务都要测 | 返回 `TERMINAL_BUSY` 并带程序名，shell 和程序都还活着 | D7 |
| S5 | 空闲时关闭，或带强制关闭 | 清理期间保留登记并占名额，成功后才删除并返回 200；查看者只收到一次 `exit` 和 1000；shell 收到挂断信号；运行 `sh -c 'trap "" HUP; sleep 999'` 这类忽略挂断信号的子程序，2 秒后也被结束 | D7 |
| S5a | 关闭尚未完成时再次关闭，或立即停止 serve | 复用同一个关闭任务；停止等待其完成，不遗漏子进程清理；不会提前释放名额 | D7、F6、F8 |
| S5b | shell 本身忽略挂断信号，或 shell 先退出而子程序仍存活 | 强制结束包含仍存活的 shell 和需要清理的子孙进程；shell 退出不提前删除登记或取消后续清理 | D7 |
| S5c | 清理失败或超时，刷新网页后重试关闭 | 列表仍返回失败记录并占名额；刷新后标签回来、不接回终端，可用 `x` 重试；重试沿用剩余进程的清理记录，成功后才删除并释放名额。创建失败后遗留的清理记录也能找到并关闭 | D7、F6 |
| S5d | 关闭尚未完成时刷新；或接回时恰好已开始关闭 | 列表仍能找到记录；不把 4404 直接当成记录已删除；原关闭入口仍可等待已有任务，不因刷新后读到 `closing` 就永久禁用。列表查询失败不当作终端已结束 | D7、F1b、F6 |
| S6 | 刷新网页、关闭面板 | shell 和其中运行的程序继续运行 | D9 |
| S7 | 非 loopback 模式 | 终端的 REST 返回 403 `TERMINAL_LOOPBACK_ONLY`，WebSocket 握手被拒绝 | D11 |
| S8 | daemon 未配置 token | 终端的 REST 返回 401，WebSocket 以 4401 关闭；其他接口行为不变 | D11 |
| S9 | Host 头主机名不是本机名（模拟 DNS 重绑定） | 首页、所有接口和 WebSocket 升级请求都返回 403，HTML 里的 token 不会下发；主机名是本机名但端口不同（SSH 转发）时正常访问 | D11 |
| S10 | WebSocket 不带 token 或 token 错误；Origin 是其他网站 | token 问题以 4401 关闭；Origin 不是本机时握手被拒绝；两种情况都收不到任何终端数据，终端不登记这个查看者 | D10 |
| S11 | node-pty 加载失败 | 新建返回 `TERMINAL_UNAVAILABLE` 并附原因；serve 的其他接口正常 | D12 |
| S12 | 一个查看者的应用层待发消息与 ws 待发量合计超过 2 MB，包含快照后的待发输出 | 只有这个连接以 4408 断开，队列释放；shell 和其他查看者不受影响；浏览器退避重连 | N12 |
| S12a | 服务端屏幕持续处理不过来 | 达到高水位暂停读取 PTY，写入回调释放积压后恢复；暂停期间仍能关闭终端 | N12 |
| S12b | ws 待发量很低，但浏览器的排队与未处理完输出合计超过 2 MB | 浏览器主动断开、释放旧队列并退避重连；旧回调不污染新画面；反复超限时退避不会因握手成功而立即重置 | N12 |
| S13 | serve 停止时有终端在运行，或正有终端在新建 | 并行等待运行中、正在关闭以及正在新建的终端完成清理；单个失败不跳过其他终端；停止流程在有限时间内完成，不被 WebSocket 卡住 | F8 |
| S14 | shell 自己退出 | 查看者收到 `exit` 和退出码，终端从 `GET /v1/terminals` 中消失，名额释放 | F7 |
| S15 | 粘贴长文本，包含中文、emoji、制表符、换行、引号和反斜杠 | 每条完整 JSON 消息的 UTF-8 编码不超过 65,536 字节；所有 data 拼接等于原文，字符完整、顺序不变，连接不断开 | D8 |
| S16 | 连接到不存在的终端 | 以 4404 关闭；浏览器同步列表、确认记录不存在后显示“终端已结束”，不重连 | F3 |
| S17 | 没有打开 workspace 时新建终端 | 新建成功，初始目录是用户主目录（`os.homedir()`），返回的 `title` 为 `~`，tab 标题显示 `~`；带了无效目录时返回 400，不悄悄改用主目录 | D3、F2 |

## 3. Integration Points（集成点测试）

| 集成点 | 验证重点 | 失败时的预期 |
| --- | --- | --- |
| node-pty（经 PTY 适配） | 真实开一个 shell，能写入、读出、调整尺寸、结束；进程表能查到 shell 的子孙进程 | 真实验收中加载失败应报失败；S11 用故意模拟的加载失败单独验证 |
| `@xterm/headless` + `addon-serialize` | 把含颜色、光标移动、备用屏幕的输出写入后，快照能还原到一个新的 xterm 实例 | — |
| `@hono/node-server` v2 + `ws` | 升级、子协议协商（只回传 `ohbaby.terminal.v1`，即使浏览器把 token 子协议放在前面）、`maxPayload` 触发 1009、`bufferedAmount` 可读、关闭码 | Host 或 loopback 不合法时握手前返回 403 |
| daemon 的单 scope 与多 scope 两种模式 | 终端路由在两种模式下都可用；Host 校验在两种模式下都生效 | — |
| daemon 停止流程 | 新增的“结束全部终端”步骤与现有清理步骤一起完成 | 某个 shell 不退出也不阻塞停止 |
| 现有接口（会话、设置、事件流、静态页面） | 加上 Host 校验后，用合法 Host 访问的行为不变 | — |
| 右侧面板 | 登记 terminal 后 Subagents 页行为不变；关闭 Subagents tab 不经过终端的关闭流程 | — |

## 4. Verification Strategy（验证策略）

**自动化测试：**

| 层次 | 内容 | 方式 |
| --- | --- | --- |
| unit | 启动配置（shell 选择顺序、参数、环境变量补齐、初始目录）；Host 校验规则（主机名白名单、端口不限、绑定的 loopback 地址）；进程表输出的解析（找出子孙进程、程序名取文件名）；Origin 规则（无 Origin 放行、本机名放行、其他拒绝）；token 的 base64url 编码 | 纯函数，不开进程 |
| unit | 终端管理器与终端会话：并发新建的名额预留与释放（S1a）、关闭流程、退出通知只发一次、停止时拒绝新建、积压断开、快照与输出衔接（S1、S2、S4、S12、S14） | 用假的伪终端驱动，可控制输出时机、子孙进程列表和退出，配合假时钟测 2 秒强制结束，以及 S5a–S5d 的重复关闭、失败重试、刷新恢复和停止等待；控制 headless 写入回调验证 S12a，分别制造应用层与 ws 积压验证 S12 |
| contract | sdk 中的终端消息与错误码，确保前后端理解一致 | 与现有 `*.contract.test.ts` 一致 |
| integration（server） | 启动真实 daemon，经 REST 和 WebSocket 走完新建 → 接回 → 输入 → 输出 → 关闭；覆盖 S5、S7–S11、S13、S17；S15 只验证服务端超过 64 KiB 时以 1009 关闭，S16 只验证以 4404 关闭（浏览器侧行为在 web 集成测试中验证） | 使用真实 node-pty，shell 用 `/bin/sh`，命令用 `echo`、`sleep` 这类稳定输出 |
| integration（server） | S2a、S3：真实 headless + serialize 验证输出、resize、快照顺序及备用屏幕恢复 | 不需要真实 shell，直接写入控制序列 |
| integration（web） | S1b–S1c：新建成功后打开、失败反馈及静默同步（旧查询不能覆盖期间已确认的增删）；加载和窗口获得焦点时按服务端终端补 tab、服务端已无的终端 tab 显示已结束、切换 workspace 后终端 tab 保留且标题含目录名；页面反馈遵循 architecture“页面反馈”表，不把内部状态都显示出来；`TERMINAL_BUSY` 弹确认、取消保留 tab；4408 退避重连；控制 xterm 写入回调验证 S2b、S12b；1000、4401、4404 不重连；4404 后查询列表区分已删除和未清理完；S5c–S5d 刷新后仍能关闭；粘贴内容切块发送 | 模拟终端客户端，与现有 `SubagentsPage.integration.test.tsx` 方式一致 |

**验收要求（2026-11-04 确认）：关键操作必须真实跑通，加载失败不能自动跳过。**

- 当前验收环境必须加载真实 node-pty，启动真实 shell。依赖加载失败、shell 启动失败或关键流程未跑通，都算验收失败，不能捕获错误后改为 skip。
- S11 单独模拟依赖加载失败，检查错误提示和聊天功能仍然可用。这个降级测试不能代替真实终端验收。
- 浏览器验收至少走完四项：输入命令并看到实际执行结果；启动持续运行的程序，刷新后仍是原来的进程；收起面板再打开后能继续输入；关闭终端后确认 shell 和应清理的子程序确实退出、开发服务器端口释放、记录消失且名额可再次使用。正常关闭的验收必须直接成功，不能把进入“关闭失败、可以重试”当作通过；失败重试另外用故障模拟验证。不能只看到标签或命令回显就算成功。
- 先在当前 macOS 环境完成验收，记录系统、架构、Node 版本、命令和结果。其他平台没有实测就写“未验证”，不能因为存在预编译包而写成已验证；声明已验证的平台也必须满足同样要求。自动化未覆盖的浏览器关键流程必须实际走查并记录，不能以模拟测试替代。
- 参考 ZCode 的 `packages/desktop/test/e2e/conversation-session/conversation-session-r3-terminal.test.ts`：等待真实提示符后从页面输入，检查运行结果；参考 dsh 的 `apps/web/tests/sidebar-terminal.e2e.ts`：真实浏览器、真实 PTY，以及刷新和断线后接回同一进程。只借鉴关键验收，不照搬整套测试设施。

**人工验证（浏览器走查）：**

1. 在 Terminal 里运行 `npm run dev`，刷新网页，终端 tab 自动回来，dev server 仍在运行，画面完整。
2. 打开 vim，关掉面板再打开，画面恢复正常。
3. 运行 `which node pnpm`，结果与 macOS 自带终端一致（验证 `-l` 登录 shell，G2）。
4. 输出中文和带颜色的内容，没有乱码。
5. 终端配色、字体与页面一致；tab 显示终端图标和目录名，悬停可见完整路径和 shell 名；终端上方没有额外标题栏。
6. 点击输出里的 `http://localhost:5173`，在新标签页打开。
7. 有程序在运行时点 `x`，出现确认；空闲时点 `x`，直接关闭。
8. 用 `--host 0.0.0.0` 启动 serve，用 curl 调用 `POST /v1/terminals`，确认返回 403 `TERMINAL_LOOPBACK_ONLY`。非 loopback 模式下 ohbaby 本身就不提供网页界面，所以这一项只能从接口验证。
9. 用 `ssh -L` 把 serve 的端口转发到另一个本机端口，从转发后的地址打开页面，终端可以正常使用。
10. Windows 验收时必须走查；没有环境则记录“未验证”：shell 依次选择 pwsh、powershell、cmd；关闭终端时直接关闭，不弹确认。
11. 持续输出日志或运行 `yes`，检查页面仍能操作，输出积压受限；触发重连后能恢复画面，停止输出后能恢复正常交互。分别走查打开与隐藏面板的情况。
