# Terminal 非功能约束

> 第四份模块设计文档。只写这个模块特有的工程约束，不列通用最佳实践。数字来源和取舍理由见 [goals-duty](goals-duty.md) 与 [architecture](architecture.md)。

## 1. Quality Priorities（质量优先级）

按优先级从高到低：

1. **安全**：终端是一个不经审批的 shell，能连上就能在本机执行任意命令。只要和其他目标冲突，就以安全为准。例如宁可在非 loopback 模式下整个关掉终端，也不提供“局域网也能用”的开关（D11）。
2. **不误杀用户的程序**：刷新网页、关面板、网络抖动都不能结束 shell；关闭正在运行程序的终端必须先确认（D7、D9）。
3. **不连累 ohbaby 其他功能**：node-pty 加载失败、某个终端卡住或刷屏，都不能影响 `ohbaby serve`、聊天和其他终端（D12、N12）。
4. **实现简单**：在满足以上三条的前提下，选最少代码的做法。例如不做跨网络的逐条输出确认、不做闲置回收、不拆包。

日常输入的手感（按键到回显的延迟）依赖本机 WebSocket，不单独设指标。

## 2. Operational Constraints（运行约束）

| 约束 | 数值 / 规则 | 理由 |
| --- | --- | --- |
| 终端总数 | 整个 serve 最多 16 个，包括正在创建、正在关闭及清理失败的终端；创建前预留名额，超出时拒绝 | 兜住开了又忘的终端（D2） |
| 服务端滚动历史 | 每个终端 1000 行 | 限制屏幕内存（D8） |
| 单条输入 | 完整 JSON 消息按 UTF-8 编码最多 64 KiB（65,536 字节）；浏览器自动拆分，保持字符完整与原顺序 | 防止异常输入撑爆内存，又不影响正常粘贴（D8） |
| 服务端屏幕的待处理输出 | 达到内部高水位时暂停读取 PTY，降到低水位后恢复 | 防止屏幕解析队列持续增长（N12） |
| 单个查看者的积压 | 初始快照单独发送、最多等 10 秒；快照后的实时输出与 ws 待发量合计超过 2 MB，断开该连接（F5） | 慢页面单独隔离（N12） |
| 浏览器的实时输出积压 | 排队和 xterm 尚未处理完的输出合计超过 2 MB，主动断开后退避重连 | 不能只限制网络发送队列；具体计量见 F5（N12） |
| 终端尺寸 | 列 2–500，行 1–200 | 防止异常尺寸请求 |
| 关闭等待 | SIGHUP 后最多等 2 秒正常退出，再对仍存活的 shell 及需要清理的子孙进程发 SIGKILL，最多再等 1 秒检查结果，一次关闭最长约 3 秒；清理完成后才返回成功 | 有的程序会忽略挂断信号，只杀 shell 会留下它们（D7） |
| 监听地址 | 只在 loopback 下开放终端；loopback 下校验 Host 头的主机名（端口不限） | 防局域网截获 token、防 DNS 重绑定，同时兼容 SSH 端口转发（D11） |
| 平台 | macOS、Linux、Windows（x64、arm64） | 目标平台及依赖预编译覆盖范围，不代表均已验证；已验证范围以 test.md 的实际验收记录为准，其他平台降级为“不可用” |
| Node 版本 | 跟随项目要求（Node 24 及以上） | node-pty 基于 N-API，预编译文件不绑定 Node 版本；实现阶段要在 Node 24 上实测 |

## 3. Reliability & Observability（可靠性与可观测性）

**故障时的行为：**

| 故障 | 行为 |
| --- | --- |
| node-pty 加载失败 | 新建返回 `TERMINAL_UNAVAILABLE` 并附原因；serve 和其他功能照常 |
| 浏览器断网、刷新、关面板 | shell 继续运行；重新连上后拿快照恢复画面 |
| 服务端屏幕处理不过来 | 暂停读取该终端的 PTY，处理下来后恢复；持续输出的程序可能暂时阻塞 |
| 查看者待发队列或浏览器本地输出积压超限 | 服务端以 4408 关闭连接，或浏览器主动断开；清理该连接的队列，退避重连拿最新画面；其他查看者不受影响 |
| shell 自己退出 | 推送 `exit`，清理资源及已记录的子进程后移除登记；失败保留记录。macOS 上未记录且已被系统重新托管的后台程序可能继续运行，见 F7 |
| shell 或子程序不响应挂断信号 | 2 秒宽限期后对仍存活的 shell 及需要清理的子孙进程强制结束 |
| 终端清理失败或超时 | 返回 `TERMINAL_CLOSE_FAILED`，保留记录并继续返回列表，刷新后仍能恢复 tab、再次关闭；serve 停止时也会再次尝试并汇总失败 |
| serve 停止 | 先拒绝新建，再结束全部终端；先 `terminate()` 所有 WebSocket 再关 HTTP server，停止流程不能被卡住 |
| serve 停止时有终端正在新建 | 开好的 shell 立即进入清理，停止流程等待创建和清理任务完成 |

**可观测性**：沿用 server 现有的诊断日志，只记录这些事件：终端新建与结束（id、workspace、shell、退出码）、node-pty 加载失败原因、因积压断开连接、强制结束。**不记录终端输入输出内容**，里面可能有密码和密钥。

## 4. Trade-offs & Deferred Requirements（权衡与暂缓项）

| 暂缓项 | 现在怎么兜底 | 什么时候再做 |
| --- | --- | --- |
| 闲置终端自动回收（N10） | 全局 16 个上限，终端 tab 会显示全部终端 | 出现长期占用资源的反馈时 |
| 跨网络的逐条输出确认（N12） | 服务端反压 PTY，查看者与浏览器分别限制积压，超限断开重连 | 出现大量输出时画面跳变明显的反馈时 |
| serve 重启后恢复终端（N11） | 不恢复 | 做 detached 常驻 serve 时一并考虑 |
| 多查看者的输入仲裁（N8） | 都能输入，尺寸以最后一次为准 | 有多人或多设备协作需求时 |
| 局域网访问终端 | 非 loopback 下关闭 | 有 TLS 和多用户鉴权之后（server N4） |
| Windows 下关闭前的确认 | Windows 直接关闭 | 有 Windows 用户反馈时，再考虑进程表检查 |
| shell 配置启动的常驻辅助进程（如 powerlevel10k 的 `gitstatusd`）会被当成“有程序在运行”，这类用户每次关闭都会看到确认 | 接受：确认框里有程序名，用户一看就懂，点一次即可 | 出现相关反馈时，改为忽略 shell 刚启动时就存在的子进程 |
| 快照恢复 SGR 鼠标编码、光标隐藏两种模式（D9 已知局限） | 不恢复，程序下次设置这两种模式时会自行纠正 | 出现接回后鼠标或光标异常的反馈时，在快照后补发这两种模式 |
