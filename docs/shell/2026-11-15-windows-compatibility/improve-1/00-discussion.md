以下四项按这次回复记为已确认。D13 的解除路径在核对代码后有修正，用户随后确认，见 D13 末尾。

- Job Object 能证明“仍在 Job 里的进程都已退出”，不能证明命令启动过的所有进程都已结束。
- 脱离 Job（breakaway）的进程不在保证范围内。实测中，pwsh 的 `Start-Process` 和 .NET `Process.Start` 启动的后台进程都不在 Job 里：Job 报告活跃进程为 0，这些进程仍在运行。这和 macOS 上用 `setsid` 脱离进程组属于同一类缺口。
- Windows 的 cleanup=confirmed 只表示 Job 已空。文档、界面和模型提示都不得把它说成“整棵进程树已清空”。
- 用户在普通 Windows Terminal 中复测，三种后台启动方式同样逃出 Job，可排除 SSH 环境的影响。具体原因仍未定位，但不影响本条边界，见 [证据附件](evidence-notes.md) 的“Koffi 进程内 Job 实验”一节。
- 这条边界不改变 D07：清理确实无法确认时，仍按现有规则暂停相关工具。

## D11 · 原生组件采用 Koffi 进程内调用（用户已确认）

- 用 Koffi 3.x（锁定 3.1.1，与 dsh 相同）在 runtime 进程内调用 Win32 Job Object API。不做 C#/.NET helper，不新增独立进程。
- 保留 Node `spawn` 及现有管道、编码和前后台流程。子进程启动后立即加入 Job（attach-after-spawn），思路与 codex `utils/pty/src/pipe.rs`、ZCode MCP stdio 一致；codex 用子进程句柄加入，ohbaby 与 ZCode 一样按 PID 打开进程再加入。
- 只有 bash 启动的命令进程加入 Job。没有登记 Job 的子进程（如 ripgrep）在 Windows 上保持现有处理，不受 D13 影响。
- 接受 spawn 与加入 Job 之间的极短窗口，不改写为挂起启动。pwsh 启动约需 400 ms 才执行用户命令，而加入 Job 是一次同步系统调用。
- runtime 持有 Job 句柄并设置 KILL_ON_JOB_CLOSE：runtime 正常退出或被强杀时，系统回收 Job 内进程，不需要另做监督协议。
- 不设置 BREAKAWAY_OK，不提供“保留后代”模式。
- macOS 保持现有进程组与身份检查，不引入 Koffi。

## D13 · Koffi 不可用时如实报告（用户已确认）

- Koffi 加载失败、建 Job 失败或加入 Job 失败时，不改用“父进程已退出”作为证据，也不静默标记为已清理。
- 任务记为 unconfirmed，原因写明原生能力不可用（如 `native-unavailable`），并在报错和任务快照中显示（实施时以快照字段代替单独日志，见 02 文末）。
- 代价：此时每条自然退出的命令都会进入 unconfirmed，相当于回到原故障，只是原因可见。因此 Koffi 预编译包缺失必须在安装包验证中拦住，运行时首次失败也要记录一次明确日志。
- **核对代码后的修正（用户已确认）。** 第二轮评审曾说“用户可在 D05 的入口解除”，这不准确。现有 abandon（`shell-jobs/recovery.ts` 的 `abandon`）要求原 runtime 已退出且本地没有该任务的句柄；runtime 仍在运行时，它自己的 unconfirmed 任务无法解除，要等重启 runtime 之后才行。助手建议第一批不新增“运行中解除”的路径，只在报错中写明“需要重启后解除”，理由是原生能力缺失应被安装验证拦住，属于罕见情况；若用户希望运行中也能解除，需要修改 D05/D07 的规则，另行讨论。

  即：接受“运行中无法解除、重启后由用户解除”，第一批不新增运行中解除的路径。

## D14 · 用户解除入口：Web 与 TUI 都做，对齐参考项目（用户已确认）

用户确认原话同 D13 末尾。对照 claude-code、kimi-code、codex 后（见 [03](03-reference-projects.md)），入口按以下方式对齐：

- **不新增入口。** TUI 沿用 `/bg` 打开的任务浏览器，Web 沿用侧栏的后台任务页。codex 用 `/ps` 列出后台终端，claude-code 和 kimi-code 也都是“一个任务列表 + 单项操作”，ohbaby 现有入口已是这种形态。
- **列表包含清理未确认的前台任务。** 查询时不再限定 `mode: "background"`；SDK 不传 mode 时已会带上清理未完成的前台任务。这类任务用错误色的说明行标出，与 kimi-code 把 `lost` 显示为错误色一致。TUI 的 `/bg` 在只有这类任务时也要能打开面板。
- **单项操作“放弃跟踪”。** 只在 cleanup=unconfirmed 且该任务不由当前后端管理时出现，交互复用现有取消的二次确认：TUI 按 `y` 在 5 秒内确认（与 kimi-code 相同），Web 沿用现有取消按钮的确认方式。文案写明“不会结束进程，只是不再阻塞工具”。
- **当前后端仍在管理的未确认任务**不提供操作，说明行写明“需要重启 ohbaby 后才能解除”（D13）。
- **报错指路。** 文件工具被阻塞时，报错写明阻塞的任务，并指向 `/bg` 或 Web 侧栏的后台任务页。
- **不做：** 批量解除、状态栏计数、自动解除。claude-code 和 kimi-code 有状态栏计数，但它们显示的是运行中的任务；ohbaby 的阻塞会直接以报错出现，不再加一处常驻提示。
- 现有前端文档把“放弃追踪”列为不做（`docs/ohbaby-web/background-tasks/04-interaction-and-states.md`、`docs/ohbaby-cli/background-tasks/00-goal-duty.md`）。本决定修改这一点，实施时同步这些权威文档。
