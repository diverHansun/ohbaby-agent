## 0.1 用户确认记录

### Stop 后继续普通队列

> 自动执行下一条,继续开始执行！除非用户清空等待排队的消息，否则stop后下一条正在等待queued的消息就会注入并推动启动下一轮turn

> 下一条消息要等到什么程度，才能开始新 Run:旧主执行结束并完成停止登记后，允许推进 B；未清理资源继续受保护

用户随后确认 ohbaby 字段语义：Session 保存会话；普通 prompt submission 启动独立 Run/runId；Run 内有多个 Step；provider 请求重试使用 request attempt。Steer 属于当前 Run。这里不把其他项目的 turn/step 名称机械套入，也不全面重命名既有事件。

### 子代理实例可以复用，旧任务不自动补跑

> 旧任务退出可执行队列，保留记录。Stop 定义为中断当前任务树，同时允许下一条用户任务启动。下一任务可能改变方向，旧子任务不应该仅因为复用了同一个子代理实例，就重新获得执行资格，所以上一轮的子代理实例如果是interruptted，那么就可以被再次被主代理唤醒，然后复用：聚焦于本轮任务（当然也可以执行上一轮未完成的任务，关键在于本轮主代理派发给子代理的实际消息）

已完成结果、实例和历史保留；结束的是旧委托的执行资格。新主任务明确要求继续旧工作时，可以基于历史继续，但应建立新的执行身份。

### 冷恢复先保证记录准确

> 确认先保证记录恢复准确的方案，参考借鉴code-cli/下这些优秀项目的实施边界，继续讨论！

对应选择：运行中 Stop 与正常退出处理取消和清理；异常重启修复失主记录，保留结果，标明无法确认的情况，不自动重放工具。本轮不加入跨重启旧进程接管/自动杀进程；不能声称崩溃前的内存锁仍然有效。

### 服务关闭与退出确认

> 关闭整个服务时，是否采用“停止接活 → 中断全部所属任务 → 有限等待清理 → 如实登记未完成项并退出”的规则，确认！

> `serve stop` 默认等待服务进程实际退出，再告诉用户“已退出”，确认这个行为

讨论已澄清：serve 所在终端的 Ctrl+C/SIGINT 也可进入正常关闭流程；`serve stop` 另有外部观察者等待退出。Command+Q 能否完成清理取决于终端处理；SIGKILL/断电没有清理保证。进程退出与所有外部资源清理完成是不同事实。

### 重启保留普通排队消息，由用户发送

> 重启先修复记录；被中断的旧执行不自动重跑，确认！但你说的重启是指怎么重启？用户重新运行ohbaby/ohbaby serve？建议重启后queued的待发送用户消息保留，但是不要主动发送queued的消息，用户自行操作

> 不要有“继续队列”的多余button，这样非常麻烦，不要过度设计，对标opencode和codex的设计交互

重启指原执行环境结束后重新运行 `ohbaby` / `ohbaby serve` 或相应 pnpm 命令。复用仍活着的 serve、刷新页面、重连、切页不算冷启动。其他旧消息不因某一条发送而启动；正常运行时 Stop 后自动推进的规则不变。

### 编辑和删除

> queue的消息，右侧有一个铅笔icon表示编辑，一个垃圾箱icon表示删除

> 去除“用户点击某条消息，内容进入现有输入框”，在输入框内删除的交互，这样更清晰一些。

> 1.确认**正常运行中的 queued 消息：** 编辑后按钮显示“保存”，保存后继续按原队列等待执行。2.**重启后保留的待发送消息：消息仍然在prompt框内，** 编辑后使用“发送”，只发送这一条，其他旧消息不跟着启动

按后续确认收敛：正文展示/选择/复制，不点击整行编辑；铅笔复用现有 prompt 输入框，垃圾箱删除该条。当前编辑内容留在 prompt 框内；多条不合并，原有草稿不丢。清空编辑文字不是删除。取消编辑恢复原草稿；不增加队列继续按钮、恢复弹窗或新管理页面。

### 恢复失败的影响范围

> 旧任务中断、某个工具没有完整结果，这属于正常恢复范围：补齐中断记录，标明结果未知，允许用户发送新消息。会话数据无法解析、修复结果无法可靠保存，恢复失败：这个会话暂时不能继续执行，显示具体原因，保留原始记录。能确定只影响某个会话的问题，就限制在这个会话及其子任务范围，其他会话照常使用

## 0.3 固定边界

- 用户仍只在根会话控制当前任务；子视图只读，不增加用户单独停止/关闭/重启子代理入口。
- 默认 TUI in-process；同 SQLite 不等于共享运行协调和审批，不能误伤另一存活执行环境。
- 复用前三轮能力；不另建 scheduler、事件总线、任务平台、通用隔离执行器或文件级锁。
- 已完成结果与第三轮 `.output` 保留；Stop 不删除会话、不删除报告。正常会话删除的授权及产物规则沿第三轮。
- 不恢复旧审批 Promise，不自动批准，不把已接收 Steer 变回普通消息。
- 不重写独立前置最终结果提取和文件工具增强；不承诺外部副作用恰好一次。
- 六个参考项目为 Kimi、OpenCode、Pi、Claude Code 本地重建版、Codex、DeepSeek Harness。具体采用/调整/不采用见 03，用户行为优先于竞品默认行为。

## 0.4 2026-09-22：静默停止、工具计时与异常阻塞

> “建议用户stop原先任务后，前端不显示，静默停止。A 主执行退出并登记后，B 就可以开始。不要额外加‘统一先等几秒’”

> “建议工具运行running时加计时器，和thinking的计时分开”

> “正常清理全部静默；清理异常确实挡住 B 时，让被挡住的工具返回普通错误结果，而不增加专门的清理提示，确认！写入文档，继续讨论！”

正常 Stop 和后台清理不新增提示、弹窗或面板，不删除后台中断/清理事实。异常时走被阻塞调用的既有工具结果通道，主代理收到真实错误；不是给旧操作伪造未执行，也不自动停止整个 B。已返回错误的调用不自动重放，旧资源保护保留到确认释放。具体准入与清理归前置 C，可靠结果和独立工具计时归第二轮，第四轮负责跨 Run 交接与组合验收。

这次确认修订前置 C 和第二轮中“异常清理使新调用一直等待”的表述；不新增普通排队超时，不把正常资源竞争当清理失败，不影响 `serve stop` 的退出报告。停止登记失败随后按 §0.5 确认；Steer 中断展示随后按 §0.6 确认；旧数据迁移与 TUI 操作在 02 中按已确认边界细化为工程方案，不新增运行时接管或管理页面。

## 0.5 2026-09-22：停止登记失败后的恢复与队列交接

> 停止登记失败时先暂缓后续执行，并保留待保存事实。后端进行有限重试；失败后，可由重新连接、进入会话或下一次执行入口再次触发同一恢复检查。原执行环境内登记成功后，自动推进仍有效的下一条 queued；冷启动恢复不自动发送旧消息。确认这样的机制！可以写入文档

用户同时确认此前四点建议：整理现有存储有限重试，不在外层重复叠加等待；失败时显示具体保存错误，停止与清理继续；普通历史查询/状态轮询不反复尝试写入；恢复成功只推进仍有效的 queued，已删除项不能执行。不新增按钮或无限轮询，重试只保存停止事实，不重跑 A 或工具。

“原执行环境”要求原 owner 仍掌握停止操作及主逻辑退出事实，不能只凭服务 PID 仍活就自动推进。具体并发去重、错误范围和执行前检查见 02 §2.6；参考项目的局部机制及不照搬的行为见 03 §3.11。
