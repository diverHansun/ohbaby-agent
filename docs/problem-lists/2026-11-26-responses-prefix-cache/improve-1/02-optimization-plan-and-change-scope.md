# 请求如何调整

只在 Responses 序列化时处理 GPT-6.2 Sol 和 Astra 的规范模型名，也接受斜线分隔的路由前缀。对模型名最后一段做完整匹配，以免同名开头的其他模型被误判。官方直接访问和兼容网关共用这一判断。

当原始消息列表第一条是 system，把它作为第一条 developer 消息写入 input。后续 system 指令继续按原顺序合并至顶层 instructions，明确保留每轮临时指令的含义。请求内容仍然通过原有校验路径。其他模型沿用原投影，工具调用、原生回放、store 和消息持久化沿用现有实现。

本轮使用默认的隐式缓存。切换顶层 effort 会改变模型看到的前缀。若以后要在首次切档时继续复用旧前缀，需要让会话保存切档的位置，并确认对应端点接受 configuration_update。这是独立的历史语义改动。上线与回退只涉及适配器及其测试，无需迁移数据。

Opus 和 Neon 都建议核查连续 system 和日期快照。正常会话生成器只插入一条基础指令。它和临时要求可能相邻，因此使用原始消息索引识别第一条。未经验证的快照、自定义别名和未来模型继续使用已有布局；后续有明确模型 ID 和实测后再扩展。工具定义或基础指令本身发生变化时，服务可能需要重算前缀。
