# 5. 实施与验收

2026-11-20，在本地分支 `codex/web-history-paging` 实施，基线为 `e9c6c3c8`。

## 实现

- 后端统一 UI 历史投影。已压缩的用户输入、回复和可见工具记录仍能回看，摘要显示为分隔线。压缩后的模型输入继续由模型上下文路径生成。
- 分叉时按实际复制进来的摘要恢复压缩状态。回归测试覆盖摘要与切点同一毫秒的两种插入顺序，以及切点落在两次压缩之间。
- 主会话历史只在窗口外的主会话推理发生相关变更时标记失效。窗口内推理随实时消息推送。子代理推理仍走各自的对话更新。
- Web 在接近顶部时分页，加载期间显示 spinner，游标前进后才自动续页。历史请求失败后，等待用户再次上滑。窗口淘汰时保留已加载的页，重连和真实历史更新按新基线刷新。

## 浏览器和 TUI

用编译后的 Web 与 CLI 启动隔离服务。从原 SQLite 只读备份出临时副本，流式输出使用本地测试模型。分叉、Side Chat 和子代理测试所需的写入都落在临时副本。

| 场景 | 结果 |
| --- | --- |
| T17 主会话 | Chrome 上滑发出两次历史请求，读到会话第一条用户消息，响应中的原文与 SQLite 一致。压缩分隔线和旧回答可见。到达会话开头后继续上滑，未发出额外请求 |
| T17 加载与阅读位置 | 只有 spinner，首屏空消息行均不占位置。插入第一页时阅读锚点偏移 0.22 px。请求失败后静默停止，两秒后再次上滑恢复 |
| T17 操作与实时输出 | 压缩前的输入没有编辑按钮，压缩后的输入可编辑。旧回答分叉创建了独立会话。一次持续流式输出期间，已加载的旧页保留，没有重复请求 |
| T17 子代理与 Side Chat | 子代理补充 60 条合成消息后验证自动翻页、已有错误条和上滑重试。Side Chat 通过本地模型完成 27 轮对话，重新打开后加载一页，到达自己的历史边界即停止 |
| T18 TUI | 使用编译后的 CLI，通过 tmux 驱动真实终端界面。翻到最早的用户原文，看到压缩分隔线，未出现乱码或历史读取错误 |

两页历史响应体分别为 408,837 B 和 3,313 B，Chrome 报告的传输大小分别为 409,137 B 和 3,613 B。本次滚动采样没记录到超过 50 ms 的长任务。

## 自动化测试

- 后端测试覆盖已压缩原文、实时压缩、模型上下文、分叉切点、子代理历史和推理失效。分页与实时压缩的新断言在基线失败，在当前实现通过。
- 首次全量并行测试中，npm 打包冒烟用例通过，但下载耗时让两组编译用例等构建锁超时。将打包用例单独计入，其余全量复跑 8,804 项通过、30 项跳过，两次合计覆盖 8,805 项通过。
- Web 和 SDK 共 1,288 项通过。选跑的 daemon、子代理和模型步骤重试端到端测试共 18 项通过，跳过了 1 项需要真实供应商的用例。
- 隔离目录的完整构建、仓库类型检查和 lint 通过。lint 有警告，错误数为 0。
- Stage 1 由 GitHub Copilot 的 Gemini 4 Carbon 独立复核。采纳了同一测试时钟的建议，手动压缩和模型输入两项用例复测通过。Stage 2 由 Claude Opus 5.5 实施。

## 已知测试失败

额外跑了 daemon 的模型空闲超时测试。旧用例要求 10 秒内暂停且只调用一次模型，在基线连续三次失败。临时基线副本按现有重试策略等待后，观察到调用 6 次，约 15.66 秒后暂停，服务仍可用。该用例未纳入本次修复。
