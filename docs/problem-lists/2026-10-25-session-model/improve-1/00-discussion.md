# 讨论记录与已确认要点

> 2026-10-25 至 2026-10-26 与用户讨论定稿。现状见 [01](01-problem-analysis-and-current-state.md)，方案见 [02](02-optimization-plan-and-change-scope.md)。

## 1. 背景与动机

现在模型选择是全局的。Web 输入框旁的模型菜单调用的是“设置全局默认模型”，选一次，所有会话的下一轮都换成这个模型。用户想让不同会话用不同模型，互不影响。

多模型库的后端已经在 [improve-2](../../2026-10-20-workspaceless-sessions-and-settings/improve-2/00-discussion.md) 做好：`model.json` 的 `models[]` 每条保存一个模型的完整配置，`activeProfileId` 记录全局默认。当时明确写了“按会话保存或切换模型本轮不做”，本议题接着做。

## 2. 已确认的决策

| 编号 | 决策项 | 结论 |
|---|---|---|
| D1 | 会话没选过模型时用什么 | **跟随全局默认**。会话不保存模型时，每一轮都用当时的全局默认模型；改了全局默认，这些会话的下一轮也跟着换 |
| D2 | 会话里切换模型要不要顺手改全局默认 | **不改**。会话里切换只影响这个会话 |
| D3 | 会话选的模型被删了 | **退回默认模型并提示**，参考 pi。具体写法见 D10 |
| D4 | 模型配置被修改（地址、key、协议等） | **不需要额外处理**。会话引用的是模型条目，配置改完下一轮自然生效 |
| D5 | TUI 做不做 | **本轮做，但分批**：先做后端和 Web，再做 TUI 适配 |
| D6 | Settings 模型页的范围 | 本轮包括优化 Settings 里的模型管理和模型配置，并评估管理界面的 UI 是否需要优化 |
| D7 | 文档落点 | `docs/problem-lists/2026-10-25-session-model/improve-1/` |
| D8 | 分工 | 文档写完后自检，并对照 opencode、pi、kimi-code、ZCode 的实施经验和代码。2026-10-26 更新：agent 实施后端、测试和子代理审查；用户检查后端并实施前端，全部完成后合并 main |
| D9 | 什么算默认模型 | Settings 模型列表里标着 Default 的那一条，即 `activeProfileId`，由用户在 Settings 里选。删除默认模型后的顺延规则、全部删光后没有默认模型，都沿用 improve-2 |
| D10 | 会话选的模型被删后怎么改写 | 清掉会话上的 `modelEntryId`（02 的命名，指模型条目 id），让会话回到“跟随默认”，并发一条提示说明原模型已删除、改用了哪个默认模型。不把默认模型的 id 写进会话，否则会话会被锁死在这个模型上，与 D1 冲突。连默认模型也没有时，这一轮拒绝执行，提示先添加或选择模型 |
| D11 | 标题和压缩摘要用哪个模型 | 都用这一轮实际使用的模型，也就是会话解析出来的模型 |
| D12 | 生成参数放哪 | 输出上限和默认 reasoning 档位挂到每个模型条目上。磁盘上的全局 `llmParams` 删除，读取旧文件时迁移进条目；会话自己选的 reasoning 档位仍存在会话上 |
| D13 | Settings 模型页优化 | 让用户看出 Default 只管跟随默认的会话（02 的做法是保留 Default 标记、在列表顶部加一行说明）；编辑器显示 reasoning 能力检测结果并可重新检测；编辑器可设这个模型的默认 reasoning 档位；输出上限真正生效；删除确认框说明正在用它的会话会改用默认模型；聊天框菜单的勾表示当前会话的模型，默认模型另加标记 |
| D14 | 实现规则 | 排队消息用提交那一刻会话选定的模型；运行中切换，当前轮继续用原模型，下一轮生效；切换后新模型不支持的会话 reasoning 档位清掉，回到该模型的默认档位；子代理继承父会话这一轮的模型；切到窗口更小的模型不做专门流程，下一轮按新窗口计算，超了走现有自动压缩 |
| D15 | 文档形式 | 02 写关键改动清单；运行时改造不另写模块级改进文档，在 02 里讲清楚。全部写完后做文档自检 |
| D16 | `model.json` 格式 | 顶层的 `provider`、`defaultModel`、`apiConfig` 快照和 `llmParams` 一起删除，文件只留 `activeProfileId` 和 `models`；读取这些字段的 smoke 测试和脚本同步修改。原 `llmParams` 的四个参数都留在条目上：`maxTokens` 对应条目已有的 `maxOutputTokens`，`contextWindowTokens` 条目本来就有，`reasoning` 和 `temperature` 成为条目的新字段 |
| D17 | 聊天框模型菜单 | 不加 “Use default” 之类的额外菜单项。菜单只列模型，默认模型旁加一个不显眼的 `default` 标记；默认模型由用户在 Settings 里改。会话选过模型后就固定用它，没选过的会话（包括新会话）跟随默认。TUI `/models` 同理 |
| D18 | 只有一个模型时 | 这个模型就是默认模型。更一般的规则：没有默认模型时，第一个配置完整的模型自动成为默认 |
| D19 | Web 会话页的模型选择 | 允许在输入框旁的模型菜单里给当前会话选模型；模型多时菜单列表限高、轻量滚动查看 |
| D20 | TUI 怎么选模型、设默认 | `/models` 面板可选择：回车只给当前会话换模型，按 `d` 把光标所在的模型设为默认。`/connect` 仍按 improve-2 规则保存并设为默认 |

D13、D14 是 2026-10-25 agent 给出的建议，用户在 2026-10-26 的回复中没有提出异议，按建议写入。D16 至 D20 在 2026-10-26 确认。

## 3. 本轮不做

- 温度的编辑入口。旧文件里的全局温度按 D12 迁移进条目，但界面上不新增编辑项。
- 每条消息单独指定模型（ZCode 的做法）。模型只挂在会话上。
- “最近使用的模型”列表（opencode 的做法）。
- 切换模型前先压缩的确认流程（kimi 的做法）。
- 从 provider 远程拉取模型列表。
- Agents 配置里的 `model` 字段。现有代码明确禁止在 Agent 配置里写模型，本轮不改。

## 4. 参考项目
