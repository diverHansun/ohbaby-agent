# 04：测试与验收标准

本文定义 improve-7 的目标断言，不是测试结果。调研阶段已有证据见 [01](./01-problem-analysis-and-current-state.md)；正式实施后结果、失败项和未测边界写 05。实施合同见 [02](./02-optimization-plan-and-change-scope.md)。Q1 两层处理已获确认，断流正文投影纳入正式目标断言；用户已授权对齐文档后按批次实施。

## 4.1 什么算通过

每个用例记录：代码 commit/工作区状态、协议及模型、输入条件、期望值、实际值、命令/证据路径、passed/failed/not-run/blocked。测试数量不能替代具体断言。

- **单元**：累积、分类、投影、事件次数、取消竞态和重试计数；输入确定、可重复。
- **集成**：真实协议适配器、Lifecycle、MessageManager、SQLite、Context、RunWorker/现有 UI bridge 的交接；允许确定性 SDK/fetch fixture，但须标明注入点。
- **真实 E2E**：从生产运行入口到真实 HTTP、工具执行、持久化、下一轮请求，使用 `.env` 中凭证和 `tests/models-4-tests.md` 对应协议。单独请求 SDK 不算 Agent loop E2E。

全部适用必测断言通过，才可以写本轮通过。缺凭证/限流/网关不支持/超出请求预算写 blocked 或 not-run；失败不能通过换模型反复试到成功来覆盖。注入的断流、过滤、503 不得写成真实上游事故。

## 4.2 单元与集成矩阵

T01–T22 均为实施验收必测项；“保留”类测试用于证明未改策略，不要求先把正确代码改坏。跨协议是 Chat Completions、Responses、Anthropic Messages 三种，不能用三个同协议模型代替。

| T02 | 单元+Lifecycle：普通文本终态             | stop→EOF、stop→尾部 usage→EOF、多个候选快照均只发一次最终快照及一次 llm:complete；使用最后合法 usage；纯文本早退不能漏发                                                                                                                                                                               |

### T16 的具体计数和限制

- 当前默认是 SDK 额外 2 次、项目额外 5 次；双方都可重试且没有输出的同一错误，单步通道上限 `(2 + 1) × (5 + 1) = 18`。用确定性 fixture 和可控时钟验证，不向付费模型制造 18 次失败。
- 已有调研例子：前 3 次 fetch 注入 503，第 4 次真实成功；预期 provider 调用 2 次、HTTP 分布 3/1、外层 retrying 1 次。正式测试固定这三个口径，不能只断言事件为 1。
- raw ECONNRESET 与 SDK APIConnectionError/APIConnectionTimeoutError 的判断分别记录。保留现有名单意味着可能观察到 SDK 用完次数后外层不重试，不得为了凑到 18 扩大分类。
- Retry-After 与取消发生在 SDK/项目退避阶段分别检查；记录停止后的 HTTP 数、等待时间和 terminal 状态。SDK 内部退避若无法被及时取消，登记已知限制；保留配置不代表承诺零延迟取消。
- overflow 的一次 force 恢复是另一条路径，摘要请求/metadata 请求也可能有自己的尝试；18 不能写成整个运行的硬上限。

## 4.3 真实 E2E 矩阵

实施者读取模型清单实际协议与能力，固定每个 profile 后运行。每个 E 用例按协议分别留证，单个“用例×协议”默认最多 20 次 HTTP（含 SDK 内层、标题/metadata 等请求）；超过就停止并报告该项，不能静默重开凑通过。需要扩大预算时先给出原因与已消耗请求数。模型能力无法触发某个边界时，采用确定性集成 fixture 补语义覆盖，不能称该边界真实上游已验证。

| ID  | 运行内容                                                                                 | 证据与通过标准                                                                                                                                                                |
| --- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1  | 三协议正常循环、两次读取、一次普通工具业务失败后的修正、SQLite 重开续聊                  | 用临时测试目录和只读工具；每次请求/工具 ID/错误结果对应；失败工具后模型能收到结果并继续；每个合法请求完成一次，最终状态正确；重开后实际 HTTP 有正确历史                       |
| E2  | 三协议真实正常终态基线；Responses 真实输出截断；过滤等用受控协议集成补充                 | 真实 length 返回可靠终态，正文保留、运行未完成、无自动续写；用户后续请求实际发送允许正文；filter 使用无害 fixture，不诱导有害内容触发过滤；不能把注入 filter 写成真实模型过滤 |
| E3  | 三协议真实流消费中注入 transport 中断，以及主动取消；保存→用户发消息→SQLite 重开再发消息 | 已有正文后不自动重发；真实 HTTP 校验断流投影（Q1 已确认）与取消正文排除；工具阶段取消保留已完成配对结果；记录“真实上游流+本地故障注入”，不能写真实上游故障                    |
| E4  | 三协议生产压缩、续聊和重开；整合已有窗口/usage/工具链                                    | force 进入真实摘要并确认 stop/非空，校验失败历史选择规则、合法工具关系、摘要后新估算、下一请求及重开续聊；force 不证明自然达到 95%，不证明上游真实 overflow                   |

E1 涉及模型是否遵循指定工具次序，harness 应核验实际发生的步骤，不凭最终自然语言宣称工具调用成功。偶发模型不按提示执行，保留该次失败记录，区分模型行为和实现错误；可调整测试指令后另留新证据，不能覆盖原始结果。

E3 的断流用例和主动取消用例分开运行。为工具阶段取消设置确定性暂停点，等待已完成结果持久化后再取消剩余执行，避免用时延猜测“应该已经保存”。

### 下一次请求必须检查什么

E2/E3/E4 至少断言以下字段或其可验证摘要：实际请求中的角色、正文、工具 callId/result、协议特殊状态是否保留/排除、窗口来源、最终估算与当前 scope。数据库中保存过正文不等于下一次请求正确发送了正文，模型回答“我记得”也不算证据。

完整请求可在本地受限证据目录临时观察；正式证据保留测试专用正文、计数、ID 配对和内容 hash。API key、Authorization header、个人会话数据与原生不透明载荷不进入提交或日志；失败日志同样脱敏。

## 4.4 运行入口与证据组织

### 已有命令

以下从仓库根目录运行。具体定向测试由 Stage 涉及的现有文件选择，不让分类型脚本忽略无分类后缀的 `llm-client.test.ts`：

```sh
pnpm exec vitest run packages/ohbaby-agent/src/core/llm-client/llm-client.test.ts packages/ohbaby-agent/src/core/llm-client/native-state.unit.test.ts packages/ohbaby-agent/src/core/lifecycle/lifecycle.unit.test.ts
pnpm test:unit
pnpm test:contract
pnpm test:integration
pnpm preflight
```

定向用例先运行；全量单元/合同/集成覆盖按影响选择，最终 preflight 统一执行。不要把同一全量集反复跑多次当额外证据。

现有 `tests/smoke/formal-cache-session.ts` 及真实 cache harness 可复用生产入口、SQLite 和请求观察能力；cache 通过本身不能代替本轮 loop 验收。正式实施需把本次调研的临时复现纳入可维护测试。

### 计划新增的真实 loop 入口（尚未实现）

建议使用 `tests/smoke/agent-loop.real.e2e.test.ts`、独立 `vitest.agent-loop-real.config.ts` 和 `scripts/run-real-agent-loop-e2e.mjs`。这是文件级建议，不是已经可运行的命令。实现时可按现有 smoke 布局调整，但必须给出单一可重复执行入口及 profile/用例选择方式。

默认 Vitest 配置不应自动触发付费调用；现有 `vitest.e2e.config.ts` 只收集 packages 下的 E2E，不能假设会发现 tests/smoke 新文件。新 runner 必须显式加载相应配置、凭证及限制，并对未执行用例明确报状态，不能因 0 tests 得到“通过”。

证据放 `.ohbaby/test-evidence/improve-7/<batch-or-run>/`，包含脱敏 JSON、测试日志、运行摘要。正式 05 摘要应记录可追溯断言和限制；不要求提交 API 原始载荷，不把临时绝对路径当唯一验收依据。`tests/models-4-tests.md` 为用户已有本地清单，不顺手提交。

## 4.5 分批门槛与最终验收

| 批次    | 核心验证                                                        | 审查重点                                                      |
| ------- | --------------------------------------------------------------- | ------------------------------------------------------------- |
| Stage A | T01 + 定向三协议集成；另做轻量真实工具循环，完整 E1 放 B/D 回归 | 只替换内部工具累积形状，三协议行为对应                        |
| Stage B | T02–T08、T15 + E2 的完成/终态部分；E1 回归                      | 请求完成、保存失败、Run 结果分开；取消及 usage 精确边界       |
| Stage C | T09–T14、T18 + E3；E2 的下一轮历史断言                          | 按已确认 Q1；正文、事实、原生状态和工具关系跨 SQLite/摘要一致 |
| Stage D | T16–T22 + E4；同一最终版本重跑 E1–E3 必要全链路；preflight      | 管理规则、SDK 限制、主子隔离、最终整体合同                    |

每批先看缺陷复现，再实施、测适用单元/集成/真实 E2E，独立子代理审查后本地提交。早期批次未实现的后续断言标记未完成，不将其当成该批新回归，也不宣称 improve-7 全通过。出现修复后，应重跑受影响用例；不相关全量无需机械重复。

最终审核必须同时查看：

1. T01–T22 与 E1–E4 的状态和代码版本，不只看 test count。
2. 完成次数、Run 状态、保存结果、工具执行次数和下一 HTTP payload 的交叉验证。
3. 原算法/95% 阈值/SDK 配置未被顺带改动；估算变化能由请求内容变化解释。
4. 真实、注入、模拟证据分开，网络限制及未测项单列。
5. 02 所列模块文档受影响章节已随实施更新，旧轮次历史验收不被改成新结论。

### 继续保留的容量验证缺口

improve-6 的真实百万窗口自然越过 95% 自动压缩、真实上游 context overflow，尚未实测。本轮 T21 的确定性阈值测试和 E4 的 force 压缩都不能关闭这两项。它们继续进入整个迁移的最终验收清单；不阻止先完成本轮 loop 适配，也不表示推迟到“压缩算法优化”后才需要验证。

按用户授权执行上述实施验收并创建 05 记录结果；不 merge/push。正式验收时有必测项失败或未执行，应明确写“部分通过”及影响，不能写全部通过。
