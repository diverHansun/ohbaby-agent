| Q2  | 能力资料未知不阻止生成，服务端错误按现有流程处理；缺少可靠参数映射时使用服务默认，见 §3.4。          | §3、UC01、T06–T09、T23 |

## 2. 三协议与旧配置兼容（P01、P03）

### 2.1 单一协议字段

沿用 `interfaceProvider`，有效值只有 `openai-compatible`、`openai-responses`、`anthropic`。SDK、REST connect/probe、Web wire/client、TUI 和 CLI 命令贯通同一枚举。

选择优先级：用户显式选择 > 已保存显式值 > 原有 base URL 推断。仅旧配置/旧客户端缺字段时使用推断；空字符串、拼错值、null 等非法显式值返回参数错误，不能悄悄推断。OpenAI 形状地址缺省 Chat；不按模型名自动选择 Responses，不在请求失败后切协议重试。

前端保存草稿区分“尚未选择”与“明确选择”；读取已有模型必须回填协议。更换 key、窗口、max output 不改变协议；显式协议与 URL 不兼容时显示真实请求错误，不能覆盖用户选择。

### 2.2 连接身份与资料更新

能力资料按 provider、model ID、协议、规范化 endpoint 匹配。只规范化可证明等价的 URL 部分，不去掉区分路由的路径，不无条件小写可能大小写敏感的 model ID。密钥不参与可展示身份，不写进日志/指纹。

兼容旧的通用 profile：保留原来未限定 endpoint/protocol 的配置语义；准确限定的记录优先于通用记录。更新一个连接的窗口资料，不能删除其他路由的能力记录，也不能把第一条同名 profile 复制到新路由。明确用户覆盖优先于自动发现；未命中不是 mode:none。

更换凭据后使当前发现结果过期并重新查询，避免继续使用另一账户的能力结论；无需把密钥明文或密钥哈希暴露到公共 DTO。不要顺带设计一个新的模型资料数据库。

## 3. 保存后识别能力与默认选择（P02、P09、P10）

### 3.1 发现来源和边界

1. 校验并保存连接；持久化成功即可报告“已保存”。
2. 后端查询该连接的模型元数据；可复用已有窗口探测请求，避免为窗口/推理重复取同一列表。
3. 元数据不完整时，结合准确匹配的已验证能力配置/官方已知 profile。尊重明确的用户 override，并保留来源。
4. 输出识别状态和可用能力；查询失败、未找到精确模型或缺字段均不能转成“不支持”。

沿用 `ReasoningCapabilities` 及现有 wire 转换。需要补充的是默认档位/有序档位和发现状态，避免同时新增多套 enabled/supported/ready 布尔值表达相同含义。前端只消费一个公共能力视图，不能看到 API key、opaque native 数据或协议转换细节。

建议公共视图概念上包含：发现状态（检测中/已识别/未知）、是否可调/可关闭、按弱到强排列的原始 effort 值、有效默认选择，以及必要的简短未知原因。最终字段名遵循现有 SDK 风格；实现时在 SDK 类型与 REST schema 中同时定义，不复制三份枚举。

`reasoning:true` 只证明模型支持推理，不能自动补上 low/medium/high 或 supportsDisabled。部分已知的信息保留，只有足够确定的选项才能显示。查询全部档位不靠模型自述；本轮不实现穷举生成请求的自动探测器。显式重试检测复用同一查询路径。

### 3.2 默认算法

对新连接或没有兼容用户选择的连接：

1. mode:none：不发推理控制参数，隐藏强度控件。
2. binary：默认开启，不伪造 effort；仅支持关闭时提供开关。
3. effort：支持 `medium` 则选 `medium`；否则选已确认且仍在支持集合内的厂商默认；否则选**已知顺序中的最低支持推理档**。
4. 不为第 3 步的例外弹窗或醒目提示，直接显示实际选中的原名。

最低档不能按字母排序、接口数组的偶然顺序或关闭值决定。已知标准档位可在后端定义稳定顺序；厂商自定义名称需 profile/元数据提供明确顺序。只知道支持推理、不知道档位或其顺序时，无法执行“最低档”，按 Q2 处理，不能凭空给 low。

writer 必须能显式清除不兼容的旧 effort/override，不能仅用 `undefined` 合并导致旧字段继续存在；内部清除语义与 REST 输入校验分别测试，最终字段沿用现有配置风格。

已保存的兼容用户选择优先于重新套默认规则。模型/协议/地址变化时重新校验：新会话默认可重置为新能力的默认；已经发送的显式选择不静默改写，见 §5。

### 3.3 查询与缓存

- 能力按连接身份匹配，模型列表分页时遵循服务返回的分页信息；未命中不能取相似 display_name 当推理能力。
- 超时覆盖响应头和正文读取；请求取消、无效 JSON、鉴权失败、限流和缺字段均有可识别结果。
- 新保存、换 key 或显式重查使旧查询失效；旧响应不能回写新连接。无需后台定时轮询。
- 能力查询不作为生成准入门槛：检测中、超时、资料缺失均允许发送，按 §3.4 走服务默认。每个 Run 在准入时固定当时可用的解析结果；后来返回的能力不改变运行中请求参数，更新前端并供后续 Run 使用，不能永久缓存 unknown。结果必须匹配同一连接版本。
- 同一连接的临时查询失败可保留已有已验证资料及过期标记；不能把 A 的资料当 B 的缓存。
- 能力发现完成后更新既有 current-model 读取/事件刷新路径；保存成功不等于发现成功，也不等于旧 Run 已换模型。

### 3.4 未知能力时发送什么

“未知”是元数据/本地 profile 没有足够资料，不是模型不可用或不支持推理。仅缺少这些资料时，resolver 返回可发送的服务默认路径，不再抛 `Reasoning capabilities unknown`。这个路径不得伪装成 mode:none/disabled，也不能用捕获全部 ConfigError 的办法绕过非法配置校验。

缺少可靠映射时省略无法确认的 reasoning/thinking/effort/budget 控制字段，不猜 medium、low 或关闭参数；正常模型、消息、工具及其他已有合法参数照常发送。已有会话偏好仍保存在会话/submission 中；实际未应用时只显示“服务默认”这一状态，不宣称保存的 high/medium 已生效。未知模型不展示伪造档位列表，发送按钮保持可用。已明确不支持某个值的情况仍按已知能力校验，不能借未知放行隐藏真正错误。

请求控制与响应保存分开：没有发送 effort 不意味着服务不会产生 reasoning。三协议的 reasoning/native 捕获、持久化、工具配对、历史来源检查继续生效；Responses 所需 `include: ["reasoning.encrypted_content"]` 等续接选项不能因不带 effort 被一起删除。应将这些必要请求选项与推理档位解析解耦，并分别验收。服务若拒绝请求，记录真实错误，不自动换协议、删参数重发或扩大 SDK/项目重试范围。

同一策略覆盖 agent-step、context-summary、session-title，不能主请求放行后标题或摘要又因 unknown 本地拒绝。未知情况下不保证特定强度生效，只保证正常发送和如实处理服务结果。

## 4. 保存与任务启动协调（P04、P05；Q3/Q4）

### 4.1 建议的最小数据流

```text
提交连接 → 后端串行校验/持久化 → 发布新的配置版本 → 返回已保存
                                      ↓
                             识别能力并更新当前配置视图

旧 Run → 保持旧 client / Context / 工具 / 子代理，继续运行
新 submission → 持久化队列 → 运行准入检查配置版本/能力
                              ↓
                    旧 runtime 无实际运行工作
                              ↓
                    释放旧 runtime，创建最新配置 runtime → 新 Run
```

保存不等待旧任务完成；新任务可提交，后端说明等待切换，不因当前有 Run 或保存操作而禁用前端按钮。无效表单仍正常校验。连续重复点击要去重或按既有 latest-save 合并，不能靠无限创建保存任务处理。

“保存成功”是配置已持久化。模型在 Run 准入时绑定，不能以第一个 HTTP 发出时为界。旧 Run 的下一步模型请求也继续旧模型；Run 内摘要、工具后的续答、SDK/业务重试、所属新启动子 Run 都不跨路由。

### 4.2 等待切换不能伤及工作

配置变化时将 runtime 标记为待换，不能立即调用当前的强制 `resetRuntime()`。在 composition 提供小型活动查询/等待通知，复用 Run、工具、子代理、shell job 的现有状态；没有需要时不建立通用 lease 框架。

自然空闲的判断包括正在执行的主 Run、子 Run、工具、关联后台 shell 工作和必要清理。已 completed/interrupted 的子代理记录本身不算忙，不能因此永远不切换。活跃长期工作确实会延迟切换，应展示可解释的等待原因；用户取消仍走旧 runtime，不能自动替用户取消。

等待新配置的 submission 仍属于队列，不能先登记为旧 runtime 的 active Run 再等待空闲，否则会自等死锁。准入栅栏放在活动登记/Run 创建之前；只有等待任务时应立即允许切换。

空闲判定与关闭旧环境/绑定新环境之间要有准入保护，防止刚判空闲又开始一个旧任务。等待期间再次保存 B→C，最终只为最新 C 创建下一环境。旧环境释放后，恢复后的子代理下一次启动使用新环境，并重新校验原生历史来源；不把旧 endpoint 的 opaque 状态发给新 endpoint。

### 4.3 多 workspace 与失败

模型文件默认位于共享配置根，保存协调不能仅在一个 workspace backend 内有效。按配置文件路径串行发布，同一 daemon 的各 backend 在新 Run 准入时检查最新配置版本；其他 workspace 已运行任务仍保留旧 client。

锁只覆盖发布及准入绑定，不覆盖远端模型请求或整段等待。新版本可以用已有配置指纹/版本机制表达；不是要求新增一个持久化版本表。跨独立进程/手工改文件至少在新 Run 准入重新读取或比较磁盘配置，不把进程内计数宣称为跨进程同步。多进程同时写配置若无现成保障，须在实施前识别并明确支持边界，不能静默丢写。

保存需要处理 P11 的多文件部分成功：密钥文件与 model.json 的写入在同一个配置协调范围内准备和提交；可捕获的写失败恢复原有效配置，只有提交完成才发布版本。若恢复也失败，报告部分保存/需修复并阻止新任务采用不一致配置，不能声称旧文件未变。后端读取同样经过协调，不能靠“不更新内存版本”遮住已经变动的磁盘。这里不宣称两个文件天然具备跨进程/崩溃事务性；复用现有原子文件工具并验证失败恢复，不引入通用事务框架。

普通未提交的保存失败不发布新版本、不切换旧环境。持久化已完成而 reload 或新 runtime 初始化失败，状态应是“配置已保存，但暂不可运行”，不能回报为“完全未保存”。能力未知本身可正常生成；真正的新配置初始化失败则明确报告，不偷偷退回旧模型替用户生成。强制退出/显式取消仍使用原有清理路径。

设置页显示已保存配置，运行信息显示实际 Run 的模型；不能把旧任务标签瞬间换成新模型。切换后使用新窗口/计量 profile，旧模型 overflow 和校准状态不得继续影响新模型；保留 improve-6/7 的规则，不重设算法。

## 5. 推理选择进入消息与 Run（P06、P10；Q1/Q2）

当前会话持久保存一个推理偏好，各会话互不影响；用户没有选择时使用 §3 默认。复用会话 metadata 的扩展路径，不为此建立独立配置服务；新会话无 override，恢复会话恢复其有效选择。

点击发送时形成独立 submission reasoning 快照，经过 SDK → REST/in-process → prompt scheduler/store → AgentService → RunManager → Lifecycle。沿用既有 ReasoningConfig/Intent，保留默认与显式选择的区别；不能把后台算出的默认值伪造成用户显式强制选择。

- Run reasoning 已有固定机制，继续复用；活动摘要与子代理继承本 Run intent。
- 已排队消息持有提交时的 reasoning；保存模型不要求持久化整份 client 或明文 key 到队列。
- 尚未准入的队列消息按最新模型启动；若能力已明确且原显式 effort 不兼容，在准入前明确提示调整/重发，不能悄悄降档，也不能无限等待未知条件；该次不兼容 submission 终结后，后续兼容消息仍可推进。
- 旧客户端/旧队列没有 reasoning 字段时按既有默认路径读取并做当前能力校验。
- 同 clientRequestId 的重放返回同一 submission；携带不同 reasoning 的冲突请求不能覆盖原任务。队列文本编辑保留原 reasoning，除非界面明确支持并提交设置修改。
- 手工摘要有 active Run 时用该 Run 的模型和 reasoning 快照；无 active Run 时使用当前会话有效偏好及最新模型，并经过与新 Run 相同的准入等待。若旧 runtime 仍有后台工作，不得直接取旧 runtime 执行却标成新模型。手工摘要自身也纳入 runtime 活动统计，不能在摘要进行时释放它。纯视觉切换不重建 runtime，不重新执行完整 connect 保存。

能力未知时不执行“已知不兼容”的拒绝分支，按 §3.4 发送服务默认并保留偏好；能力后来识别成功，仅供后续 Run 解析使用。

## 7. 风险、回滚与范围约束

持久化新增字段保持可选，旧数据无字段仍可读取；不要删除 Chat 支持。数据库如需扩展 submission/session 元数据，使用已有迁移路径并测试旧库升级；旧程序能否忽略新字段要用真实读取验证，不能仅因字段可选就假定可回滚。先备份隔离测试数据，迁移不触碰用户日常配置。

本轮不新建三套连接接口、不替换 SDK、不做自动协议降级、不枚举付费生成请求探测全部能力、不更改压缩/prune/95%/cache 算法、不重写 TUI 编辑器，不做设计系统重建。新旧 runtime 立即并行不在本轮范围。
