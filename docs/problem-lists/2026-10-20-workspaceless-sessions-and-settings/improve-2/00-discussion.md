# 讨论记录与已确认要点

> 2026-10-22 已确认决策，规划已整理，尚未实施。本轮接替 [improve-1 §2.4](../improve-1/02-optimization-plan-and-change-scope.md) 的设置批次，并把范围扩到完整的设置后端。现状依据见 [01](01-problem-analysis-and-current-state.md)，方案见 [02](02-optimization-plan-and-change-scope.md)。

## 1. 为什么开 improve-2

improve-1 原计划分两批：先做工作区，再做设置。工作区后端已经提交，设置一行代码都还没写。这期间 `ohbaby-llm` 抽包和 SDK/server 结构整理都已合入，improve-1 §2.4 里的锚点和接口设想已经对不上现在的代码。

用户希望为后续 Web 端优化和重构铺路，先把设置后端规划完整。因此把设置从 improve-1 切出来，在同一议题下新开 improve-2，属于“主动切割”。improve-1 的第一批 Web 接入（G1）仍归 improve-1，它的 05 尚未闭环；设置是独立范围，不依赖 G1 的 Web 页面，所以不等 improve-1 闭环再开新轮。

## 2. 范围：标准档

| 分区 | 本轮内容 |
|---|---|
| 模型 | `model.json` 的 `models[]` 每条保存一个模型的完整配置，按 provider 字段分组展示；模型可新增、修改、单删，也可按 provider 整组删除，并独立选择全局默认模型 |
| MCP | 全局 MCP 文件的完整管理：新增、修改、删除、启用/停用；按目录查看运行状态、失败原因和工具列表；手动重连 |
| 联网搜索 | 完整读写搜索配置（服务、key 变量名、key、`baseUrl`、默认参数），修掉保存 key 时丢字段的问题 |
| Skills | 只读，按目录展示生效的 Skills 及来源；复用现有机制补齐文件更新、增删的自动刷新 |
| Agents | 只读，按目录展示生效的 Agents 及来源（内置、全局、项目） |
| 关于 | 版本、ohbaby home、日志与诊断路径、默认工作区 |
| 变更传播 | 写入后通知所有已加载的实例，并在下一轮开始时生效 |

顺带修复四个已证实的问题：搜索保存覆盖配置、共享 backend 的 Skill 加载路径忽略 `skills/settings.json`、Agents 在 daemon 里按 `process.cwd()` 找项目配置、MCP 摘要丢失错误和工具数。

## 3. 已确认的决策

| 决策项 | 结论 | 理由 |
|---|---|---|
| 接口放在哪一层 | **按数据性质分**。全局配置的读写（模型、搜索、全局 MCP 文件、关于）放 daemon 全局层，不需要目录头；随目录变化的内容（MCP 运行状态、生效的 Skills/Agents、手动重连）放实例层 | 全局配置本来就与目录无关，放实例层会让“写一次要通知其它实例”变成每个实例的负担 |
| 多 provider 怎么存 | **扩展 `model.json`**，连接字段（地址、协议、key 变量名等）直接放在 `models[]` 的每个条目里；provider 只是条目上的字段，不另建 `providers` 结构；key 仍放 `.env` | 现有档案已有 `id`、`provider`、`baseUrl`、`interfaceProvider`、`label`，只需补 `apiKeyEnv` 等少数字段；不新增文件或连接表，旧文件通过统一读取适配 |
| 同一 provider 下的模型 | 同一个 provider 可以保存多个模型，每个模型保存完整连接配置：地址、接口协议、key 引用等，并分别记录能力 | 保留 `/connect` 已有的模型配置能力，不要求为不同配置新建 provider |
| 修改模型配置 | 修改地址、协议或 key 只影响目标模型，不联动同 provider 的其它模型；修改当前模型时下一轮生效，当前轮继续完成 | 模型配置独立，不增加 provider 到模型的继承与批量覆盖规则 |
| 模型凭据 | key 原文仍存 `.env`，各模型的连接保存自己的 `apiKeyEnv`；切换时恢复目标引用，修改或清除 key 只影响目标。历史共享变量由后端自动隔离 | 补全多模型保存与切换，不增加用户操作；不能把旧档案未保存凭据引用的缺口变成产品限制 |
| 同名模型多份配置 | 新设置接口**不查重**：用户新增的每一条都是独立条目，同一服务商、同一模型名可以因 key 不同分别保存，用可选备注区分。旧 `/connect` 按 provider + 模型名 + 规范化地址匹配原条目并更新（含只改协议或 key），没匹配到才新增 | 查重要读取并比较 key 原文，成本和泄露风险都不划算；是否重复交给用户和前端提示判断 |
| 保存与切换 | 新增候选模型只保存配置，不改变当前模型；明确选择后，所有会话下一轮使用所选模型 | 整理模型列表不会顺便改变默认模型；保存和切换是独立后端操作，前端入口位置另行设计 |
| 删除模型 | 支持单独删除模型，删除入口统一在 Settings；删除即移除整个条目（含连接配置），只保留 `.env` 中的 API key；删除当前模型后自动切到下一个模型，无需用户先切换，下一轮生效 | 删掉后不能选也不能恢复的“保留连接”没有用处，去掉可省一层数据结构；本轮只实现后端，Settings 页面以后实现 |
| 删除服务商 | 删除 provider 即删除 `provider` 字段等于它的全部条目；若包含当前模型，按原列表顺延并跳过被删除条目，末尾回到开头；下一轮生效，保留 API key；无剩余模型则没有默认模型 | 与单独删除模型保持一致，不要求用户预先切换 |
| 模型顺序与删空 | 新增模型排在列表末尾，编辑和切换不改变顺序；删除当前项后按列表顺序顺延，末尾回到开头；全部删完则没有默认模型，保留 API key | 选择结果可预期，不需要额外配置优先级 |
| 保存与能力获取 | 本地校验通过后先保存，再后台自动获取 reasoning 能力；获取失败不撤销保存。未获取到时保留默认 Reasoning，不猜档位、不反复提示 | 上游暂时不可用不妨碍配置整理，减少用户等待和操作负担 |
| 推理能力来源 | 能力按条目分别记录。来源依次是：内置规则（**保留**，但去掉 provider 名称条件，改为按官方地址 + 模型名 + 协议匹配）、上游元数据、主动探测。候选模型保存后只读上游元数据；主动探测会真实发送聊天请求，只在选为当前模型或手动 probe 时进行。不新增手填能力的设置接口 | 内置规则本来就带官方地址条件，只去掉名称条件就能支持自定义名称；整体去掉规则会让官方模型每次都付费探测，且 OpenAI 等上游元数据不含档位，结果反而变成 unknown |
| 切换模型作用于谁 | **只改全局当前项**，所有会话从下一轮起使用。**按会话保存 LLM 配置本轮不做** | 用户明确要求先不做会话级模型 |
| 何时生效 | **写入 + 下一轮生效**，与现有模型切换一致；保存 MCP 后只写文件并通知，不自动重连空闲实例；需要时显式重连当前项目；不加文件监听 | 复用现有机制，减少自动重载路径；保存成功后，已初始化项目的连接状态可暂时反映旧配置 |
| 项目配置 | **只读**，接口只写全局文件；项目配置由用户手改 | 参考 codex、kimi：API 不需要判断写到哪一层 |
| Skill 动态更新 | 沿用按需加载与注册表刷新，更新、增删不要求用户重启或手动刷新；本轮仍不提供 Skill 编辑接口 | 正文已有每次读盘机制；普通目录增删和元数据刷新缺触发，作为后端接线缺口处理，不另起一套热加载设计 |
| MCP 同名覆盖 | 全局与项目定义同名服务器时，Web 编辑仍写全局文件，响应提示“被项目配置覆盖” | 参考 codex 的 `okOverridden`，不阻止操作，但让用户知道为什么没生效 |
| 凭据 | 接口从不返回 key 原文，只返回变量名和“是否已配置”；更新 key 用三态：不传保持、空串清除、给值替换 | 参考 kimi，避开 opencode 明文返回凭据的做法 |
| TUI 与 JSON-RPC | 新接口只走 HTTP，不加 JSON-RPC 方法；TUI `/connect` 交互不变，保存时按上文规则更新或新增目标条目并设为当前项，与 Web 共用同一套条目写入逻辑 | 只改共用逻辑，TUI 无需新界面 |
| 关键改动清单 | 02 写入承重项清单 | 改动跨 agent、llm、server、sdk 多个包 |

## 4. 本轮不做

- 按会话保存或切换模型。
- 编辑项目级配置（MCP、Agents、Skills）。
- MCP OAuth 登录、Skills/Agents 启用停用或编辑。
- 权限默认值持久化，代理、日志、主题的配置文件。
- 通用配置文件监听，hooks、插件页、快捷键；Skill 的动态加载沿用现有机制并补齐刷新触发。
- 从 provider 远程拉取模型列表。
- 生成参数（温度、`maxTokens`）的编辑接口。现有推理开关保持不变。
- 手动填写推理能力的设置接口；本轮使用自动获取结果提供可选项。
- 单个 MCP 服务器重连（本轮重连整个目录的 MCP）。
- 下线旧的 `/v1/model` 和 `search-api-key` 接口，等 Web 迁到新接口后再定。
- Web 设置页面本身。本轮只交付后端和 SDK 类型，页面在 Web 重构规划后再做。
