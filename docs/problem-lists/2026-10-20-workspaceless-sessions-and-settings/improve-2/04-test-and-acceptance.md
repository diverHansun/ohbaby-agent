# 4. 测试与验收标准

> 对照 [02](02-optimization-plan-and-change-scope.md) 验证。本文是实施后的验收标准，规划期没有运行这些测试。

## 4.1 测试范围与运行方式

沿用项目现有的 unit、contract、integration 分类，文件命名为 `*.类型.test.ts`。

| 类型 | 重点 |
|---|---|
| unit | 写入函数的合并规则、key 三态、凭据脱敏、设置版本的分区哈希 |
| contract | SDK 类型与服务端响应字段一致，错误码与格式 |
| integration | 真实临时 `OHBABY_HOME` 与 daemon 下的读写、生效、通知、多目录 |

所有用例使用临时 `OHBABY_HOME`，不碰开发者自己的 `~/.ohbaby`。定向测试用 `pnpm exec vitest run <具体测试文件>`；涉及 daemon 和共享 dist 的集成用例加 `--no-file-parallelism`。不调用真实付费模型，用现有的假 LLM 客户端或本地假服务。T12、T13 可注入假客户端，但其它设置分区的版本检查仍须生效（02 §2.5）；无模型配置时仅改搜索 key，也不能误触发默认 LLM 加载。T16、T19 的模型路由、协议和 key 验证使用本地假上游及正常配置加载路径，不能固定注入一个客户端后声称已验证模型切换。

## 4.2 关键场景

### Stage 1：缺陷与生效机制

| ID | 场景 | 类型 | 验证点 |
|---|---|---|---|
| T1 | 搜索保存不丢字段（B1） | unit + integration | 已有 `baseUrl`、`defaults` 的 `search.json`，保存 key 后这些字段原样保留 |
| T2 | Skills 配置目录生效（B2） | integration | `skills/settings.json` 指定的额外目录中的 Skill，在 TUI 与 daemon 共用 backend 的模型工具中可见；Stage 2 的设置读取沿用同一注册表 |
| T3 | Agents 按目录加载（B3） | integration | 目录 A、B 的项目 Agents 配置不同，daemon 启动目录是第三个目录；A、B 实例各自只看到自己的项目 Agents |
| T4 | MCP 摘要完整（B4） | unit | 失败的服务器在命令摘要中带 `error`；连接成功的带 `toolCount`；旧字段不变 |
| T12 | 下一轮生效 | integration | 改全局 MCP 文件后，下一轮开始前 MCP 按新配置重连；运行中修改时出现 “Waiting to apply settings”，当前轮不中断；只改 `model.json` 时 MCP 客户端不重连；手改 `agents/settings.json`、`tools/search.json` 后下一轮生效；注入假 LLM 客户端的实例同样生效；多次重建后 MCP、Skills 的变化监听数量不增长 |
| T23 | Skill 自动刷新触发 | integration | 在临时目录真实更新正文、描述，新增和删除 Skill；不重启、不手动 reload、不先打开设置页，下一轮模型目录及显式 Skill 使用能反映变化，正文继续按调用读盘；删除项不再可用，普通读取不会循环刷新或积累监听。测试必须经过生产触发入口 |

### Stage 2：实例层只读

| ID | 场景 | 类型 | 验证点 |
|---|---|---|---|
| T5 | MCP 状态 | integration | 全局、项目、插件来源的 `origin` 正确；同名时显示项目来源；工具数等于过滤后的工具列表长度；失败原因可见 |
| T6 | Skills 列表 | integration | 字段齐全，不同目录返回各自生效的 Skills；更新、增删后的设置列表与 T23 中的模型可用目录一致；只读接口不新增一份独立缓存 |
| T7 | Agents 列表 | integration | 内置、全局、项目的 `origin` 正确；`disabled` 的不出现；缺目录头返回 400 |

### Stage 3：全局层与通知

| ID | 场景 | 类型 | 验证点 |
|---|---|---|---|
| T8 | 搜索读写 | integration | `GET` 不含 key；`PUT` 只改出现的字段；key 三态对应保持、清除目标使用、替换；独占受管变量清除后文件和进程值同步，仍共享的引用不被误删；响应按实际解析结果报告 `apiKeyConfigured`；保存后下一次搜索使用新配置 |
| T9 | MCP 全局文件管理 | integration | 新增、修改、停用、删除都写入文件，其它服务器条目不变；`env`、`headers` 补丁只改提到的键；非法配置返回 400 且文件不变；删除不存在的返回 404；项目配置同名时 `overriddenIn` 含该目录 |
| T10 | 关于 | contract | 版本、ohbaby home、默认工作区与实际一致；不需要目录头 |
| T13 | 写入后通知 | integration | 加载 A、B 两个实例并初始化 MCP，通过全局层写 MCP，两个实例的事件流都收到 `settings.changed`；即使实例空闲，保存和随后读取状态也不触发重连，连接次数不增加，各自在下一轮应用新配置；写模型时还收到 `model.invalidated`，只写搜索 key 时不收到；之后才加载的实例 C 读到新配置；全局路由不截走实例层的 `/v1/settings/mcp/status` |
| T14 | 手动重连 | integration | 只重连请求目录，连接与工具刷新完成后才返回最新状态并记录版本，下一轮不重复重连；有轮次、子代理或后台工具等活动时返回 409 `INSTANCE_BUSY`；用可控制的异步步骤验证忙碌检查与重连之间不能插入新轮次；其它已加载实例不重连 |

### Stage 4a / 4b：模型条目、推理能力与整体检查

| ID | 场景 | 类型 | 验证点 |
|---|---|---|---|
| T15 | 旧文件读取与首次写入 | unit + integration | 多次 GET 的规范化 id 稳定且不写文件；首次写入固化 id、条目连接字段和 `activeProfileId`，保持旧算法实际选中的档案及预算，当前条目从顶层补齐 `apiKeyEnv`；无匹配档案时从顶层合成当前项；其它历史条目保留已知字段并标记 `configurationComplete: false`，不猜 key、不自动发现或选用，PATCH 补齐（含明确的无 key 模式）后可正常选择；新旧读取入口都能处理 `active: null`，不会直接落回旧磁盘校验；旧文件中带显式能力的通配档案能匹配当前配置时，迁移后当前模型的能力不变，缺路由字段的通配档案标记为不完整；`models[]` 按文件原顺序固定，此后保存不再把当前项移到末尾 |
| T16 | 条目独立与凭据隔离 | integration | 同 provider 的 A、B 两个条目各自保存地址、协议和 key，切换后下一轮使用目标条目的配置；修改 A 不改变 B，当前轮继续完成；新 key 自动分配独立变量；旧文件 A、B 共用变量时，替换或清除 A 只影响 A，B 和搜索仍能使用原值；模型与搜索并发保存不同 key 均不丢失，故障回滚不覆盖另一项成功写入；后台元数据写回后所有实例收到通知 |
| T17 | 兼容旧入口 | integration | TUI `/connect`、`POST /v1/model`、`POST /v1/settings/search-api-key` 交互入口不变；`/connect` 按 provider + 模型名 + 规范化地址命中已有条目时更新它（含只改协议或换 key）并启用，未命中时追加并启用，其它条目和顺序保留；共享变量先隔离再写 key；多条只差协议的旧条目时更新列表中第一条；缺 `baseUrl` 的旧条目不被匹配；缺 `provider` 的旧条目按规范化后的 provider 匹配；旧读取经统一规范化及当前配置投影；搜索保存保留其它字段；JSON-RPC 方法列表不变 |
| T18 | 推理能力获取（4b） | unit + integration | 使用本地假上游：给官方地址起自定义 provider 名称仍命中内置规则，且不发探测请求；调用 probe 且规则和元数据都无结果时才主动探测，结果写回该条目；重新获取的结果替换旧自动结果；没有可确认能力时返回 unknown，不据名称补出选项；覆盖三种接口协议 |
| T19 | 保存与切换分离 | unit + integration | 当前使用 A 时保存候选 B、C，当前项和全局生成参数保持不变；B、C 的后台发现互不取消，结果分别写回档案且不激活任一候选；无当前项时保存第一个模型仍返回 `active: null`；明确选择 B 后，当前轮仍正常完成，各实例下一轮使用 B；上游模型名含 `/` 时能保存并按条目 id 选用 |
| T20 | 先保存与默认 Reasoning | unit + integration | 用本地假上游控制响应：能力请求尚未完成时保存接口已成功返回、文件已落盘；超时、401 或缺少能力字段均不撤销保存；未知时返回 `unknown` 和空 `efforts`，模型请求不注入推理开关或强度，沿用 `service-default`；仅因能力获取失败不产生反复警告；非法本地参数或文件写入失败仍返回错误，真实聊天请求错误不被吞掉；候选条目保存后假上游收不到主动探测请求；同路由不同 key 的两个条目能力分别记录不混用；PATCH 改地址、协议或 key 后旧自动能力清除；在同一变量里换 key 值后，旧 key 发起的元数据请求晚到也不能回写 |
| T21 | 删除模型、服务商与稳定顺序 | unit + integration | 新增追加，编辑、切换和能力写回不重排；删除非当前项不切换，删除当前项按原列表顺延并循环，当前轮不中断、下一轮生效；单删移除整个条目，`.env` 中的 key 保留；整组删除移除该 provider 的全部条目并保留 key，顺延跳过本次删除的全部条目，覆盖 provider 交错排列和含 `/` 的 provider 名称（URL 编码）；只跳过配置不完整的历史条目，不因能力未知或网络失败跳过；无完整可选项时 `active: null`、新轮次不能用已删模型；晚到的元数据结果不能恢复删除内容；不存在的删除返回 404 |
| T22 | 不查重与条目身份 | unit + integration | 同 provider、同模型名、同地址的条目可以因 key 或协议不同新增多份，各自获得独立 id，备注可选；各自切换、编辑、删除与能力获取互不影响；当前项按条目 id 记录；按 id 编辑协议保留 id、位置和当前选择，下一轮生效；新增和编辑过程不读取、不比较 key 原文；响应不含 key 原文或指纹 |
| T11 | 凭据不回传 | integration | 在模型 key、搜索 key、MCP `env` 和 `headers` 中放入测试值，并让 MCP 失败信息包含这些值；所有设置读取和写入接口的完整响应文本中都找不到这些值 |

## 4.3 集成边界

- 全局层路由与 `InstanceStore` 的通知：用真实 daemon 加载两个以上实例验证，不能只用 mock backend。
- 运行时重建与 MCP 重连：用本地假 MCP 服务器（stdio 脚本）计数连接次数，判断是否重连。
- `model.json` 写入：用真实文件系统和临时目录，检查文件内容，不只检查返回值。

## 4.4 回归范围

- TUI：`/connect`、`/models`、`/mcps`、`/skills`、`/status` 的现有测试。
- 模型切换：现有 `connectModel`、上下文窗口探测、回滚与“配置不一致”的测试。
- improve-1 的工作区测试，确认全局路由挂载顺序没有影响 `/v1/sessions` 等接口。
- `pnpm typecheck`、`pnpm lint` 通过。

## 4.6 重点检查

| 风险 | 检查方式 |
|---|---|
| 保存模型时丢掉条目或新字段 | T15、T17：经过 `/connect` 等旧入口保存后，其它条目、`apiKeyEnv` 和 `activeProfileId` 仍在 |
| 官方模型被不必要地付费探测 | T18：命中内置规则或仅保存候选时，假上游收不到探测请求 |
| 凭据泄露 | T11 检查完整响应文本，新增字段也要经过同一脱敏函数 |
| 改模型导致 MCP 无谓重连 | T12 计数 MCP 连接次数 |
| 运行中修改打断当前轮 | T12 检查当前轮正常完成 |
| 写入覆盖手改的其它条目 | T1、T9：文件中其它字段和条目原样保留 |
