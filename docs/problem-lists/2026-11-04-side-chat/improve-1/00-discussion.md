# 讨论记录与已确认要点

> 2026-11-04 与用户讨论定稿，2026-11-08 按轮次投影落地后的代码和逐项讨论修订（见第 6 节）。第 2 至 4 节是讨论中确认的结论；第 5 节是写规划时根据代码勘测补充的决定，随整套文档提交用户审查。推理过程见 [01](01-problem-analysis-and-current-state.md)，实施方案见 [02](02-optimization-plan-and-change-scope.md)。

## 1. 背景与动机

主会话在跑一个长任务，或者用户读到回答里某一段想追问，又不想把主对话的上下文弄乱。现在只能新开一个会话从头解释，或者在主会话里插话。用户想要一个“旁边的小窗口”：看得到主对话在说什么，问完就扔。

## 2. 已确认：目标与范围

| 决策项 | 结论 |
|---|---|
| 做法 | 对照 codex 的 `/side`、`/btw`：打开一个会话，它继承主对话的历史 |
| 上下文 | 模型看得到主对话；界面上不显示继承来的内容，只显示 side chat 自己的对话 |
| 打开方式 | Web：主界面顶栏菜单里的“Side chat”（快捷键暂定 `⌘;`）、右侧面板入口页、side chat 标签排里的 +，或选中消息里的文字后点“Ask in side chat”。TUI：`/btw` 命令，`/btw <问题>` 直接把问题作为第一条消息。主会话还没有消息时两端都不能打开（P17） |
| 端 | TUI 只做 `/btw` 命令；Web 做界面，以后的 App 端同样做界面 |
| 工具 | 全部可用，审批跟主会话的档位走。边界消息里写“默认只读，用户要求才改”；不能调用子代理（P3、P7） |
| 禁用 | fork、撤销重发、手动压缩、goal、切换模型与 reasoning、改名、归档、移动工作区、导出、嵌套 side chat、创建子代理（P7） |
| 关闭后 | 不保留。关闭即删除，不弹确认；没有历史 side chat 的入口，也没有历史记录。daemon 重启后看不到之前的 side chat（2026-11-08 用户确认） |
| 数量 | 一个主会话可以同时开多个 side chat，每次打开都新建一个（2026-11-08 用户改定，原为“一个主会话一个”，对照 codex app、Claude app） |
| 主会话在运行时 | 可以打开，主会话不会被打断。继承的历史截到主会话最近一个已结束的主 run 的末尾；正在运行的那一轮不复制，只在边界消息里说明主会话正在做什么（见 P14） |
| 选中文字的弹窗 | 只有“在 side chat 里问”一项 |
| 结果带回主会话 | 不做，需要时手动复制 |

## 3. 已确认：边界

| 项 | 处理 |
|---|---|
| 选中文字后“引用到主输入框” | 不做 |
| 把 side chat 的结论自动带回主会话 | 不做 |
| side chat 出现在侧栏、搜索、会话列表、导出里 | 不允许，它对用户来说是临时的 |
| Web 的 `/btw` 斜杠命令 | 不做，Web 用界面入口 |

## 5. 规划中补充的决定

勘测和三轮文档审查后定下的细节，理由见 01 和 02。最初设想把 side chat 做成主会话的子会话（`parent_id` 指向主会话），审查发现读取、回执、steer、中止、提交都会被“只认根会话”的检查拦住，提交还会把客户端的绑定切走，要改十几处，已放弃。

| 编号 | 决定 | 一句话理由 |
|---|---|---|
| P1 | side chat 是一个**隐藏的根会话**：`parent_id` 为空、`isSubagent` 为 `false`，`session.data.sideChat = { mainSessionId, boundaryMessageId, ownerPid }`。有没有 `sideChat` 就是判断标准 | 根会话能直接用现有的读取、推送、提交、中止和审批机制，不用开口子 |
| P2 | 每次打开都新建一个 side chat，在一个事务里复制历史、写入边界消息。标题为 `Side chat N`，N 取这个主会话现有 side chat 里最小的空号 | 一个事务保证不会留下半个 side chat；编号照 ZCode 的“辅助对话 N” |
| P3 | 给模型的 side chat 说明不放进系统提示词，而是写成一条边界消息：一条普通的用户消息，接在复制来的历史后面，模型看得到，界面不显示，不带额外标记，它的 ID 记在 `data.sideChat.boundaryMessageId`。内容：现在在 side chat 里，不是主对话；前面的历史从主对话继承，只供参考；不要接着做主对话的任务，只回答新问题；默认只读，用户明确要求时才改文件、Git 和配置；不能调用子代理；主会话有正在运行的一轮时，说明它正在做什么（见 P14）（2026-11-08 用户确认） | 系统提示词排在历史前面，改一个字节，后面整段历史的缓存都会失效。codex、kimi-code、ZCode、dsh 都不改系统提示词，说明都放在继承历史之后。提醒类消息只能在运行时写，用不上；普通用户消息打开时就能写 |
| P4 | Web 的 side chat 面板另开一个 daemon 客户端，绑定到 side chat。查看、提交、中止、审批都走现有接口，面板只显示边界消息之后的内容 | 服务端本来就按客户端分别记绑定 |
| P5 | 后端在提交目标是 side chat 时，不改动后端共用的“当前会话” | TUI 默认在进程内运行，后端的当前会话就是 TUI 的绑定；不这样做，往 side chat 提问会把 TUI 拉过去 |
| P6 | 从用户能看到的列表里隐藏 side chat：新加判断函数 `isUserFacingSession`，用在全局列表、搜索、TUI 会话列表、“继续上次会话”、空会话复用、归档后的替补会话、Web 备用侧栏。不改 `isPrimarySession`，也不过滤会话快照 | `isPrimarySession` 和会话快照决定 side chat 自己能不能被绑定、能不能拿到消息 |
| P7 | 对 side chat 会话拒绝这些操作，统一返回新错误码 `SIDE_CHAT_UNSUPPORTED`（409）：fork、撤销、手动压缩、goal、切换模型与 reasoning、归档、移动工作区、导出、在 side chat 里再开 side chat。创建子代理在工具执行时拒绝，工具列表不变。side chat 面板不提供斜杠命令和改名，输入原样作为问题发出。保留发消息、停止、审批（显示在 side chat 面板里）、运行中插话。上下文管理、缓存前缀匹配、自动压缩都和主会话走同一套机制，不做特殊处理；只拦手动压缩入口，不拦自动压缩（2026-11-08 用户确认） | 根会话默认这些都能做，必须显式拦住；一个错误码就够。换模型会让和主会话共用的缓存失效，codex 也禁用 `/model`。自动压缩被拦，长对话会顶到上下文上限 |
| P8 | 关闭时：取消排队的 prompt，中止正在运行的一轮，等它结束（最多 5 秒，超时返回 `SESSION_RUNNING`），再删除全部数据和内存状态。界面上直接关闭，不弹确认。重复关闭直接返回成功 | 用户已确认“关闭不保留”；现有代码没有“中止并等待”的函数，要写清楚 |
| P9 | daemon 启动、进程内 TUI 启动时，删除 `ownerPid` 对应进程已经不在的 side chat，跳过忙碌检查 | 崩溃留下的 run 记录可能还标着“运行中”；同一个数据库可能同时被 TUI 进程使用，不能误删别的进程正在用的 side chat |
| P10 | 审批：Web 显示在各自 side chat 的面板里（它自己客户端的审批面板），主会话的审批照常在主界面；多开时，没在看的 side chat 在等审批，就在它的标签上加一个简洁的“等待审批”标记，不加别的提示。TUI 面板打开期间同时订阅主会话和 side chat 的审批：side chat 的在面板里处理；主会话有待处理的审批时，面板标题栏提示主会话需要审批，按 Esc 回到主会话后照常弹出（2026-11-08 用户确认）。打开时把主会话当时的“总是允许”规则复制给 side chat，之后各管各的：side chat 新加的规则不带回主会话，关闭时清掉。side chat 正在等审批时被关闭（用户关闭或主会话归档），这个审批跟着取消（2026-11-08 用户确认，取代原来“不带给 side chat”） | 审批跟主会话走（第 2 个问题），“总是允许”也跟着走才一致，用户不用把主会话已允许的命令再点一遍；审批按根会话路由；TUI 现有的审批同步只认当前会话，只同步 side chat 的话，主会话卡在审批上用户也不知道；codex 在 side chat 里显示“main needs approval”提示 |
| P11 | 提示词缓存沿用主会话的做法，不另写缓存逻辑，Anthropic、OpenAI Responses、OpenAI 兼容三种接口都要命中。side chat 和主会话用同一份系统提示词；模型请求用主会话的 ID 计算缓存身份（目前只有 OpenAI 兼容接口在官方端点上发 `prompt_cache_key`，Anthropic 和 Responses 按前缀匹配）；打开时带上主会话已加载的 MCP 工具，工具定义与主会话一致（2026-11-08 用户确认，取代原来“可能命中不了，本轮接受”的决定。2026-11-10 改定：由[已加载 MCP 工具从历史重建议题](../../2026-11-09-mcp-loaded-tools-from-history/README.md)保证，side chat 从复制来的历史重建，不再写 `copyScope`） | codex 用父会话的 ID 作缓存 key（`fork_cache_key`），kimi-code 同一会话共用一个 key、工具定义一个不删，两者都有测试守住。缓存 key 按会话 ID 算、MCP 工具按会话加载，不处理的话 side chat 的第一次请求就对不上主会话的前缀 |
| P12 | Web：右侧面板里一个 side chat 一个标签（`Side chat N`，带 ×），和终端标签同排；新建入口是顶栏菜单（快捷键暂定 `⌘;`，实施时确认不冲突）、右侧面板入口页、标签排里的 +；选中文字后出现“Ask in side chat”按钮。细节见表下（2026-11-08 用户确认） | 右侧面板本来就是标签页结构，终端已经是一个终端一个标签；Claude App、Codex App 都是右侧标签加 + 和快捷键 |
| P13 | TUI：`/btw` 打开一个面板，替换主视图，下方复用现有输入框，关闭命令面板，标题栏写“Side chat · Esc to close”；`/btw <问题>` 打开后立即提交；主会话正在运行时也能打开；一次只开一个；输入框为空时按 Esc 关闭并删除。主会话还没有消息时不能打开（P17）。连接远程 daemon 时 `/btw` 不可用（2026-11-08 用户确认） | 学 codex TUI；子代理浏览器只能看不能输入；终端里没有标签页，多开反而难用；远程模式下按会话提交会切走客户端的绑定 |
| P14 | 历史切点与快照：复制到主会话最近一个已结束的主 run 的末尾。“已结束”沿用 SDK `listEndedTurns`（`packages/ohbaby-sdk/src/util/turn.ts`）的规则：run 的结局是成功、失败、取消或中断；有 prompt 的，prompt 也已结束；没有 prompt 的 run 要写过自己的消息才算。正在运行的那一轮不复制，边界消息里按触发来源写一句：用户触发的附上那条用户输入原文，goal 续跑写“主对话正在继续 goal”并附 goal 内容，子代理唤醒写“主对话正在处理子代理交回的结果”。打开后是快照，不随主会话更新；想看主会话的新进展，关掉重开（2026-11-08 用户确认） | 轮次投影落地后，界面上的一轮等于一个 run，子代理唤醒和 goal 续跑的 run 没有 prompt，按 prompt 切会漏掉它们。不复制半截的一轮，就不用像 codex、kimi-code 那样补“中止”或“结果未知”的标记。codex、kimi-code、ZCode、dsh 都是快照 |
| P15 | 主会话被归档时，关闭它的全部 side chat（中止、删除），不等下次启动清理 | 否则 daemon 长时间不重启时残留会一直留着；codex、ZCode 都在归档父会话时清掉 side chat（2026-11-08 用户确认） |
| P16 | 刷新页面、断网重连不关闭 side chat。页面加载时，列出这个主会话当前还开着、由本进程创建的 side chat，逐个接回它们自己的客户端。列出的只是还开着的，关掉的已删除，查不到。只有用户关闭、主会话归档（P15）、daemon 重启时的清理（P9）会让 side chat 消失。App 端退出时是否主动关闭，做 App 时再定 | ZCode 断网时沿用重连界面、不作废 side chat，Claude Code VS Code 扩展重载窗口后 side chat 还在；没有参考项目在客户端断开时删除。刷新就删不适合以后的 App 端（2026-11-08 用户确认） |
| P17 | 主会话还没开始过时（没有主 run，也没有已接收的 prompt），不能打开 side chat：后端返回 `SIDE_CHAT_UNSUPPORTED`，说明为 “Send a message first”；Web 的入口置灰，悬停显示同一句；TUI 提示 “/btw is unavailable until this conversation has started. Send a message first, then try /btw again.”。主会话开始过就能开，第一轮还在跑也可以，这时 side chat 只有边界消息（2026-11-08 用户确认） | 照 codex TUI 的 `/side`；前端已经置灰，后端检查只是兜底，复用现有错误码，不另加名字 |
| P18 | 开发顺序为 side chat → fork → 撤销重发。复制历史的函数由本议题写，起中性的名字 `copySessionHistory`（`A/services/session/copy-history.ts`），做法从 fork 议题 02 搬来并改为按 run 定切点；复制范围、ID 改写、压缩标记处理照 fork 的设计。本议题新建 `SIDE_CHAT_UNSUPPORTED` 和 `ConversationStream` 的 `side-chat` 开关；fork、撤销以后挂按钮时遵守这个开关，并在各自入口拒绝 side chat 会话；撤销在复制函数里加“跳过已撤销内容”的条件。fork、撤销的文档到讨论它们时再改（2026-11-08 用户确认） | 复制函数是两个议题共用的，谁先做谁是主人；实施 side chat 的人只看本议题的文档就够，不用去翻按 prompt 切点、已经过时的 fork 文档 |

P12 细节：

- 每个 side chat 一个标签，标签名旁边在等审批时显示一个小圆点，悬停显示 “Waiting for approval”。
- 空状态只有一行 “No messages yet”，下面一行小字 “Sees this chat up to now. The main chat won't see it.”。
- 输入框占位文字 “Ask a quick question”，只有发送和停止，不放模型、权限、goal 控件，不开斜杠命令；消息只有复制按钮。
- 选中主会话消息里的文字后出现 “Ask in side chat”：正在看某个 side chat，就把文字按 Markdown 引用（每行前加 `> `，后面空一行）填进它的输入框；否则新建一个再填进去；不自动发送。
- 切换主会话时，旧主会话的 side chat 标签收起，不删除，它们的客户端也保留，审批照常到达；切回来时直接显示。
- 每个 side chat 的 × 直接关闭并删除，不弹确认。

## 6. 用户确认记录

- 2026-11-04：用户确认 side chat “选中文字或者输入 /btw 打开一个子会话，模型看得到主对话，界面上不显示。工具全部可用，但不能 fork 和编辑（对照 codex 实现）”，“TUI 做 /btw 命令即可，Web 端、App 端 UI 即可”，并确认全景讨论中的建议（关闭即删、一个主会话一个、主会话运行时可开、软提醒、禁用清单、选中文字只做 side chat、不带回主会话）全部按建议执行。
- 2026-11-04：用户要求设计遵循 KISS，不过度设计。
- 2026-11-08：用户确认第 1 个问题：缓存沿用主会话的做法，不重新实现，兼容 Anthropic、OpenAI Responses、OpenAI 兼容三种接口；不在系统提示词里加 side chat 说明，说明写成一条普通用户消息，接在复制来的历史后面，模型看得到，界面不显示。P3、P11 据此修订。
- 2026-11-08：用户确认第 2 个问题：side chat 的提示词（即 P3 的边界消息，一条接在末尾的用户消息）里写“默认只读，用户要求才改”；审批跟主会话的档位走，不为 side chat 单独强制审批；side chat 不能调用子代理，执行时拒绝，工具定义保留（P7）。已知代价：主会话开着 `full-access` 时，side chat 改文件只靠这句提示约束。
- 2026-11-08：用户确认第 3 个问题：切在主会话最近一个已结束的主 run 的末尾；side chat 只看到打开那一刻的主对话，是快照，不随主会话实时更新，想看最新的就关掉重开。新增 P14。
- 2026-11-08：用户确认第 4 个问题，原则是“side chat 只是临时的，不要紧，可以多开”（对照 codex app、Claude app）：一个主会话可以开多个 side chat；关闭就没了，没有历史入口和历史记录；关闭时直接关，不弹确认；主会话归档时顺手关掉它的 side chat（中止、删除）；daemon 启动时删掉创建进程已经不在的 side chat，重启 daemon 后看不到之前的 side chat。P2、P8、P12 据此修订，新增 P15。
- 2026-11-08：用户否决“客户端断开超过 5 秒就删除 side chat”的提议：浏览器刷新不应关闭 side chat，后面还要做 App 端。确认刷新、重连后恢复当前主会话还开着的 side chat。新增 P16。
