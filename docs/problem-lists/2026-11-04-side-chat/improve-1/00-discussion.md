# 讨论记录与已确认要点

> 2026-11-04 与用户讨论定稿。第 2 至 4 节是讨论中确认的结论；第 5 节是写规划时根据代码勘测补充的决定，随整套文档提交用户审查。推理过程见 [01](01-problem-analysis-and-current-state.md)，实施方案见 [02](02-optimization-plan-and-change-scope.md)。

## 1. 背景与动机

主会话在跑一个长任务，或者用户读到回答里某一段想追问，又不想把主对话的上下文弄乱。现在只能新开一个会话从头解释，或者在主会话里插话。用户想要一个“旁边的小窗口”：看得到主对话在说什么，问完就扔。

## 2. 已确认：目标与范围

| 决策项 | 结论 |
|---|---|
| 做法 | 对照 codex 的 `/side`、`/btw`：打开一个会话，它继承主对话的历史 |
| 上下文 | 模型看得到主对话；界面上不显示继承来的内容，只显示 side chat 自己的对话 |
| 打开方式 | Web：选中消息里的文字后点“在 side chat 里问”，或从右侧面板打开。TUI：`/btw` 命令，`/btw <问题>` 直接把问题作为第一条消息 |
| 端 | TUI 只做 `/btw` 命令；Web 做界面，以后的 App 端同样做界面 |
| 工具 | 全部可用，正常走权限审批。加一句软提醒：用户没要求就不要改文件 |
| 禁用 | fork、撤销重发、压缩、goal、切换模型、改名、归档、创建子代理 |
| 关闭后 | 不保留。关闭即删除；daemon 启动时清理上次没关掉的 |
| 数量 | 一个主会话同时只有一个 side chat，再次打开回到原来那个 |
| 主会话在运行时 | 可以打开，主会话不会被打断。继承的历史截到最近一轮已结束的对话；正在运行的那一轮，只把用户的输入告诉 side chat |
| 选中文字的弹窗 | 只有“在 side chat 里问”一项 |
| 结果带回主会话 | 不做，需要时手动复制 |

## 3. 已确认：边界

| 项 | 处理 |
|---|---|
| 一个主会话开多个 side chat | 不做 |
| 选中文字后“引用到主输入框” | 不做 |
| 把 side chat 的结论自动带回主会话 | 不做 |
| side chat 出现在侧栏、搜索、会话列表、导出里 | 不允许，它对用户来说是临时的 |
| Web 的 `/btw` 斜杠命令 | 不做，Web 用界面入口 |

## 5. 规划中补充的决定

勘测和三轮文档审查后定下的细节，理由见 01 和 02。最初设想把 side chat 做成主会话的子会话（`parent_id` 指向主会话），审查发现读取、回执、steer、中止、提交都会被“只认根会话”的检查拦住，提交还会把客户端的绑定切走，要改十几处，已放弃。

| 编号 | 决定 | 一句话理由 |
|---|---|---|
| P1 | side chat 是一个**隐藏的根会话**：`parent_id` 为空、`isSubagent` 为 `false`，`session.data.sideChat = { mainSessionId, boundaryMessageId, ownerPid }`。有没有 `sideChat` 就是判断标准 | 根会话能直接用现有的读取、推送、提交、中止和审批机制，不用开口子 |
| P2 | 打开时在一个事务里完成：查这个主会话有没有 side chat（有就返回）、调用 fork 议题的 `forkSessionRows` 复制历史、写入边界消息 | 一个事务保证并发打开也只有一个 |
| P3 | 边界消息是一条普通的用户消息，不带额外标记，它的 ID 记在 `data.sideChat.boundaryMessageId`。内容合并 codex 的两段提示；主会话有正在运行的一轮时，附上那一轮的用户输入原文。不改系统提示词 | 提醒类消息只能在运行时写，用不上；普通用户消息打开时就能写，模型也看得到 |
| P4 | Web 的 side chat 面板另开一个 daemon 客户端，绑定到 side chat。查看、提交、中止、审批都走现有接口，面板只显示边界消息之后的内容 | 服务端本来就按客户端分别记绑定 |
| P5 | 后端在提交目标是 side chat 时，不改动后端共用的“当前会话” | TUI 默认在进程内运行，后端的当前会话就是 TUI 的绑定；不这样做，往 side chat 提问会把 TUI 拉过去 |
| P6 | 从用户能看到的列表里隐藏 side chat：新加判断函数 `isUserFacingSession`，用在全局列表、搜索、TUI 会话列表、“继续上次会话”、空会话复用、归档后的替补会话、Web 备用侧栏。不改 `isPrimarySession`，也不过滤会话快照 | `isPrimarySession` 和会话快照决定 side chat 自己能不能被绑定、能不能拿到消息 |
| P7 | 对 side chat 会话拒绝这些操作，统一返回新错误码 `SIDE_CHAT_UNSUPPORTED`（409）：fork、撤销、压缩、goal、切换模型与 reasoning、归档、移动工作区、导出。创建子代理在工具执行时拒绝，工具列表不变。side chat 面板不提供斜杠命令和改名 | 根会话默认这些都能做，必须显式拦住；一个错误码就够 |
| P8 | 关闭时：取消排队的 prompt，中止正在运行的一轮，等它结束（最多 5 秒，超时返回 `SESSION_RUNNING`），再删除全部数据和内存状态。重复关闭直接返回成功 | 用户已确认“关闭不保留”；现有代码没有“中止并等待”的函数，要写清楚 |
| P9 | daemon 启动时，删除 `ownerPid` 对应进程已经不在的 side chat，跳过忙碌检查 | 崩溃留下的 run 记录可能还标着“运行中”；同一个数据库可能同时被 TUI 进程使用，不能误删别的进程正在用的 side chat |
| P10 | 审批：Web 显示在 side chat 面板里（它自己客户端的审批面板）；TUI 在面板打开期间按 side chat 的 ID 同步审批。主会话里的“总是允许”不带给 side chat | 审批按根会话路由；TUI 现有的审批同步只认当前会话 |
| P11 | 提示词缓存：系统提示词与主会话一致；OpenAI 兼容接口的缓存 key 和已加载的 MCP 工具按会话区分，可能命中不了。本轮接受 | 为一个临时会话，把缓存用的会话标识一路传过四层代码，不划算 |
| P12 | Web：右侧面板加“Side chat”页；选中文字后出现“Ask in side chat”按钮。细节见表下 | 右侧面板的页注册表已经给 side chat 留了位置 |
| P13 | TUI：`/btw` 打开一个面板，下方复用现有输入框，关闭命令面板；`/btw <问题>` 打开后立即提交；输入框为空时按 Esc 关闭并删除。连接远程 daemon 时 `/btw` 不可用 | 子代理浏览器只能看不能输入；远程模式下按会话提交会切走客户端的绑定 |

P12 细节：Side chat 页随主会话切换而重置，切回来再打开，回到原来的 side chat。点“Ask in side chat”会打开这个页，并把选中的文字以 Markdown 引用的形式填进 side chat 的输入框。面板右上角有关闭按钮，确认后删除。
