# 讨论记录与已确认要点

> 2026-11-04 与用户讨论定稿，2026-11-09 逐条重新讨论后更新（R1 至 R7，见第 6 节）。第 2 至 4 节是讨论中确认的结论；第 5 节是写规划时根据代码勘测补充的决定，随整套文档提交用户审查。推理过程见 [01](01-problem-analysis-and-current-state.md)，实施方案见 [02](02-optimization-plan-and-change-scope.md)。

## 1. 背景与动机

消息发出去以后就改不了。用户发现问错了、漏了条件，只能再发一条补充，错误的那一轮还留在上下文里。现有的“resend”和“edit”只针对还在排队、或者还没被处理的输入，对已经跑完的对话不起作用。

用户把这项功能叫“编辑重发”。2026-11-09 重新讨论后定为：Web 学 ZCode，在消息气泡里直接改，点 Send 时撤销和发送一次做完；TUI 学 kimi-code 和 codex，先撤销，再把原文填回输入框，由用户改完自己发。下文统一叫“撤销重发”。

## 2. 已确认：目标与范围

| 决策项 | 结论 |
|---|---|
| 做法 | Web：点 Edit 后这条用户消息的气泡变成编辑框，下面是 Cancel 和 Send，点 Send 时后端一次完成“撤销这条及之后的对话 + 发出改过的文字”。TUI：撤销后把原文填回主输入框，用户改完自己发送（2026-11-09 改定） |
| 旧消息 | 留在数据库里，作为废弃分支，从模型上下文和界面上隐藏，不删除 |
| 文件 | 本轮不回滚，界面上明确告诉用户“文件改动不会撤销”。“连 AI 的文件改动一起撤销”另立议题，接口先预留位置（2026-11-09） |
| 压缩边界 | 最近一次压缩之前的消息不能撤销，因为它们已经合进摘要里了 |
| 撤销点 | 只有正常提交的 prompt 算撤销点。运行中插进去的 steer 不算 |
| 会话在运行 | 学 ZCode：运行中也能编辑，包括正在跑的这一轮。点 Send 时后端先停下来（取消排队的消息、暂停 goal、中断当前这一轮并等空闲），再撤销。只有正在压缩等少数情况才拒绝（2026-11-09 改定，原为“运行中拒绝”） |
| 后台子代理与任务 | 学 ZCode：撤销前先停掉被撤销那几轮里启动的后台子代理和后台 shell 任务，停不掉就不撤销；它们没送达的结果不再投递，子代理调用从列表里隐藏（2026-11-09 补充） |
| 输入框有草稿 | Web 不碰主输入框，不存在这个问题。TUI 先确认，再用原文替换草稿 |
| 端 | Web 在用户消息卡片下方、悬停时出现的操作栏里放 Edit 按钮（铅笔图标，紧挨复制按钮）；TUI 新增 `/rewind`（不设别名），打开列表选择撤销到哪一轮；任意一条用户消息都能选（2026-11-09 确认） |
| 名字 | 对外和内部统一叫 rewind：TUI `/rewind`、接口 `POST /v1/sessions/:id/rewind`、错误码 `REWIND_*`、列 `rewound_at`；Web 按钮文字叫 Edit；议题名“撤销重发”不改（2026-11-09） |

## 3. 已确认：边界

| 项 | 处理 |
|---|---|
| 文件回滚 | 本轮不做，另立议题（见第 2 节“文件”行） |
| 浏览或恢复已撤销的分支、重做 | 不做。用户想保留旧版本，先 fork 一份再撤销 |
| 编辑框里换模型、reasoning 或加附件 | 不做。只改文字，模型和 reasoning 沿用原来那一轮的；ohbaby 目前也没有附件 |
| goal 的已用轮数与 token | 不回退，界面上说明 |
| TUI 双击 Esc 进入撤销 | 以后再做 |

## 5. 规划中补充的决定

勘测和文档审查时发现、讨论阶段没有覆盖到的细节，理由见 01 和 02。原则是复用现有机制，不新造。

| 编号 | 决定 | 一句话理由 |
|---|---|---|
| P1 | `message` 和 `prompt_submission` 各加一列 `rewound_at`（迁移 `029`；P9 另给 `subagent_execution` 加同名列）。为空表示可见，有值表示已撤销。不另建索引 | 读消息的地方有二十多处，用一个列在存储层统一过滤最简单；现有索引够用 |
| P2 | 消息存储的三个列表入口（`listPage`、`listByIds`、`listBySession`）和 prompt 存储的列表入口（`listForSession`、`listVisible`）默认排除已撤销的行；会话搜索的 SQL 单独加条件。按单个 ID 读取的入口**不过滤** | 列表入口覆盖绝大多数读取方；按 ID 读取服务于 steer 流程和“空会话”判断，过滤反而会弄坏它们 |
| P3 | 撤销接口以“目标 prompt”定位：`POST /v1/sessions/:sessionId/rewind`，请求体 `{ promptId, text? }`，撤销这条及之后的全部内容。带 `text`（Web）时撤销后立即接收这段文字作为新 prompt；不带（TUI）时只撤销，返回原文 | 用户点的是某一条消息；按条数撤销在并发提交时会撤错位置。一个接口两种用法，不另开“编辑重发”接口 |
| P4 | 撤销范围有两部分：一是主上下文里从目标用户消息开始的全部消息，排序与模型历史相同（`listBySession` 的 `created_at, rowid`）；二是本会话里不早于目标 prompt 的全部 prompt | 规则简单，不会漏掉夹在两轮之间的 steer、提醒和通知；切分位置和模型历史一致 |
| P5 | 撤销在 adapter 层执行。会话在运行时先停下来：取消排队的 prompt、暂停 `active` 的 goal、中断当前这一轮，等到空闲（最多 10 秒）。再照手动压缩的做法，在 `runControl(sessionId)` 里检查忙碌并占住会话执行闸门；仍忙就等闸门放开再来一圈，10 秒内没占到才返回 `SESSION_RUNNING`。暂停 goal 时保留它的后台子代理，留给 P9 按轮次处理。停止之前先做不依赖运行状态的校验（含目标有用户消息、在压缩点之后、没在压缩、排队没被别的窗口锁住），校验不过就什么都不停（2026-11-09 改定，审查后细化） | 忙碌状态只存在于 adapter 的内存里；占住闸门后，prompt 准入、goal 续跑、子代理唤醒都会被挡住，不需要另造锁 |
| P6 | 撤销后用现有的 `syncSessionStatsBestEffort` 重算会话统计。“空会话复用”和“首条消息起标题”沿用现有判断，不改代码 | 现有判断已能正确处理“撤销到底”的会话，04 用测试确认 |
| P7 | 隐藏消息通过消息管理器的提交流程发出 `Removed` 变化，由视图投影转成 `session.changed` 的 `removedMessageIds`，不手写事件。被撤销的 prompt 更新 `updatedAt` 并带上 `rewoundAt`；视图里不再包含被撤销 prompt 的 run。prompt 存储的标记绕过调度器的通知，所以撤销后要对每条被标记的 prompt 补发一次 `prompt.updated`（2026-11-09 审查补充） | 视图投影有自己的消息缓存，绕过提交流程直接改库，`GET /view` 会继续返回旧消息 |
| P8 | 错误码和状态码复用现有的 `SESSION_NOT_FOUND`（404）、`SESSION_RUNNING`、`SESSION_NOT_ROOT`、`SESSION_ARCHIVED`（409），只新增 `REWIND_TARGET_INVALID`、`REWIND_BEFORE_COMPACTION`（400） | 不为同一种情况造两个名字 |
| P9 | 按被撤销消息和 prompt 上的 runId 找出被撤销的轮次，对每轮先停子代理（`interruptByRootRun`）和后台 shell 任务（`cancelByRootRun`），停止失败就不撤销；再把 `root_run_id` 属于这些轮次的子代理调用写上 `rewound_at`（`subagent_execution` 加列），未送达的结果改为不投递。子代理调用列表排除被撤销的调用，调用全部被撤销的子代理不显示；执行存储的通用列表不过滤，停止和唤醒还要用 | 子代理的结果会唤醒父会话或插进下一轮，只停止挡不住已在等待的结果。原方案用的 `root_prompt_id` 从没写过值，`root_run_id` 每次都写且有索引。先停后撤学 ZCode（2026-11-09 改定） |
| P10 | Web 前端不判断压缩边界，压缩点之前的消息照常显示 Edit，点了由后端返回 `REWIND_BEFORE_COMPACTION` 并提示 | 前端拿不到可靠的边界；再算一遍容易和后端不一致 |
| P11 | 不做重复请求的特殊处理。目标已经被撤销时返回 `REWIND_TARGET_INVALID`，前端照常提示 | 撤销是用户手动触发的低频操作，为网络重试单独设计一条成功路径不划算 |
| P12 | 带 `text` 时，新 prompt 在占着闸门期间接收进来，放开闸门后才开始执行；模型和 reasoning 取目标 prompt 上记录的值。撤销成功但接收失败时保留撤销，返回 200 并带 `sendError`，前端把改过的文字放进主输入框：输入框为空直接填入，有草稿就接在草稿后面，不覆盖。预检先确认模型可选，让这种情况几乎不发生 | 接收 prompt 本来就不看闸门，执行队列会跳过闸门被占的会话，所以不需要新锁。照 ZCode：撤销可以留下，用户改过的文字不能丢（2026-11-09） |
| P13 | 撤销点之后的 goal 续跑、子代理唤醒、提醒不按来源单独处理（目标之后有压缩摘要时目标本身就不能撤销，见 P10 与 02 Stage 1 第 6.2 步），随 P4 一起隐藏；它们没有 prompt 记录，不能当撤销点。消息存储的 `listPageByRun` 也加过滤；TUI 删掉被撤销轮次的完成提示 | 有撤销功能的参考项目都是从撤销点往后一刀切、只让用户自己发的消息当撤销点；`listPageByRun` 是视图初始化取最近一轮的入口，漏掉会让被撤销的轮次重新出现（2026-11-09） |

## 6. 用户确认记录

- 2026-11-04：用户确认撤销重发“学习 kimi-code（撤销最近 N 轮，再把原文填回输入框；旧消息留作废弃分支，文件不回滚），codex app 也是这样”，并确认全景讨论中的建议（压缩边界、撤销点、忙时拒绝、停止子代理、草稿确认、TUI `/rewind`）全部按建议执行。
- 2026-11-04：用户要求复制与撤销重发分成两个议题；确认 TUI 保留 `/rewind`；要求设计遵循 KISS，不过度设计。
- 第 5 节 P1 至 P11 随整套文档提交用户审查。
- 2026-11-09：开发顺序为 side chat → fork → 撤销，逐条重新讨论，每个问题先对比 code-cli/ 下的项目。
  - R1（名字与入口）：对比结果：claude-code `/rewind`、Esc Esc；codex Esc Esc（“edit previous message”）；kimi-code `/undo`、Esc Esc；opencode Web “Rewind to here”、TUI `/undo`；ZCode Web 铅笔 “Edit”、只能改最新一条；dsh 没有。用户确认：TUI 用 `/rewind`；Web 在用户消息卡片下、悬停时出现；可以选任意一条。内部名字随之统一为 rewind（接口、错误码、列名），Esc Esc 仍以后再做。
  - R7：撤销最后落地，side chat 的 `SIDE_CHAT_UNSUPPORTED` 检查和 fork 共用复制函数里的 `rewound_at` 条件都由本议题加。
  - R2/R3（编辑方式与草稿）：对比结果：只有 ZCode Web 在气泡里编辑，Send 一次完成“停止、撤销、发送”，编辑框只改文字、不碰主输入框；codex、claude-code、kimi-code、opencode 都是把原文填回主输入框，分两步；dsh 没有编辑功能（曾有的 Edit 按钮没接逻辑，已删除，e2e 断言没有 Edit 按钮）。codex app、Cursor 闭源，从界面看是在气泡里编辑。用户确认：Web 和以后的 app 在气泡里编辑，点 Send 一次完成撤销和发送；TUI 填回主输入框；编辑框只改文字。
  - R2/R3（文件回退）：对比结果：opencode 用独立 git 仓库给整个目录拍快照，覆盖 bash，回退不查冲突；claude-code 和 ZCode 只备份编辑工具改过的文件，让用户选“连文件一起”还是“只撤销对话”，ZCode 回退前比对哈希；codex、kimi-code 只撤销对话。ohbaby 的 `snapshot` 模块做法同 opencode，但从没开启，恢复会覆盖整个目录、不查冲突、旧快照不清理。用户确认按建议：本轮只撤销对话，文件回退另立议题，接口以后加 `files` 参数。
  - R4（非用户发起的轮次）：对比结果：claude-code、opencode、codex、kimi-code、ZCode 都是从撤销点往后全部截掉，goal 续跑、后台任务和子代理通知都不能当撤销点（各自用消息类型、来源标记或内容特征排除）；dsh 没有撤销。ohbaby 只有用户提交才有 prompt 记录，现有设计已覆盖；勘测发现 `listPageByRun` 和 TUI 完成提示两处漏洞。用户确认按建议：一刀切，补这两处（P13）。
  - R5（子代理与后台任务）：对比结果：ZCode 撤销前停掉被撤销轮次里的后台任务，停不掉就不撤销，迟到的通知按代次丢弃；codex 关掉整个运行时再重载；opencode 不停任务，撤销生效时丢掉撤销点之后的待处理输入；kimi-code 不停任务，还把被撤销的完成通知补回上下文；claude-code 不处理；dsh 没有撤销。勘测发现原方案依赖的 `root_prompt_id` 从没写过值，后台 shell 任务在轮次成功结束后还会跑但跑完不通知主会话。用户确认学 ZCode 的周全做法（P9 改定）。
  - R6（会话在运行）：对比结果：ZCode 后端先停当前这一轮、等空闲再撤销，排队的消息保留但暂停自动发送，停掉的是 goal 的一轮时暂停 goal；opencode 前端先中断、等空闲再撤销，撤销点之后待处理的输入撤销生效时丢掉；claude-code 编辑会先取消，只有任务在跑时才暂停 goal；codex、kimi-code 运行中不能撤销。勘测发现 ohbaby 的 Stop 只发中断信号、不等结束，停下后排队的 prompt 会自动开跑，goal 在两轮之间也会抢闸门。用户确认按建议：后端先停再撤，排队的 prompt 直接移除，active 的 goal 暂停，正在压缩时才拒绝（P5 改定）。
  - 自检与子代理审查（2026-11-09）：审查发现 7 个主要问题、11 个次要问题，已全部修正。主要的有：停下来后只查一次忙碌会被调度器收尾或子代理唤醒抢先，改为等闸门放开后循环重试；`pauseGoal` 会停掉 goal 名下所有轮次的后台子代理，改为加 `preserveBackground` 选项；目标校验改为查用户消息行本身，排队中或从排队取消过的 prompt 不能当目标；prompt 标记后要补发 `prompt.updated`；子代理列表只在两个界面入口过滤；发送失败时不覆盖主输入框草稿；排队里有 retained 或被别的窗口锁住编辑的 prompt 时预检拒绝。另删去没人用的 `rewoundPromptIds`，编排文件改名为 `session-rewind.ts`，校正了行号。
