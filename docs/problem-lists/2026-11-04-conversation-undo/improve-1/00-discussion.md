# 讨论记录与已确认要点

> 2026-11-04 与用户讨论定稿。第 2 至 4 节是讨论中确认的结论；第 5 节是写规划时根据代码勘测补充的决定，随整套文档提交用户审查。推理过程见 [01](01-problem-analysis-and-current-state.md)，实施方案见 [02](02-optimization-plan-and-change-scope.md)。

## 1. 背景与动机

消息发出去以后就改不了。用户发现问错了、漏了条件，只能再发一条补充，错误的那一轮还留在上下文里。现有的“resend”和“edit”只针对还在排队、或者还没被处理的输入，对已经跑完的对话不起作用。

用户把这项功能叫“编辑重发”。本议题按 kimi-code 和 codex 的做法实现：先撤销，再把原文填回输入框，由用户改完自己发。下文统一叫“撤销重发”。

## 2. 已确认：目标与范围

| 决策项 | 结论 |
|---|---|
| 做法 | 学 kimi-code 和 codex：撤销最近 N 轮，把被撤销的第一条用户消息原文填回输入框，用户改完自己发送。不自动重发 |
| 旧消息 | 留在数据库里，作为废弃分支，从模型上下文和界面上隐藏，不删除 |
| 文件 | 不回滚。界面上明确告诉用户“文件改动不会撤销” |
| 压缩边界 | 最近一次压缩之前的消息不能撤销，因为它们已经合进摘要里了 |
| 撤销点 | 只有正常提交的 prompt 算撤销点。运行中插进去的 steer 不算 |
| 会话忙 | 会话在运行时不能撤销。后端直接拒绝，Web 按钮置灰并提示先停止 |
| 后台子代理 | 被撤销的那几轮里启动的后台子代理一并停止，并从子代理列表里隐藏 |
| 输入框有草稿 | 先确认，再用原文替换草稿 |
| 端 | Web 在用户消息上放 Edit 按钮；TUI 新增 `/undo`，打开列表选择撤销到哪一轮 |

## 3. 已确认：边界

| 项 | 处理 |
|---|---|
| 文件回滚 | 本轮不做。`snapshot` 模块目前默认关闭，等它启用后再单独立议题 |
| 浏览或恢复已撤销的分支、重做 | 不做。用户想保留旧版本，先 fork 一份再撤销 |
| 编辑后自动重发 | 不做，由用户手动发送 |
| goal 的已用轮数与 token | 不回退，界面上说明 |
| TUI 双击 Esc 进入撤销 | 以后再做 |

## 5. 规划中补充的决定

勘测和文档审查时发现、讨论阶段没有覆盖到的细节，理由见 01 和 02。原则是复用现有机制，不新造。

| 编号 | 决定 | 一句话理由 |
|---|---|---|
| P1 | `message` 和 `prompt_submission` 各加一列 `undone_at`（迁移 `029`）。为空表示可见，有值表示已撤销。不另建索引 | 读消息的地方有二十多处，用一个列在存储层统一过滤最简单；现有索引够用 |
| P2 | 消息存储的三个列表入口（`listPage`、`listByIds`、`listBySession`）和 prompt 存储的列表入口（`listForSession`、`listVisible`）默认排除已撤销的行；会话搜索的 SQL 单独加条件。按单个 ID 读取的入口**不过滤** | 列表入口覆盖绝大多数读取方；按 ID 读取服务于 steer 流程和“空会话”判断，过滤反而会弄坏它们 |
| P3 | 撤销接口以“目标 prompt”定位：`POST /v1/sessions/:sessionId/undo`，请求体 `{ promptId }`，撤销这条及之后的全部内容 | 用户点的是某一条消息；按条数撤销在并发提交时会撤错位置 |
| P4 | 撤销范围有两部分：一是主上下文里从目标用户消息开始的全部消息，排序与模型历史相同（`listBySession` 的 `created_at, rowid`）；二是本会话里不早于目标 prompt 的全部 prompt | 规则简单，不会漏掉夹在两轮之间的 steer、提醒和通知；切分位置和模型历史一致 |
| P5 | 撤销在 adapter 层执行，照手动压缩的做法：在 `runControl(sessionId)` 里检查忙碌并占住会话执行闸门。“会话忙”沿用压缩的判断，再加上 goal 处于 `active` | 忙碌状态只存在于 adapter 的内存里；占住闸门后，prompt 准入、goal 续跑、子代理唤醒都会被挡住，不需要另造锁 |
| P6 | 撤销后用现有的 `syncSessionStatsBestEffort` 重算会话统计。“空会话复用”和“首条消息起标题”沿用现有判断，不改代码 | 现有判断已能正确处理“撤销到底”的会话，04 用测试确认 |
| P7 | 隐藏消息通过消息管理器的提交流程发出 `Removed` 变化，由视图投影转成 `session.changed` 的 `removedMessageIds`，不手写事件。被撤销的 prompt 更新 `updatedAt` 并带上 `undoneAt`；视图里不再包含被撤销 prompt 的 run | 视图投影有自己的消息缓存，绕过提交流程直接改库，`GET /view` 会继续返回旧消息 |
| P8 | 错误码和状态码复用现有的 `SESSION_NOT_FOUND`（404）、`SESSION_RUNNING`、`SESSION_NOT_ROOT`、`SESSION_ARCHIVED`（409），只新增 `UNDO_TARGET_INVALID`、`UNDO_BEFORE_COMPACTION`（400） | 不为同一种情况造两个名字 |
| P9 | 被撤销轮次里启动的子代理（按执行记录的 `root_prompt_id` 找）：仍在运行的停止；尚未投递给父会话的结果标记为已处理 | 子代理的结果会唤醒父会话、开启新的一轮。只停止子代理，挡不住已经在等待投递的结果；把结果标记为已处理就能挡住，不用再改唤醒查询 |
| P10 | Web 前端不判断压缩边界，压缩点之前的消息照常显示 Edit，点了由后端返回 `UNDO_BEFORE_COMPACTION` 并提示 | 前端拿不到可靠的边界；再算一遍容易和后端不一致 |
| P11 | 不做重复请求的特殊处理。目标已经被撤销时返回 `UNDO_TARGET_INVALID`，前端照常提示 | 撤销是用户手动触发的低频操作，为网络重试单独设计一条成功路径不划算 |
