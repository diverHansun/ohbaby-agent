# improve-2 前端：质量约束

## 1. 键盘与可读性

全路径可用键盘；光标、选择、失败、完成都不能只靠颜色。正常/浅色背景、低色彩和关闭动画可辨；暗淡文字仅用于辅助内容。审批未完整显示必要操作时不接受隐藏提交。终端没有 DOM/ARIA，不以 Web 自动化检查声称终端读屏器兼容。

## 2. 性能与输出

动态帧遵从 improve-1 预算；稳定无输入、无真实变化、无活动动画时不新增持续 stdout。200 行/2 万字符输入 fixture 下，输入、光标和缩放无逐字符整串重复拼接造成的明显卡顿；在同机同终端记录改前改后耗时与输出字节，有明显回归需定位后验收，暂不发明缺乏基线的毫秒指标。

不为每个字符取模型信息，不增加审批轮询；字素/显示分行可做局部缓存但不预建通用增量渲染框架。长内容只限制显示范围，数据保存遵从原协议。

## 3. 兼容性

主验收 macOS Ghostty，尺寸与退化行为见 [03 §5](03-ui-layout-and-style.md#5-尺寸与空间优先级)；记录具体版本与字体，不宣称全终端等宽一致。中文 IME、bracketed paste、组合字符、复制和 resize 必须实测。tmux/SSH 记录是否启用，不能用没测的组合宣称覆盖。Windows 保留已有入口和基础测试，不在本轮承诺同等专项适配。

## 4. 数据与授权

未发送原文不为调试写入日志；记录阶段/请求身份及长度即可。草稿不新增持久化；可见文本投影处理沿用既有终端输出安全边界，不把任意控制序列直接当终端指令。审批展示值不能扩大实际权限，不因标题/intent 猜测全项目或永久范围。

## 5. 诊断

沿用现有错误处理与测试输出，不新增遥测系统。排错优先记录操作归属、代次及结果类别，避免打印完整草稿/命令。未完成真实终端验证的项目在验收明确保留。
