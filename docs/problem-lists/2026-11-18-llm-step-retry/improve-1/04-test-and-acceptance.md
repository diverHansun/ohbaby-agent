# 4. 测试与验收标准

## 4.1 测试范围

| 类型 | 覆盖什么 | 放在哪里 |
| --- | --- | --- |
| 单元测试 | 重试资格、错误分类、模型历史投影、请求事实、子代理结果正文 | 各包现有的 `*.unit.test.ts` 旁边 |
| 集成测试 | 在 fetch 边界注入故障，核对实际 HTTP 次数、请求体、事件和消息落库 | `tests/integration/core/llm-client/`（已有 `sdk-retry.integration.test.ts`）和 `tests/integration/core/` 下的 lifecycle 用例 |
| 端到端 | 主会话、子代理、Side Chat 的后端入口各跑一次“先断后成功” | `tests/e2e/`，使用假模型服务 |
| 真实验收 | 用真实端点的响应做受控中断，核对实现前后的请求次数和结局 | 当前基线见 [01 §1.10](./01-problem-analysis-and-current-state.md#110-真实-api-请求基线)，实施后的结果写入 05 |

重点验证真实风险：会不会重复执行工具、会不会停不下来、模型会不会看到半截内容、预算会不会被重置。不追求覆盖率数字。

## 4.2 关键场景与用例

| ID | 场景 | 类型 | 验证点 | 对应 02 |
| --- | --- | --- | --- | --- |
| T1 | 流内返回 `server_error`（OpenAI 兼容、Responses）或 `overloaded_error`（Anthropic），没有输出，第二次成功 | 集成 | 实际 HTTP 请求 2 次；`retry` 帧的 `reason` 为上游错误码；结果成功 | Stage 1 |
| T2 | 流内返回已知终态错误、未知上游错误，或普通异常带未知 `code` | 单元 + 集成 | 无普通重试，保留安全诊断。上下文超长仍走强制压缩 | Stage 1 |
| T3 | Responses `response.failed` 分别带 `server_error`、`invalid_prompt`、空的 `error` | 集成 | 第一种会重试；第二种不重试，归为请求无效；第三种为收到失败事件但原因未知，不重试。前两种保留安全的 `upstreamCode` | Stage 1 |
| T4 | 三种协议的模型步骤都在没有输出时缺终止事件，第二次成功 | 集成 | 三种协议都会重试，`reason` 为 `stream_eof` | Stage 1 |
| T5 | 已输出一段正文后连接断开，预算还有剩余 | 集成 | 请求先封存为 `retryScheduled: true`，失败观测带 `retryDelayMs`。随后发 `retry` 帧，再抛出只携带等待时间的 `stepRetry`。单次 `streamResponse` 调用只发出了首次 HTTP 请求 | Stage 2 |
| T6 | 传入 `priorFailedAttempts` 为 2 和 5，并在输出后断开 | 单元 | 为 2 时，当前请求的 `attempt` 为 3，`retry.attempt` 为 3，`stepRetry.delayMs` 与帧一致。为 5 时抛 `ProviderRetryExhaustedError`，没有新的重试帧 | Stage 2 |
| T7 | 输出后发生协议校验失败、工具参数解析失败、provider 自报中止、用户取消 | 单元 | 行为与改动前一致，不带 `stepRetry` | Stage 2 |
| T8 | lifecycle 第一次输出正文后断开，第二次成功 | 集成 | 整轮成功。第一条助手消息保存正文并记为 `finish: "error"`、`retried: true`，对应请求在封存时已记录 `retryScheduled`。第二次使用新的请求 ID 和助手消息 ID，同一步骤号，尝试编号接续 | Stage 3 |
| T9 | 接 T8，检查第二次请求的请求体（等待期间没有新输入） | 集成 | 请求体排除被取代的半截正文和中断说明，保留此前已完成的工具结果 | Stage 3 |
| T10 | 第一次流出了半截工具参数（会写文件的工具）后断开，第二次给出完整的工具调用 | 集成 | 失败尝试不执行工具，第二次请求成功后才执行，合计一次。此前步骤的工具不重复执行 | Stage 3 |
| T11 | 退避等待期间用户停止，或子代理达到时限 | 集成 | 已封存的重试排期仍可查，无后续请求。结局分别为取消和超时，没有遗留的计时器 | Stage 3 |
| T12 | 交替出现“输出前失败”和“输出后断开”，一直失败 | 集成 | 纯临时故障最多 6 次实际 HTTP 请求；`terminalReason` 为 `provider_retry_exhausted` | Stage 2、3 |
| T13 | 主会话、子代理、Side Chat 各跑一次 T8 的场景 | 端到端 | 三者都自动完成；子代理不需要主代理介入 | Stage 3 |
| T15 | 子代理最终失败，分别在实例开着、已关闭和查不到时，另加一例 `timed_out` | 单元 | `failed` 且开着时，结果正文有“可以继续”的提示；已关闭、查不到实例或 `timed_out` 时没有 | Stage 4 |
| T16 | Anthropic 空响应只收到带 `stop_reason` 的 `message_delta`，缺 `message_stop`。另验已收到正文的同类 EOF | 集成 | 两种场景均识别为 `eof`。结束原因本身不计为输出，空响应走原地重试，有正文由 lifecycle 处理 | Stage 1、3 |
| T17 | 用现有摘要调用链验证同类故障在改动前后的重试资格 | 集成 | 503 和既有可重试的传输错误复用现有用例，ContextManager 最多发 2 次 HTTP 请求。原来不重试的 EOF 和已知流内临时错误各发 1 次。摘要和标题遇到输出后中断均不产生 `stepRetry` | Stage 1、2 |
| T18 | 同一步先有一次 LLM 内部重试，随后遇到上下文超长，强制压缩后连续遇到临时故障 | 集成 | 压缩严格一次，压缩后只剩 4 次临时故障重试。统计 7 次实际步骤请求，不计摘要请求。整个步骤的重试帧编号是 1 到 5，最后的结局是 `provider_retry_exhausted` | Stage 2、3 |
| T19 | 临时故障耗尽预算，最后一次分别为正文后断流、无正文 EOF | 集成 | 两种结局都是 `provider_retry_exhausted`，此前被替换的消息排除出模型历史。有正文的最后一次按既有中断投影保留正文和说明。无正文的最后一次不添加单独的中断说明 | Stage 3 |
| T20 | 真实本地 HTTP 连接在正文后被销毁；OpenAI 兼容流另测已有原生推理且干净 EOF | 集成 | 识别嵌套的 `UND_ERR_SOCKET` 为临时网络断流。兼容接口的原生推理流按 EOF 分类。沿用安全诊断字段 | Stage 1、2 |
| T21 | 有一条已随首次请求发送的待处理输入，首次请求中途失败，重试成功 | 集成 | 失败后输入仍待处理，重发请求带入一次，成功后只确认一次 | Stage 3 |
| T22 | 接 T8，按顺序记录推送给 UI 的事件 | 集成 | 被取代消息的请求记录带 `retryScheduled: true`，而且早于这条消息的失败状态到达；它的最后一次 `agent-step` 请求挂在这条消息上 | Stage 2、3 |
| T23 | SDK 投影：被取代的消息后面出现新尝试；另测不同步骤、没有 `retryScheduled` 的失败 | 单元 | 只有同一步且带 `retryScheduled` 时等待链跨消息，阶段为 `retrying`，计时起点不变。被取代的尝试只在后面有新助手消息时列出 | §2.5 前端呈现 |
| T24 | Web：退避、新尝试开始、新尝试出正文三个时刻；另测本轮折叠 | 单元 | 退避时半截正文仍在，等待行为 `Retrying #1`。新尝试开始后半截正文换成一行 `Interrupted · retried`，等待行仍是 `Retrying #1`。出正文后等待行消失。成功的一轮可以折叠，普通失败消息仍阻止折叠 | §2.5 前端呈现 |
| T25 | TUI：被取代的尝试先冻结了推理片段，再出现新尝试；另测恢复历史和退避时停止 | 单元 | 已冻结的片段不重发，其余部分提交为一行 `Interrupted · retried`。恢复历史时同样只剩一行。重试没开始的消息保留原文 | §2.5 前端呈现 |
| T26 | 假模型服务：首次请求出半截正文后断开连接，第二次请求先挂起再给出完整回答 | 端到端 | Web 和 TUI 的实际界面先显示 `Retrying #1`，半截回答换成一行灰字，新回答完整出现，本轮结束行正常 | §2.5 前端呈现 |

## 4.3 集成边界

- **LLM 层与 lifecycle 之间**：LLM 层通过现有 `retry` 帧给出累计次数，lifecycle 用该次数传回 `priorFailedAttempts`。`stepRetry` 只传等待时间，由 T5、T6、T8 和 T18 验证。
- **lifecycle 与上下文投影之间**：`retried` 标记，由 T8、T9 验证。
- **后端与前端之间**：02 §2.5 的前端衔接约定由 T22 验证，前端呈现由 T23–T26 验证。
- **外部依赖**：自动化测试使用受控的 HTTP 响应或本地服务。真实模型用于手工验收。

## 4.4 回归清单

- LLM 层仍然不在流内部重放已经输出过的内容。原有“已有输出不重放”的测试按新语义改写：LLM 层不重放，只发出决定。
- 上下文摘要的重试保持不变：摘要请求仍是 `maxRetriesPerStep: 0`，由 `ContextManager` 最多请求两次。标题生成同样不启用整步重来（T17）。
- 回滚兼容：用旧代码读取带 `retried` 的消息，按普通中断消息投影，不报错。
- 上下文超长的强制压缩路径保持不变。
- 11-11 议题已有的后端请求事实及事件继续可读。
- 输出长度截断和内容过滤仍然不重试，也不自动续写。
- 旧消息（没有 `retried` 字段）的投影结果不变。

| 项 | 标准 | 如何验证 |

## 4.6 对抗性审查要点

| 攻击面 | 防御 | 残余风险 |
| --- | --- | --- |
| **工具被执行两次**：如果以后改成“边输出边执行工具”，整步重来就会重复执行 | 现在工具只在流完整结束后执行；T10 固定这个前提 | 以后改工具执行时机时，必须重新审视本议题 |
| **预算被悄悄重置**：`priorFailedAttempts` 在快照变化重试、强制压缩等其他 `step -= 1` 路径中被清零或丢失，导致无限重试 | 只在进入新的一步时清零；T12 统计实际 HTTP 次数，T18 覆盖强制压缩路径 | 新增其他重跑路径时可能再次出错 |
| **改变摘要重试资格** | 以模型请求的用途限定新规则，由 T17 检查实际请求次数 | 无 |
| **停不下来**：等待没有绑定 `signal`，或者等待结束后没有再次检查是否已取消 | T11 覆盖用户停止和子代理时限两种情况 | 无 |
| **模型看到半截内容**：`retried` 标记写入失败，或者摘要序列化没有走同一个函数 | T9 检查真实请求体；投影规则只在 `selectFailedHistoryText` 一处 | 无 |
| **把未知错误当成可重试** | T2、T3 固定已知临时错误才重试。未知错误保留可用安全诊断并结束 | 新的临时错误可能需要凭实际证据补充识别 |
