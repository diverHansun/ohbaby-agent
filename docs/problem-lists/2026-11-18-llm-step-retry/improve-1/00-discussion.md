# 讨论记录与已确认要点

> 2026-11-18 与用户讨论定稿。证据与推理见 01，方案见 02，验收见 04。

## 1. 背景与动机

2026-11-16 的一次长任务里，主代理同时派出 3 个子代理做表格审核，其中 2 个中途失败，一共留下 3 条失败记录。用户发现子代理经常失败，于是提出两个问题：一次网络波动就让子代理结束，那前面跑的内容还有意义吗？子代理和 Side Chat 这类直接依赖 LLM 请求的调用，有没有做重试？

之前的诊断（ChatGPT Codex 会话）和本次核查得出一致结论：

- 主会话、子代理和 Side Chat 用的是同一条请求链路，也是同一套重试策略。所以失败的原因不在“子代理没有接重试”。
- 重试覆盖的范围太窄。三条失败记录都是 `attempt: 1`、`retryScheduled: false`，也就是第一次出错就放弃了。
- 已完成的工具结果和历史都保存着，子代理实例也没有关闭，所以前面的工作并没有白做。缺的是遇到临时故障后接着完成任务的能力。

用户最初的设想是“优化 retry 机制，并把它扩展到主会话、子代理和 Side Chat”。讨论后调整为：在三者共用的那一层补齐重试，改一处，三边同时生效。

## 2. 已确认：目标与范围

| 编号 | 决策项 | 结论 |
| --- | --- | --- |
| D1 | 改在哪一层 | 改共享链路，不给子代理或 Side Chat 单独加重试。LLM 层负责判断“能不能重来”，lifecycle 负责“怎么重来” |
| D2 | 模型开始输出后再断线 | lifecycle 从头重新请求当前步骤。沿 `cause` 链识别已知网络码，覆盖实测的 `UND_ERR_SOCKET`。其余可重试场景为缺终止事件、空闲超时和 D6 的已知临时错误。协议校验、工具参数解析、取消、内容过滤和长度截断沿用现有规则 |
| D3 | 半截输出与待处理输入（方案 A） | 后端保存被重试取代的半截输出及中断状态，模型上下文排除这条尝试。重试使用已完成工具结果及仍待处理的输入，成功后才确认处理。预算耗尽后，最后一次确实中断的正文沿用现有带说明的历史投影。前端呈现见 D11 |
| D4 | 重试预算 | 开始输出前后共用每步 5 次临时故障重试。强制压缩恢复沿用现有的一次重发机会，且压缩前后重试计数连续。进入下一步才重置。只有 lifecycle 启用整步重来，摘要继续沿用现有重试规则 |
| D5 | 用户停止 | 退避等待和重新请求都必须响应停止，停止后不再重试 |
| D6 | 流里返回的服务端错误 | 三种协议都保留可用的上游错误码和类型。只重试已知临时错误，例如限流、过载和明确的服务端错误。认证、额度、权限、无效请求、策略限制和未知错误结束当前请求，保留可用的安全诊断信息。上下文超长走既有压缩恢复 |
| D7 | 缺终止事件的流 | 各协议按自己的结束条件识别 EOF。Anthropic 必须收到 `message_stop`，仅有 `stop_reason` 时仍算中断。以已交付的正文、推理或工具片段区分原地重试与 D2 的整步重来 |
| D8 | 子代理最终失败时 | 状态为 `failed` 时（`timed_out` 不算），发给主代理的失败结果里补一句：实例仍然可用，历史和已完成的工具结果都还在，可以继续给它发任务。只补提示，不自动续跑。不统计工具调用次数，因为现有结果里拿不到这个数，为一行提示去查库不值得 |
| D9 | 文档落点 | `docs/problem-lists/2026-11-18-llm-step-retry/improve-1/`；不建模块级 improve 文档，02 列出实施后必须同步的权威设计文档 |
| D10 | 关键改动清单 | 02 不写关键改动清单，只写到文件和符号级别的改动面 |
| D11 | 前端呈现（TUI 和 Web） | 被重试取代的尝试只留一行灰字 `Interrupted · retried`，不展开、不显示错误原因，也没有复制按钮。TUI 已冻结进滚动区的片段（如推理）保留。等待行从退避开始一直显示 `Retrying #n`，跨消息接着数，直到新尝试出现可见内容。退避时停止、重试没开始的那条消息照常显示原文。被取代的尝试不阻止本轮折叠 |

本表以本次逐项复核的确认结果为准。真实端点验证完成后更新方案和验收标准。

## 3. 已确认：边界（不做的事）

| 项 | 结论 |
| --- | --- |
| 整轮失败后自动续跑（子代理或主会话） | 本轮不做。整步重来上线后再看失败率，需要时另立议题 |
| 让模型接着半截输出续写（方案 B） | 不做 |
| LLM 层自己重放已输出的流 | 不做。LLM 层“出现有效输出后不重放”的规则保留 |
| 新的重试配置项、重试框架或新的数据表 | 不做 |
| provider 或模型自动切换（fallback） | 不做 |
| 摘要请求的重试 | 不动，继续由 ContextManager 负责 |
| 前端额外信息 | 不显示断线原因、错误码、退避秒数和尝试上限。用户只需要知道“刚才那段断了，系统在重试”。被取代的半截回答不提供展开，因为新回答会完整重写同样的内容 |

## 4. 已确认：与关联议题的关系

- [模型等待与错误反馈](../../2026-11-11-model-waiting-and-error-feedback/README.md)：那一轮明确“不增加自动续写或部分输出后的自动重放”。本议题有意放宽其中“部分输出后不重来”这一条，范围限于 D2。它定下的 `retryScheduled` 事实、等待行所依赖的请求事实及错误归一化继续复用。
- [llm-client 目标与职责](../../../core/llm-client/goals-duty.md)：LLM 层“出现有效输出后项目层不重放”不变。“不新增自动续写”需要补充说明：lifecycle 的整步重来不属于续写。
- [lifecycle 架构](../../../core/lifecycle/architecture.md) 与 [lifecycle 数据模型](../../../core/lifecycle/data-model.md)：“无有效输出的内部重试不是新的可信 Step”需要扩展到整步重来的情况。
