# 5. 实施与验收

2026-11-19，在原仓库的本地分支 `codex/llm-step-retry` 实施，基线为 `798442de`。

## 实施结果

LLM client 在封存失败请求前判断是否重试。无有效输出时在该调用内退避。已有正文、推理或工具片段时，只有启用整步重来的模型步骤才能继续，LLM client 先封存 `retryScheduled: true`，再发出累计重试编号和退避时间。Lifecycle 保留失败助手消息，标记 `retried: true`，完成可取消的等待后重新准备同一步。模型请求和摘要都会排除被取代的消息。后端仍在完整响应通过校验后提交工具调用。

同一步最多安排五次临时故障重试，强制压缩恢复共用已消耗的计数。失败时已随请求发送的待处理输入在成功后才确认，之前完成的工具结果可以随重试使用。子代理执行失败且实例仍开放时，结果正文给主代理提供继续执行的提示。

## 验收场景

| 用例 | 核对结果 |
| --- | --- |
| T1–T4、T16 | 三种协议的已知流内临时错误和无输出 EOF 均重试一次并成功。Responses 保留明确失败事件的错误码，未知错误、无错误体的失败事件和终态错误只请求一次。Anthropic 的 `stop_reason` 需配合 `message_stop`。 |
| T5–T7、T20 | 本地 HTTP socket 在首段正文后被销毁，后端识别嵌套的 `UND_ERR_SOCKET`。请求结束记录早于重试帧，帧和中断错误携带相同延迟，LLM client 当次调用只发送一次请求。原生推理流的干净 EOF 同样可重试。证书、额度不足、协议错误、工具参数解析失败、provider 中止和调用方取消均未安排重试。 |
| T8–T10、T19、T21–T22 | 两次尝试使用不同请求和消息 ID，步骤号相同。请求结束事实早于原消息的失败状态。重试请求包含此前工具结果和一次待处理输入，排除被取代正文和中断说明。写文件工具仅在完整的替代响应后运行一次。耗尽预算时保留最后一次有正文的中断投影，无正文时沿用普通失败投影。 |
| T11、T13 | 持久化后端入口覆盖主会话、子代理和 Side Chat。三者均在同一步恢复。用户停止和子代理达到时限均能中断退避，未发出后续步骤请求。子代理结果为 `timed_out`，已安排的重试记录仍可查。退避时停止会为当前步骤发出一次 `turn:end`。 |
| T12、T18 | 交替发生输出前后临时故障时实发六次，随后以 `provider_retry_exhausted` 结束。加入一次强制压缩恢复时实发七次步骤请求，压缩前后重试编号连续为 1 到 5。 |
| T15、T17 | 仅失败且开放的子代理实例附上提示。摘要原来可重试的 503 和传输错误仍至多两次，流内临时错误和 EOF 仍只发一次。标题和摘要的部分输出中断均未启用整步重来。 |

Anthropic 现在通过同一条原始 SDK 事件流检查结束信号。没有正文、收到 `stop_reason` 但缺 `message_stop` 的摘要响应会记录为 EOF，仍只发一次请求。Responses 摘要继续沿用原有的压缩恢复判断。

## 真实端点

使用 `tests/models-4-tests.md` 的路由和项目 `.env` 的凭据，在隔离的持久化后端实例中运行固定短提示。SDK 正常请求真实模型，测试在客户端读到首段非空正文后注入故障。标题和测试准备步骤在本地完成。

| 后端入口 | 真实端点与模型 | 注入故障 | 结果 |
| --- | --- | --- | --- |
| 主会话 | OpenAI Responses · `gpt-6.1-terra` | 首段正文 SSE 事件后提前结束响应体 | 提示与运行均为 `succeeded` |
| Side Chat | ZenMux Anthropic Messages · `deepseek/deepseek-v4.1-flash` | 首个正文块的文本帧后提前结束响应体 | 提示与运行均为 `succeeded` |
| 子代理 | ZenMux OpenAI 兼容 Chat Completions · `deepseek/deepseek-v4.1-flash` | 首段正文后注入带嵌套 `UND_ERR_SOCKET` 的读取异常 | 子代理执行为 `completed`，子运行是 `succeeded` |

三条链路各实发两次请求，六次 HTTP 响应均为 200。SQLite 保留截断的正文及 `retried: true`，第一次请求记录 `attempt: 1`、`outcome: error` 和 `retryScheduled: true`。第二次用新的请求和消息 ID，以同一步骤号和 `attempt: 2` 发起请求，结果为 `stop`。重试请求中的助手历史条数与首次请求一致。

另用同一 ZenMux Chat Completions 路由实测退避期间停止。收到真实首段正文后向客户端注入 `server_error`，并令退避为 8 秒。重试事件发出后调用后端停止，实发一次 HTTP 请求并返回 200。运行和提示均为公开接口的 `interrupted`，事件流对步骤 1 发出一次 `run.turn.end`。SQLite 仍保留半截正文和重试排期。首次探针把公开状态误断言为 `cancelled`，复核接口约定后复验通过，两次各实发一次请求。

## 前端实施

2026-11-19 在同一分支实施。第一版已提交（`d03bd858`），按 00 D11 调整后的版本尚未提交。设计见 [00 D11](./00-discussion.md) 和 [02 §2.5](./02-optimization-plan-and-change-scope.md)。

已有输出后的整步重来对用户透明：

- 退避期间半截回答还在，等待行照常显示 Thinking。
- 新请求开始时，半截回答整条隐去，不留提示，Thinking 继续，计时不归零。
- 只有请求在出字前失败（如 503、429）时，等待行才显示 `Retrying #n`。这是做这个议题之前就有的行为。

错误原因、错误码、秒数和次数上限都不展示。

判断逻辑放在 SDK。`listRetriedAttemptIds` 在同一运行、同一步的替代请求启动后才标记旧尝试。替代助手消息只进入占位时，仍保留原文。`projectModelActivity` 的等待链只在同一步且带 `retryScheduled` 时跨消息延续，计时起点和尝试编号保持连续。链中最近一次失败的消息有可见输出时，阶段为 `requesting`，否则为 `retrying`。

Web 在 `ConversationStream` 中直接过滤掉被取代的尝试，它因此也不会阻止本轮折叠。`ExecutionProgress` 不把失败尝试的半截正文当作进展。TUI 在提交前用 `withoutRetriedAttempts` 处理消息：已冻结进滚动区的片段保留，其余部分丢弃，没有冻结片段的尝试整条去掉。主会话、Side Chat 和子代理浏览器共用这一逻辑。

## 前端端到端走查

本地假模型服务兼容 OpenAI 协议。普通提示的第一次请求流出半截正文后断开连接，第二次请求先挂起，放行后给出完整回答。含 “busy” 的提示第一次请求返回 503。实例使用隔离的配置目录。

**Web（内置浏览器）**

- 用 MutationObserver 记录状态变化，依次为：Thinking、半截正文流出、半截正文与 Thinking 同在（退避）、约 480ms 后半截正文消失且 Thinking 继续、完整回答出现。全程没有出现 `Interrupted` 或 `Retrying`。
- 挂起期间页面只显示 `Thinking 5s`。
- 打开第一版留下的历史会话，两轮回答之前都没有中断提示，折叠区里也没有。
- 503 提示的等待行显示 `Retrying #1`，放行后正常回答。
- 实例运行期间控制台没有新的报错。

**TUI（tmux，110×32）**

- 依次出现：半截正文流出且下方是普通的工作提示行、新请求开始后半截正文消失、工作提示行继续且计时从 1s 往上走、完整回答和 `Total 14s`。滚动区没有半截正文或中断提示。
- 503 提示显示 `Retrying #1`，放行后正常回答。
- 假模型不输出推理，走查没有覆盖“推理先冻结”的情况，这一情况由 T25 单测覆盖。

## 前端实施审查

第一版完成后派子代理审查代码和文档。它发现一处 TUI 缺陷：带冻结片段的被取代消息提交为灰字后，提交计数改成了灰字消息的长度，下一次更新会用这个数再切原消息，滚动区多出一行灰字。当时用夹取冻结数修复，并在 T25 中补了新尝试继续输出的回归断言。调整为隐去之后，被取代的尝试不再追加任何内容，提交计数不会再增长，夹取随之去掉，该断言保留并通过。

第一版走查记录的 Web 灰字与 `Retrying` 行之间约 57px 的间距，来自新助手消息尚无内容时的空消息块，属于既有问题，本轮未改。

调整后的版本再次派子代理审查，已处理 `run-process` 中重复的过滤逻辑、`projectModelActivity` 中多余的阶段判断及本文一处描述。只输出推理就断流时，退避期间暂缓写入中断提示。若在退避中停止，补上中断提示，见 T27。

## P2 修复复验

- SDK 和 lifecycle 回归覆盖了新助手消息已创建、替代请求未启动时停止的窗口。只发出一次模型 HTTP 请求，旧正文仍可见。SDK 单测也验证了 `startedAt: 0` 的占位记录。仅推理断流另测在退避、上下文准备完成时及准备阶段的输入协调中停止。三个场景都只写入一次中断提示。
- 内置浏览器接入本地可控 HTTP 模型服务。首个流断开后，旧正文随 Thinking 保留，第二次请求启动后旧正文消失，放行后完整回答出现。仅推理流断开后在退避中点击 Stop，出现中断提示。
- TUI 在 tmux 中接入同一个模型服务。Steer 在流断开前发出，随旧正文立即显示。第二次请求启动后旧正文从界面和滚动区消失，Steer 保留，随后出现完整回答。仅推理流断开后按两次 Esc 停止，出现中断提示。
- Web 和 TUI 各用真实 `deepseek-flash` 完成一轮流式请求。本地模型服务负责断流、退避和停止的可复现场景。
- UI runtime 的整步重试和子代理端到端测试共 13 项通过。全量 `pnpm test` 通过 8,634 项，跳过 29 项。构建、类型检查、ESLint 和格式检查均通过。
