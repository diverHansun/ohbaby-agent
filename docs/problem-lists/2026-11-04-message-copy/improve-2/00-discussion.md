## 1. 背景与动机

improve-1 和[轮次投影议题](../../2026-11-06-turn-projection/README.md)的前端部分已经实施。用户验收时发现，复制按钮还有两处不对：

1. **长会话里，旧答复还在，复制按钮却消失了。** 一条子代理唤醒后的收尾答复，起初有 `Copy answer` 和 `Subagent update` 耗时行。用户再发一条消息后，这条答复移出服务端最近 50 条消息的窗口：页面上正文还在，按钮和耗时行一起消失。点 `Load earlier messages` 后两者恢复。
2. **隐藏工具执行后中断，阶段说明被当成了最终答案。** 模型先写 `I will check the private task list.`，随后真的调用了 `todo_read`。工具写盘后中断服务，再打开同一会话，页面正确显示 `interrupted`，却在这句阶段说明下面给出了 `Copy answer`。

## 3. 已确认：问题 1 的修法

验收标准：一条答复只要还显示在页面上，就能找到它所属的 run（普通轮次还有 prompt），不需要先点 `Load earlier messages`。

| 决策项 | 结论 |
|---|---|
| 修在哪一层 | 只改 Web store，后端不动。Web 自己决定保留哪些旧消息，就由它自己保留这些消息对应的 run 和 prompt |
| 缓存什么 | 实时视图里已结束的 run 和已结束的 prompt，与消息一样缓存。只缓存 run 不够：普通轮次靠 prompt 找回自己 |
| 什么时候用缓存 | 缓存表里的条目不逐条删除；组合快照时，只用仍被显示中的消息引用的副本（run 看消息的 `runId`，prompt 看 `userMessageId` 或 `runId`）。与后端 `visibleRuns` 是同一条规则：run 跟着消息走。只经 prompt 引用、自己没写过消息的 run 不取用，与后端一致，这一轮仍靠 prompt 算出来 |
| 新旧副本谁覆盖谁 | 运行中的 run 和未结束的 prompt 不进缓存，它们一定在实时视图里，以实时副本为准。已结束的副本不会再变，不存在旧副本盖掉新副本的问题。历史页写入 run 时同样跳过运行中的副本 |
| 不在本轮 | 已加载过历史后，“加载更早消息”的起点不再跟随实时视图更新。核实时顺带发现，未验证，和复制按钮无直接关系 |

## 4. 已确认：问题 2 的修法

验收标准：纯正文流到一半点 Stop，仍可复制已显示的正文；阶段说明后面调用过隐藏工具、随后中断，这条阶段说明没有 `Copy answer`。两种情况在实时页面和重开数据库后表现相同。

| 决策项 | 结论 |
|---|---|
| 规则 | 一步里只要调用过工具，这一步就不是最终答案，隐藏工具也算。这是轮次投影 00 里“沿用工具消息的排除规则”的补充说明，不是新规则 |
| 后端 | 只改 `messageToUiMessage` 一处：删掉隐藏工具片段时，在消息上加可选字段 `hiddenToolCalls: true`。`select_tools`、`todo_read`、`todo_write` 都算。工具照样不显示。字段只记录事实（这一步调用过界面不显示的工具），“因此不是答案”是 Web 的规则 |
| Web | 判断最终答案时，带这个标记的消息不算答案。复制按钮继续只挂在 `answerId` 上，不另写规则 |
| 不改 | `run-stream-adapter.ts` 和 TUI。前者不是 Web 主会话的消息来源，子代理详情本来就没有答案复制按钮；TUI 没有复制功能 |
| 放弃：把工具数据照发给客户端，由界面隐藏 | 这是 deepseek-harness、kimi-code、ZCode 的做法。对我们来说，等于重新划分后端、Web、TUI、导出各自的隐藏职责，超出本次修复范围 |
| 放弃：中断的轮次一律没有答案 | 这是 codex 的做法，但和 2026-11-07 已确认的“Stop 后可以复制已显示的半段正文”冲突 |
| 不在本轮 | Web 的 `filterTodoToolMessages` 只认 `todo_read` 和 `todo_write`，与后端的隐藏名单不一致；隐藏名单在后端、Web、TUI 共有四份。这些不影响本次修法，列为以后的候选 |

## 5. 参考项目

调研了 codex、deepseek-harness、kimi-code、ZCode，详见 [03](03-reference-projects.md)。结论：判定答案的规则（调用过工具就不是答案）与 codex 核心层、deepseek-harness 的折叠规则、kimi-code 的 Web 端一致；把“调用过工具”这个事实留在源头是 codex 的做法；复制按钮与答案判定必须是同一套规则，deepseek-harness 和 kimi-code 正是因为复制另有一套宽松规则而出现同类问题。
