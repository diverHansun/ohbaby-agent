# 讨论记录与已确认要点

> 2026-11-04 与用户讨论定稿。第 2 至 4 节是讨论中确认的结论；第 5 节是写规划时根据代码勘测补充的决定，随整套文档提交用户审查。推理过程见 [01](01-problem-analysis-and-current-state.md)，实施方案见 [02](02-optimization-plan-and-change-scope.md)。

## 1. 背景与动机

用户想在一段对话的某个节点“分个岔”：保留到这一轮为止的上下文，换个方向继续问，又不想破坏原来的会话。现在只能新建会话从头讲一遍，或者在原会话里继续，把原来的走向搅乱。

## 2. 已确认：目标与范围

| 决策项 | 结论 |
|---|---|
| 做法 | 学 deepseek-harness（下称 dsh）：fork 是把切点之前的历史复制成一个新会话 |
| 切点 | 某一轮已结束对话的末尾，包含这一轮的完整回答。一轮就是一个主 run（轮次投影议题），所以切点按 run 定（2026-11-08 改定，原为按 prompt） |
| 哪些轮次能 fork | 跟着复制按钮走：哪一轮的最终答案有复制按钮，哪一轮就有 fork 按钮。用户、goal、子代理唤醒触发的轮次都算；失败、中断但最终答案有正文的也算（2026-11-08 确认） |
| 来源记录 | 在新会话的 `session.data` 里记一份最小的来源信息：来源会话、切点所在的 run。不使用 `parent_id`（它是子代理专用的） |
| 侧栏 | 和普通会话平级，按更新时间排，不嵌套（2026-11-09 讨论过嵌套，最终仍定为平级） |
| 归档、删除 | fork 和源会话互不牵连：归档或删除任何一方都不影响另一方 |
| Web 入口 | 两处：每轮最终答案的操作栏里、紧挨复制按钮的 fork 按钮；会话行菜单里的 fork（从最近一轮已结束的对话 fork） |
| TUI 入口 | 新增 `/fork`，从最近一轮已结束的对话 fork |
| 标题 | 照 dsh：`原标题 (1)`、`原标题 (2)` 依次递增，不加时间；用户可以自己改名 |
| goal | 不带过去 |
| 新会话继承 | 工作区、运行目录、agent、模型、reasoning 设置 |
| 不带过去 | 排队的 prompt、正在运行的那一轮、子代理实例 |

## 3. 已确认：边界

| 项 | 处理 |
|---|---|
| 从一轮对话的中间 fork | 不做。只能在一轮结束之后的位置 fork |
| 从用户消息 fork（“在这条之前分岔”） | 不做。需要改某条消息时用撤销重发 |
| 侧栏嵌套、从 fork 跳回源会话的链接、fork 标记徽章 | 不做 |
| 复制源会话的文件或快照 | 不做。fork 共用同一个工作目录，文件本来就是同一份 |

## 4. 已确认：与关联议题的关系

| 议题 | 关系 |
|---|---|
| [消息复制](../../2026-11-04-message-copy/README.md) | 回答下面的 fork 按钮挂在它的消息操作栏上 |
| [撤销重发](../../2026-11-04-conversation-undo/README.md) | 复制时跳过已撤销的消息，条件由撤销议题加在共用的复制函数和切点查询里 |

## 5. 规划中补充的决定

> 2026-11-08：P2 至 P6 描述的复制做法已经搬进 side chat 议题的 `copySessionHistory`（side chat 02 Stage 1 第 0 步），以那里为准；这里保留为决策来源。

勘测时发现、讨论阶段没有覆盖到的细节，理由见 01 和 02。原则是只复制“不复制就会出错”的东西，不为将来多复制。

| 编号 | 决定 | 一句话理由 |
|---|---|---|
| P1 | 接口以目标 run 定位：`POST /v1/sessions/:sessionId/fork`，请求体 `{ runId? }`。给了 `runId` 就切在这个主 run 的末尾（含这个 run）；不给就从后往前找最近一个已有最终 AI 回答正文的已结束主 run。只有用户问题、工具调用或空记录的轮次不能作为切点（2026-11-10 确认） | Web 的每一轮本来就是一个 run，回答按钮知道自己的 run；唤醒轮、goal 续跑轮没有 prompt 记录，按 prompt 定位会把它们漏掉 |
| P2 | 复制五张表的行：`message`、`part`、`prompt_submission`（含并入别的轮次的 `steered` prompt）、`current_run_input`、`run_ledger`。别的都不复制 | 少了 prompt 记录，Web 无法按轮分组；少了当前轮输入记录，steer 和子代理结果会从模型上下文里消失；后者有外键指向 run 记录 |
| P3 | 所有被复制的行都换新 ID。ID 改写用一条规则：复制行的文本列和 JSON 字符串，凡是值**完全等于**某个旧 ID 的，一律换成新 ID。消息 ID 按源会话的顺序编号生成，两个客户端请求 ID 直接生成新值 | 不用逐个字段列举（`parentId`、`runId`、`runtimeInput`、提醒锚点、`steer_receipt` 等），以后新增字段也不会漏 |
| P4 | 工具调用的 `callId` 不改 | 模型原生状态（加密推理等）回放时要求 `callId` 对得上 |
| P5 | 切点之后才发生的压缩，会在切点之前的片段上留下“已压缩”标记，而摘要消息不在复制范围里。复制时清掉这类标记：片段的压缩时间晚于最后一条被复制消息的时间，就去掉 | 否则这些片段在新会话里既不显示原文，也没有摘要替代，模型上下文会缺一块 |
| P6 | 复制在一个同步数据库事务里用 SQL 完成，照 `archive.ts`、`workspace-move.ts` 的写法；新会话的统计按复制结果直接写好 | 现有的会话创建接口设不了模型、reasoning、统计，消息存储也没有批量写入；一个事务保证要么全有要么全无 |
| P7 | 源会话不需要空闲。fork 只读源会话已提交的行，不占用它的执行闸门 | fork 不修改源会话；dsh 也允许在源会话运行时 fork 最近一轮已结束的对话 |
| P8 | 源会话必须存在、是根会话、未归档。错误码与状态码复用现有的 `SESSION_NOT_FOUND`（404）、`SESSION_NOT_ROOT`、`SESSION_ARCHIVED`（409）；没有可用的切点时返回新错误码 `FORK_TARGET_INVALID`（400）：run 不存在、不属于这个会话、不在主上下文、还没结束，或没有最终 AI 回答正文 | 与撤销重发议题、现有会话接口保持一致 |
| P9 | 标题在服务端算：去掉源标题末尾的 ` (n)`，在现有会话里找同名的最大序号，加一 | 一次请求就能拿到最终标题，不用像 dsh 那样再发一次改名请求 |
| P10 | fork 成功后，Web 和 TUI 都切换到新会话 | 用户点 fork 就是想在新会话里继续 |
| P11 | 新会话里，源会话子代理的卡片仍然显示结果文字，但打不开子代理对话；模型读源会话的子代理大结果文件和工具长输出文件时要弹确认（这些文件都在源会话的存储区里；2026-11-06 复核时补上工具长输出）。本轮接受，不处理 | 子代理实例和执行记录不复制，处理它们要牵出子代理的整套生命周期，不值得 |
| P12 | 源会话里如果有当时没被处理的 steer，新会话里会同样显示为“未处理”的提示卡片。本轮接受 | 这是复制历史的如实结果；为它单独过滤反而让两个会话看起来不一致 |
| P13 | `session.data.fork` 要加进会话类型的读写转换里 | 现有的 `encodeData` 只写回四个固定字段，不加的话会话下次更新时来源信息就丢了 |

- 2026-11-08：开发顺序定为 side chat → fork → 撤销重发。逐条讨论 fork，每个问题先对比 code-cli/ 下的项目。
  - 第 1 问（切点、哪些轮次能 fork、按钮位置）：切点按 run 定，含这一轮；不指定时切在最近一个已结束的主 run（dsh、codex、kimi-code 都这样）。哪些轮次能 fork 学 codex、dsh：跟着复制按钮走，不学 ZCode、kimi-code 的“只认用户开启的轮次”，因为 ohbaby 的唤醒轮也单独显示、有复制按钮。按钮放在复制按钮旁边（dsh、ZCode、kimi-code VS Code 版都这样）。
  - 第 2 问（复制代码要不要和 side chat 共用）：共用，学 ZCode。对比结果：ZCode 的 side chat 是 SQLite 里的子会话，和 Fork 共用 `commitAtomicConversationFork`；codex 的 `/side` 就是一次临时 fork；kimi-code 的 btw 是会话里的一个子代理，和会话 fork 分开写，关掉后文件一直留在磁盘上；deepseek-harness 还没做 side chat，提案打算复用 fork 的历史复制。ohbaby 的 side chat 是存盘的隐藏会话，和 ZCode 同类。差别放在函数外面：fork 自己定切点、算 `(n)` 标题、写 `data.fork`、发事件；复制函数不知道是谁在调用。来源信息去掉 `inheritedMessageCount`，`sourceRunId` 已经唯一确定切点。
  - 第 3 问（缓存）：fork 出来的会话用自己的缓存身份，不沿用源会话。学 codex、kimi-code、ZCode、dsh，只有 opencode 沿用。已加载的 MCP 工具：复制。MCP 工具本身是全局的，但“这个会话加载了哪些”按会话记在内存里，不从历史重建，不复制的话模型再调用历史里用过的工具会被拒绝；复制用 side chat 议题的 `copyScope`。从历史重建是根本修法，另立议题。2026-11-10 改定：[已加载 MCP 工具从历史重建议题](../../2026-11-09-mcp-loaded-tools-from-history/README.md)先于本议题实施，新会话从复制来的历史重建切点时的已加载工具，不再写 `copyScope`。
  - 第 4 问（“总是允许”规则）：不带，学 codex。fork 是独立的新会话，side chat 带是因为它是主会话的临时帮手。
  - 第 5 问（叫法、标题、fork 后去哪）：TUI 叫 `/fork`；Web 按钮用分叉箭头图标，紧挨复制按钮，悬停提示“Fork from here / Starts a new session from this point. This one stays as it is.”（参照 Claude app 截图）；标题保持 `原标题 (n)`；fork 后切到新会话。新会话是普通主会话，不进右侧面板（不像 side chat）。  
  - 第 5 问补充（左侧会话列表）：6 个开源参考项目都平级显示，fork 来源都记在独立字段里，不借用子代理的父字段（ZCode 借用过，重启后 fork 从列表消失，只好改过滤条件）。用户确认：学多数项目，后端平级；只在显示上学 Claude app 嵌套。只嵌一层；源会话不在同一列表（已归档、已删除、未翻到）时 fork 显示在最外层；默认展开，折叠状态存浏览器本地；置顶区、搜索不嵌套；归档、删除互不牵连；TUI 平铺。
