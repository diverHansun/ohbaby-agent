# 讨论记录与已确认要点

> 2026-11-06 与用户讨论确定。第 2 至 4 节是用户确认的结论；第 5 节是写规划时根据代码勘测补充的决定，随整套文档提交用户审查。现状证据见 [01](01-problem-analysis-and-current-state.md)，方案见 [02](02-optimization-plan-and-change-scope.md)。

## 1. 背景

用户在实际使用中发现两个问题：

1. 消息复制按钮的那一行可能被输入框挡住。
2. 不是每个会话都能复制 AI 的最后一条回答。例如会话 `session_1793633275109_owbs9e1` 的最后回答就没有复制按钮。用户注意到主代理会被多次“唤醒”，怀疑这和“一轮做完后只展开最终回答”的折叠设计有关，难以用“最后一条消息”来界定任务是否做完。

用户要求去看 codex 和 `code-cli/` 下的项目怎么处理，并判断是否应该从源头修。

第 1 个问题是消息复制议题的样式问题（最后一条消息下面的操作栏伸进了输入框的位置），在消息复制议题的分支上单独修，不属于本议题。

## 2. 已确认：从源头修，“一轮”按 run 划分

| 决策项 | 结论 |
|---|---|
| 根因 | 子代理唤醒主代理时会新开一个 run，但不写 prompt 记录；Web 和 TUI 按 prompt 划分一轮，这个 run 就没有折叠、最终答案、复制和耗时 |
| 修法 | 从源头修：界面上的一轮按主会话的 run 划分，后端给 run 记下触发来源 |
| 唤醒的显示方式 | 主代理空闲时被结果唤醒，新开的 run 单独成一轮：每轮各自折叠，各自显示答案、复制按钮和耗时行，并标明是子代理触发的 |
| 借鉴 | 参考 codex、claude-code、deepseek-harness、ZCode、kimi-code 的做法，见 03 |

**已确认的唤醒规则（2026-11-06）**：后台子代理正常运行时，由程序检查状态，不因时间到了就叫醒主模型。子代理交回结果、失败或超时，才把结果交给主代理：主代理忙时并入当前 run，空闲时按已有规则唤醒。该决定取代[旧方案 D31、D44](../../2026-10-26-subagent-lifecycle/improve-1/00-discussion.md) 中按 2/5 分钟启动主模型巡查的部分。过去已经发生的巡查仍按真实 run 展示。

这里沿用[子代理 D54](../../2026-10-26-subagent-lifecycle/improve-1/00-discussion.md)：新子代理一律在后台运行。派活后主代理可以继续工作，也可以结束当前 run；接收结果不要求主代理一直占着这个 run。Goal 是否另开 run 续跑是独立问题，尚在讨论。

**已确认的 AI 消息复制范围**：每个已结束的主 run 只检查最后一条 AI 消息。无论用户、Goal 还是子代理开启该 run，只要这条消息有可复制的模型正文，就在它下面放一个按钮。出错或中断时可以复制已经写下的正文，系统附加的错误或中断提示留在界面上。沿用工具消息的排除规则；即使展开过程，中间的阶段结论也只供手动选中复制。最后一条没有合格正文时，到此为止，不往前找。

## 3. 已确认：术语

ohbaby 的执行循环分 run、turn、step 三层，turn 里面还有 call。本议题统一按下面的意思使用这几个词（代码对应见 01 §1.1）：

| 词 | 意思 |
|---|---|
| run | 一次执行，`run_ledger` 里的一条记录。一个用户 prompt、一次 goal 续跑、一次子代理唤醒，各自是一个 run |
| turn | run 内 `Lifecycle.run` 的一次循环，从 `turn:start` 到 `turn:end`。一个 run 只有一个 turn |
| step | turn 里的一次模型请求，对应一条助手消息 |
| call | step 里的一次工具调用，用 `callId` 标识 |
| 一轮（界面） | 界面上折叠、显示耗时、挂复制按钮的单位。本议题之后，一轮等于主会话的一个 run |

## 4. 已确认：范围与边界

| 项 | 结论 |
|---|---|
| 端 | 后端、Web、TUI 都在本议题内 |
| 关键改动清单 | 不写，02 只写到文件一级 |
| 模块级改进文档 | 不写；实施完成后同步各模块的权威文档 |
| fork、撤销、side chat | 这几个议题的文档等本议题实施落地后再改，本议题不动它们的文档 |
| 合并成一次“交流” | 不做。把一条用户消息之后的几轮唤醒合在一起、只显示最后一个答案（deepseek-harness 的做法），留到以后视需要再议 |

## 5. 规划中补充的决定

| 编号 | 决定 | 一句话理由 |
|---|---|---|
| P1 | run 的触发来源有三种：`user`、`goal`、`subagent`，在创建 run 时写入 `run_ledger.trigger`，并通过 `UiRun.trigger` 交给前端。触发来源和提交方（owner）是两件事：带子代理状态输入的 run 记为 `subagent`，即使它在 goal 期间由 goal 提交；其余按提交方记 | 现在只有 `user` 一个值，goal 续跑和子代理唤醒都被记成了 `user`；参考 ZCode 的 `origin`、kimi-code 的 `PromptOrigin`、codex 的 `turn_trigger`。提交方还决定权限、todo 作用域和 `driver`，不能拿它直接当触发来源（2026-11-06 子代理审查发现） |
| P2 | `UiRun` 增加 `outcome`：`succeeded`、`failed`、`cancelled`、`interrupted` | 现在的 `UiRun.status` 把成功和用户取消都映射成 `idle`，前端判断不了“这一轮是否成功结束”，这正是 2026-09-29 折叠议题只能依赖 prompt 的原因 |
| P3 | 视图里的 run 跟着已加载的消息走：返回已加载消息涉及的 run 和仍在运行的 run，翻历史时一并返回该页涉及的 run | 现在只返回最近 50 个 run，长会话往上翻，较早的轮次会失去折叠和复制 |
| P4 | 有 prompt 的轮次继续用 prompt 的时间算耗时，没有 prompt 的用 run 的开始和结束时间 | 普通轮次的耗时显示不变；只给原来没有耗时的轮次补上 |
| P5 | 子代理触发的轮次，耗时行前面加上 `Subagent update`；goal 续跑的轮次已经有一条显示 goal 内容的用户消息，不另加标签 | 和 ZCode 的“后台结果”标题、deepseek-harness 的触发节点一致；不重复标注 |
| P6 | 旧数据里子代理唤醒的 run 被记成 `user`，前端兜底判断：没有 prompt、且能看到开轮时 `subagent-status` 唤醒记录的 run，按子代理触发处理。只看到中途交付的结果时省略标签 | 不做数据迁移，也能让旧会话正确显示 |
| P7 | 消息复制常显的那一行，挂在最后一个已结束轮次的最终答案上，包括唤醒那一轮 | 和消息复制议题的规则一致，只是轮次的来源变了 |
| P8 | 右侧栏子代理详情里的对话不在本轮范围内 | 子代理视图另有自己的 run 和数据来源，本轮先修主会话 |
| P9 | `subagent_execution.root_prompt_id` 从未写入的问题，只记录、不在本议题修 | 它影响的是撤销议题的方案，等本议题落地后在撤销议题里一起修订 |
| P10 | 没有任何消息的 run（中途失败、被打断）不成为一轮 | 本地数据里没有 prompt 的 run 大多是这种；它们在界面上本来就没有内容可显示 |
| P11 | Web 和 daemon 一起发布，不为“新前端连旧后端”另写一套规则：`outcome` 缺失时用 prompt 的状态代替，再没有就不折叠 | 只保留一条投影路径 |
| P12 | 耗时组件沿用现有的名字（Web 的 `PromptDuration`、TUI 的 `PromptCompletion`），只在注释里说明它们现在按 run 工作 | 改名牵涉 20 多处引用，和目标无关 |
