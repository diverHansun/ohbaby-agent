# 第 4 批已确认结论与边界

> 2026-10-12 汇总自 plan [00](../plan/00-discussion.md)、[02](../plan/02-optimization-plan-and-change-scope.md)、[discussion-notes §17](../plan/discussion-notes.md)。只列已确认结论，不重复推理过程；推理和证据见 [01](./01-problem-analysis-and-current-state.md)、[02](./02-optimization-plan-and-change-scope.md)。

本批把“何时切、切到哪、怎么一次性落地”收口。上游第 1～3 批解决发送侧（预算、请求形状、重试），本批解决本地选择与提交侧。

## 1. 目标与取向

- 压缩要真腾出空间，保留任务连续性，不让未读信息被错误移除。
- 精细化指**问题和需求**的精细化，靠复用已有工具、请求准备、计数、事务和调度，不靠新增分配器、增长预测或多套降级。
- 一条纪律贯穿全批：**不允许留下只能靠后续批次拆除的脚手架**。

## 2. 一次临时计划与单滚动摘要（已确认）

| 决策项 | 结论 |
| --- | --- |
| 选择次数 | 一次压缩只选一次范围；生成、压后检查、提交消费同一份选择，提交时不再临时重切 |
| 计划内容 | 复用现有 candidate，持有 prepared 请求、待退场 parts 快照、保留 IDs、受保护 inputIds；`compactionId` 直接用现有 attemptId |
| 摘要份数 | 模型上下文只留一份更新后的摘要；旧摘要和原始记录继续留库 |
| 首次迁移 | 读全部仍活动的旧摘要，与覆盖的旧段一起退场，只留新摘要；不建 `activeSummaryId`、摘要链表或后台迁移 |

## 3. 固定 20K 尾段（已确认）

- 近期原文按固定预算 20K 选取，不按窗口比例，不设 40K／30% 第二档。
- 从最新往前累计到约 20K，切点对齐合法边界（真实用户消息起点或助手消息起点），不拆工具调用与对应结果；未闭合调用整组向前扩展。
- 20K 是**首选预算，不是硬线**：为对齐允许略超；最新一组不可拆交互本身超过 20K 时，整组保留、允许超预算。
- 保留段**不写进摘要指令**；边界由宿主在计划里决定，模型看不到，避免“提前告知的边界与实际不一致”造成丢信息。

## 4. 模式 A：摘要请求本身放不下（已确认）

- 只裁摘要请求的**临时副本**，从较老原文的完整交互组开始，按估算一次裁够。
- 保护全部活动旧摘要、受保护的新输入、未闭合依赖和必须留下的近期内容；工具调用与结果整组处理，不拆配对。
- **最多占用第 3 批已确认的两次实际请求总额度**，不单开 PTL 额度；可裁材料耗尽仍放不下则失败。
- 容量检查的摘要输出预留用**摘要自己的** `requestedOutputTokens`（见 [02 §4.1](../plan/02-optimization-plan-and-change-scope.md)），不取普通偏好。
- **遗漏 = 未进入成功摘要请求、压后也未原样保留的原文**。其精确 part IDs 和容量原因写进新摘要正文 part 的现有 `metadata`；退场复用 `time.compacted`，不新增 `time.dropped` 或表。
- 宿主附加一句遗漏说明并计入正文上限；完成提示也简短告知；不承诺尚未建设的召回能力。
- 裁剪点之后的旧前缀不再照原样复用；此前未变的 system／tools 和旧摘要仍可能命中缓存，按真实 usage 记录，不写“必然全部 miss”。

## 5. 模式 B：压完之后仍放不下（已确认）

- 判据是压后完整输入＋本次普通请求全量输出预留＋安全余量超过窗口。**一次按缺口算**保留预算：`max(0, 窗口 − system − tools − 摘要 − 安全余量 − 本次普通请求输出预留)`，取 `min(20K, 该值)`，再对齐边界，不循环递减。公式为简写，受保护输入与协议固定开销也须先扣除，按实际投影各计一次。
- “本次普通请求输出预留”取**全量 `config.maxTokens`**，不套 `maxOutputReservation` 的 50% 帽子。
- 摘要额度不动；收缩守住边界规则，**下限是最近一个完整交互组**，缩到只剩它仍装不下就直接失败、保留原历史，不缩到没有原文尾段。
- 收缩是事后决定留多少原文，**摘要请求体一个字节都不变，缓存身份不变**。
- 装不装得下由 ohbaby **本地判定**，不照发超窗请求靠 provider 报错兜底。

## 6. 最终正文、触发与失败（已确认）

- 最终摘要正文 ≤16K，包含宿主**事先预扣**的文件操作信息与遗漏说明——生成前就计入额度，不为模型写满后再追加造成确定性超限。
- 自动触发沿用完整窗口占用 `currentTokens / contextLimit`（现有 `needsSummaryCompaction`），**不含输出预留帽**；带 50% 帽的 `usageRatio` 只是 mask 触发用的，随 mask 在第 5 批删除，不留给 summary。
- “占用确实下降”是硬门槛：压完不降算失败，保留原历史，不切过去。摘要成功且压后完整请求能发、确实变小，才提交。
- 两个词分开：**没有可压旧段＝无需压缩**，跳过、不启动模型、不算失败（但仍需压后容量检查）；**发了摘要但压后占用没降＝无收益**，算失败。
- 触发还受**无进展地板**约束：每次成功压缩提交后把压后绝对占用记为地板，占用严格大于地板才允许再次自动压缩；地板按 session／scope，只在成功压缩后更新，不随 run 重置，**手动与 overflow／force 豁免**。
- 地板只抑制**相同容量条件**下的重复压力触发。窗口缩小、普通请求输出预留增大等容量条件变化后，容量保护按**完整请求**重新判断，**不被旧地板挡住**。

## 7. 失败终止、删旧限制与界面（已确认）

- **本批同批**完成三件事：接上“自动摘要最终失败结束本次运行”、删除 `MAX_COMPACTION_PER_TURN`、删除 `THRASH_*` 抖动锁。三者不可拆开；删除依据是失去引用，不是“名字看着旧”。
- 最终失败或无收益：结束本次自动运行，保留会话、全部历史和已完成工具结果；自动／overflow／force 不能在同一运行里另开摘要额度。用户明确重试或继续后进入新运行。
- 成功后：重新准备下一份普通请求并再检查容量。提交前 Stop 不应用候选；**提交后 Stop 保留已成功的事实**，不倒退成“未压缩”。
- 界面全部复用现有组件：进行中沿用 spinner 加 `Compacting`；完成后在消息流插一条暗色单行，给压前／压后占用；提交后立即刷新 footer 与占用面板（`composition` 里已有 `summarized-conversation`）。用本地估算，下一轮真实 usage 回来后按既有路径校正。摘要请求自身消耗不进占用显示，只在日志里。
- 用量归属：成功的摘要请求记录挂在这条摘要 `AssistantMessage` 已有的 `modelRequests` 上，**自动与手动一致**，`messageId` = **预分配的 `summaryMessageId`**；`purpose=context-summary` 判别所有权变体，`compactionId` 复用现有 attemptId。**同一事务**与正文、parts 退场一起落库，不另建尝试表、不加外键。不把摘要记录挂到普通消息上（否则记录所有权与所在摘要消息不一致）；普通请求 `runId／messageId／step` 保持必填；自动的 run／step 只作为真实关联信息、必要时附带（见 plan §6.1）。

## 8. 批次边界（已确认）

- 本批完成失败终止、force 一次恢复、Stop 与事务保护的基本链路；第 5 批贯通全部入口并做回归。force 标志在调用前置位、失败不回滚，同一步快照变化不重置，新 model step／新运行才重置；成功后重发不挂恢复钩子，二次超窗终止。
- prune 由第 3 批删除，mask 由第 5 批删除；本批不重复这些任务，也不改第 2 批工具结果投影。
- 本批产出的摘要、metadata、退场标记按普通消息保留；回退不把已退场历史无条件塞回窗口，也不重新请求模型。
