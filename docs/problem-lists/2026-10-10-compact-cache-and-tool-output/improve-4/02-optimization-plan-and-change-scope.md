# 第 4 批优化方案与改动面

> 依据 [00](./00-discussion.md)、[01](./01-problem-analysis-and-current-state.md) 与 [plan/02](../plan/02-optimization-plan-and-change-scope.md)。本文供后续开发者实施，验收见 [04](./04-test-and-acceptance.md)；本次只改文档。
> 源码路径除注明外相对 `packages/ohbaby-agent/src/`，以符号名定位。

## 2.1 方案总览

本批用一份临时计划管理摘要读取、原文保留和最终退场。有效摘要通过容量与收益检查后，和请求记录、遗漏 metadata、旧 parts 退场一起提交；同时接上失败终止与基本恢复保护，再删除旧次数上限和抖动锁。

```text
第 3 批的 prepared 材料 + 活动历史 + 受保护输入
  → 选择一次保留段：20K 首选，合法边界，超大最新组整组保留
  → candidate 保存计划、待退场快照、保留 IDs、受保护 inputIds
  → 预扣宿主已知追加文字，检查摘要请求容量
      放不下 → 模式 A：只裁临时请求副本中的较老完整组
                更新请求读取范围、重新预扣遗漏说明
  → 发摘要：使用第 3 批同一份两次实际请求预算
  → 校验有效正文、最终正文 ≤16K、覆盖与保留关系
  → 检查压后完整普通请求容量
      放不下 → 模式 B：一次按缺口收缩保留段，再检容量与遗漏
  → 检查占用确实下降
  → commitCompaction：摘要 + modelRequests + 遗漏 metadata + 精确 parts 退场
      提交前失败 / Stop / 冲突 → 不应用候选
      提交成功 → 刷新估算占用；自动重建普通请求，手动报告结果
```

Context 管选择与容量；LLM 层管请求、协议和实际 usage；MessageStore 管事务；调度器管新输入与运行状态。本批不增加计费服务、召回系统或通用工作流。

## 2.2 设计取舍

| 项目 | 选择 | 边界 |
| --- | --- | --- |
| 计划 | 扩展现有 candidate，生成、检查、提交共用 | 不增加历史版本树或第二处选择器 |
| 摘要 | 继承全部活动旧摘要，只留一份新摘要入模 | 原文和旧摘要继续留库，不建摘要链表 |
| 尾段 | 固定 20K 首选预算，按实际回传表示计数 | 合法边界可超预算，不设 40K／比例第二档 |
| 容量恢复 | 模式 A 改请求副本，模式 B 改压后保留范围 | 不互相替代，不另开请求额度 |
| 失败保护 | 最终失败终止运行，成功后的无进展地板抑制重复 | 与删除次数上限、抖动锁同批完成 |
| 用量与遗漏 | 复用摘要消息的 modelRequests 和正文 part.metadata | 不加表、外键或第二种退场标记 |
| 界面 | 复用已有 spinner、消息提示和占用组件 | 不新建用量面板或进度条 |

## 2.3 实施阶段

### Stage 4.1：临时计划与固定尾段

- candidate 持有 compactionId、prepared 请求、待退场 parts 快照、保留 IDs、受保护 inputIds，以及成功请求实际读取范围。compactionId 复用已有 attemptId。
- 摘要输入包含全部活动旧摘要。成功后旧摘要与被替代旧段一起退场，模型视图只保留新摘要，原记录继续存库。
- 尾段从最新向前按第 1 批的同源计数累计到约 20K，切点对齐真实用户或 assistant 消息起点，不拆 call/result；未闭合依赖整组向前扩展。
- 最新不可拆组本身超过 20K 时整组保留。受保护输入与未闭合依赖不因预算被裁掉；删去 `getHistoryToCompress` 的 `fullTokens × COMPRESSION_PRESERVE_RATIO` 分支。
- 保留边界由宿主决定，不写入摘要指令。生成、检查和提交不各自重新选边界。

完成条件：旧摘要继承、20K 计数与边界一致；超大最新组、未闭合依赖和受保护输入不丢。

### Stage 4.2：模式 A，摘要请求本身放不下

1. 只裁摘要请求的临时副本，从较老原文的完整交互组开始，按容量缺口一次裁够。
2. 保护全部活动旧摘要、受保护输入、未闭合依赖及必留近期内容；工具调用与结果一起处理。保护集合之外已无可裁材料仍放不下，则失败。
3. 摘要容量使用它自己的显式 `requestedOutputTokens`，不使用普通输出偏好。发送次数仍由第 3 批 Context 的同一计数管理：网络故障和容量恢复合计最多两次实际请求；本地检查不耗一次请求，但也不产生额外额度。
4. 记录成功摘要实际读取的精确 IDs。最终遗漏 = 未进入成功摘要请求、且压后未原样保留的原文；不能把所有“未读”直接当遗漏。
5. 遗漏的精确 part IDs 与容量原因随新摘要正文 part.metadata 保存。`time.compacted` 只表示退出活动视图，不证明已被模型总结。

裁剪点之后的旧前缀不再原样复用，此前未变的 system／tools／旧摘要仍可能命中缓存，按真实 usage 记录。第 1 批已删除旧 `shrinkSummaryHistory`；这里在现有 Context 选择逻辑中实现受保护的组选择，不恢复旧缩水重试函数。

### Stage 4.3：模式 B，压后普通请求仍放不下

判据必须使用压后完整请求：**实际输入估算＋本次普通请求全量输出预留＋安全余量＞窗口**。实际输入包括 system、tools、摘要、保留段、受保护输入和协议固定开销，各项按同源计量计算一次。

一次按缺口计算保留预算，沿用 plan 的公式：

```text
保留预算 = max(0, 窗口 − system − tools − 摘要 − 安全余量 − 本次普通请求输出预留)
目标保留预算 = min(20K, 保留预算)
```

上述是简写。实现时，未包含在 system／tools／摘要中的受保护输入与协议开销，也必须作为固定材料先扣除；不能漏算，也不能对已包含的材料重复扣除。普通输出预留取下一份普通请求实际发送的全量 `config.maxTokens`，不套半窗帽。

- 按目标预算一次向下收缩并对齐合法边界，不循环递减；受保护输入和未闭合依赖不裁剪。
- 下限是最近一个完整交互组。算出的空间容不下该组及其他受保护材料时直接失败，不拆组、不缩成零尾段。
- 模式 B 只更新同一计划内的保留集合，不重发或修改已经成功的摘要请求，摘要额度与缓存身份不变。
- 更新保留集合后重新计算遗漏及最终宿主说明，验证正文上限、完整请求容量和收益；不能为通过“无收益”检查另行裁尾或截断摘要。

完成条件：本地确认放得下才提交；失败保留原历史；不依赖 provider 再次报超窗来替代检查。

### Stage 4.4：正文、原子提交与新输入

最终正文 ≤16K，包含宿主追加的文件操作信息与遗漏说明。生成前预扣已知附加文字；模式 A 改变请求副本后，在下一次发送前重新预扣相应说明。若附加内容已占满额度，直接失败；后续模式 B 改变遗漏集合时仍须重验最终正文，不超限保存、不自动升额重做。

成功要求：非空正文、正常完整结束、无工具调用、最终长度合规、覆盖关系正确、压后完整请求能发且占用确实下降。

在一个 `commitCompaction` 事务内保存新摘要、它的 modelRequests、遗漏 metadata，并标记精确旧 parts 退场。待退场快照或相关工具组变化时冲突失败；失败、提交前 Stop 不应用候选。提交已完成后收到 Stop，保留已成功的事实。

压缩期间的新输入交给现有调度器。摘要读过准备时的受保护输入，不算普通请求已交付，不调用普通 request admission／delivery 确认。提交只作用于计划内精确 IDs；提交后重读历史和待交付输入，重建普通请求并重新检查容量。

完成条件：事务异常、冲突、Stop 前后及进程恢复都满足全部提交或全部不应用；新输入不丢、不误确认。

### Stage 4.5：失败终止、force 一次与无进展地板

以下保护和旧限制删除必须同批完成：

1. 删除 `MAX_COMPACTION_PER_TURN`、`THRASH_*` 及其专属参数、事件原因、reset 调用和测试；复用现有运行结束链路。
2. 自动摘要最终失败或无收益后结束当前运行，保留会话、原历史和已完成工具结果。当前运行的 automatic／overflow／force 不能为同一失败另开摘要额度；用户继续后进入新运行。
3. 普通请求 overflow 不进网络重试，进入一次 force 恢复。标志在调用压缩前置位，失败也不回滚；作用域是本次恢复流程，同一步因输入快照变化重入不重新获额，新 model step／新运行才重置。
4. 仅 force 成功、占用下降且容量通过后重发普通请求；重发不挂恢复钩子，二次 overflow 终止运行。摘要请求自身 overflow 只走模式 A，不递归发起 force。
5. 成功提交后按 session／scope 保存压后绝对占用地板，不随 run 重置；相同容量条件下，占用严格超过地板才允许再次自动压缩。手动与 force 豁免；窗口缩小、普通输出预留增大等变化必须重新判完整请求容量，不能被旧地板挡住。
6. 无可压旧段是 `not-needed`，不启动模型、不算摘要失败，但仍检查普通请求能否发送。发了摘要却占用不降才是无收益失败。

完成条件：同一 run 在占用正常增长时可连续三次成功压缩；无增长不重复压；一次最终失败后不另发摘要或装不下的普通请求。第五批只扩展全入口回归，不首次补这些保护。

### Stage 4.6：提示与占用刷新

进行中复用 spinner 显示 `Compacting`；成功后给一条压前／压后估算占用提示，有遗漏时简短说明。提交后按新投影调用既有 `updateFromContextUsage`，立即刷新 footer 与 composition 的 `summarized-conversation`，后续真实 usage 沿现有路径校正。

手动与自动结果语义一致，但不要求同一种传输通道：自动沿用 run 流，CLI 手动沿用命令生命周期，Web 沿用请求状态与返回结果；手动的占用刷新复用 `compactSessionInternal` 的 `context.window.updated`。业务失败须按 `result.status` 展示，不能把 completed action 一律当成功；Web 完成后重查当前占用。手动没有普通 run，不能为提示伪造 run。提交前 Stop 显示停止，提交后 Stop 不抹掉成功提示；摘要请求消耗不混入占用显示，按请求记录和日志保存。第五批验证各入口的展示与信号贯通，本批先完成对应组件及基本接线。

## 2.5 跨批接口契约

计划字段至少区分 `compactionId`、`preparedRequest`、`compactedPartSnapshot`、`keptIds`、`protectedInputIds`、成功请求的 `readIds`。模式 A 更新请求副本与实际读取事实；模式 B 是唯一允许改变已选保留边界的情况，更新后重新核对遗漏和退场。提交时不能另做选择。

第 3 批返回有效正文、成功 requestId、预分配 summaryMessageId 和成功 record。自动与手动 record 均为 `purpose=context-summary`，`messageId=summaryMessageId`，`compactionId` 复用已有 attemptId；普通 `agent-step` 的 runId／messageId／step 保持必填。

第 4 批用同一 summaryMessageId 创建摘要消息，把成功 record 放入其 modelRequests，与正文、遗漏 metadata 和旧 parts 退场同事务保存。失败、Stop、无收益而没有摘要消息时只留日志；不建尝试表、假 run 或额外外键。

## 2.6 迁移、回退与风险

旧会话第一次成功压缩时继承全部活动旧摘要，再切为一份；原记录留库，无后台全文迁移。usage 和遗漏信息用现有记录／metadata 兼容读取，旧记录缺字段时保持未知。本批不做数据库 schema 迁移。

回退保持已提交摘要、请求记录与原历史可读，不把所有退场历史无条件塞回窗口，不重新请求模型来“撤销”。缓存前缀可能变化，不承诺回退仍命中。

主要风险及验收：模式 A 未读范围错误退场（E7）、模式 B 漏算普通输出或受保护材料（E8）、Stop／冲突半次提交（D6）、删帽后跨入口循环（E3／E4）、旧地板挡住容量变化（D1）。摘要语义连续性另用已知事实样本检查，标题齐全不能证明内容完整。

## 2.7 与第五批的边界

第四批完成选择、事务、Stop 基本链路、失败终止、force 一次保护与提示刷新；第五批贯通手动／自动／force 的现有入口、补齐手动 busy／重复拒绝，做全入口回归并删除 mask。第四批不能把删次数帽后的保护推迟到第五批。

服务端 compact、历史召回、溢出学习窗口、缓存预热、工具结果存储改造不在本批。第三至第五批共同完成策略切换，中间状态不单独作为完整策略发布；每批不留等待下一批拆除的临时开关或双实现。
