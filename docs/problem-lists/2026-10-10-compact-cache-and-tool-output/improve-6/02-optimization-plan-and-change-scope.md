## 2.2 实施阶段

### Stage 1：Web／CLI 子代理压缩标记回放（S1）——已确认

**目标**：Web 子代理会话与 CLI 执行详情一起修复。首次打开、重开、重新 seed 和历史翻页，都能在对应位置看到每次压缩的标记；同一消息不重复，兄弟 scope 不串。连续压缩三次，回看能找到三次记录，仍只显示压缩提示，不展开内部摘要正文。

**做法**：沿用现有 MessageManager、历史读取和标记投影，在读取侧补齐被 run 过滤漏掉的摘要，让标记参与正常分页，而不是只在首页追加一页。

| 读取入口 | 需要覆盖的链路 |
| --- | --- |
| Web 子代理会话 | `adapters/ui-inprocess/subagent-conversation-history.ts` 及 `subagent-conversation.ts` 的 seed／实时合并 |
| CLI 执行详情 | `adapters/ui-inprocess/subagent-views.ts` → `adapters/ui-state/source-session-projection.ts` 的 `executionHistory`；通过既有 SDK reader 消费 |

以上路径位于 `packages/ohbaby-agent/src/`。能共用的筛选与排序规则应共用，避免两端各自维护一套摘要规则；不为此新建通用历史框架。

**读取与分页约束**：

- 只纳入真正的压缩摘要记录，必须同时限定 session 和 scope。不能把所有无 `runId` 消息一并拉入；父用户消息沿用现有处理。
- 同一子代理可以有多轮 execution。标记应结合既有执行记录与消息顺序放回对应分段；CLI 执行详情只显示本次执行对应的标记，不能把同 scope 的全部摘要重复放进每一轮。
- 保持既有排序和游标身份校验。同时间戳使用稳定的消息顺序；run 游标不能直接传给 session 分页，不能取消 scope／run 校验来绕过错误。
- 标记与普通消息一起参与页大小、边界和更多历史的判断。Web 的前后翻页、CLI 的向前加载，以及实时更新后的重新读取都不能漏项、重复或停在同一页；不为 CLI 新增它原本没有的翻页操作。
- 已退场的旧摘要仍显示历史压缩标记。去重依据消息 ID，不能以“同样的提示文案”去掉不同压缩记录。
- 保持旧 execution 的隔离语义；不能因为它缺少 child run，就将同 scope 其他执行的消息归给它。

**改动边界**：修读取侧，保留现有压缩算法和存储结构，不新增表、不改兄弟共享 child session 的结构，也不给摘要伪造 `runId`。原文、摘要正文与用量统计均沿用既有规则。验收见 [04 A 组](./04-test-and-acceptance.md)。

### Stage 3：子代理关键测试补齐（S3）——已确认

复用已有 Lifecycle、Context 集成测试及 fixture，用可控假模型稳定制造边界。先补测试；暴露真实缺陷才最小修复，不另建框架或重写压缩算法。

1. **普通请求溢出恢复**：使用 `isSubagent: true` 与真实 `contextScopeId`，验证同一步最多 force 一次，调用前消耗机会、失败不返还，同一步 snapshot 重入不重置，新一步仍可恢复。再次溢出结束该子代理这一轮，并在共享运行时实际验证父代理和兄弟能继续。
2. **成功占用地板隔离**：A 压缩后，让 B 同样达到自动压缩条件且占用低于 A 的地板，验证 B 仍可压缩；同一 scope 在内容未增长时抑制重复自动压缩。这样才能发现去掉 scope key 的错误。
3. **持续压缩与手动豁免**：同一子代理随内容增长至少三次成功压缩后仍能继续；共用手动压缩路径绕过自动地板。沿用既有入口，不因此新增子代理手动压缩 UI。
4. **实际保留与遗漏内容**：为 Mode A／B 的关键行为补带 scope 的独立预期，检查消息／part ID 集合、工具调用与结果配对、原记录留库。尾段按固定 20K 预算选择并对齐合法边界；最新完整组超过预算、未闭合工具依赖需要向前保留时允许超出，不把 20K 改成硬上限。

优先扩展 `packages/ohbaby-agent/src/core/lifecycle/lifecycle.unit.test.ts`、`core/context/compaction-plan.integration.test.ts` 与 `tests/integration/core/context-subagent-scope.integration.test.ts`。无需复制整套主代理测试或穷举所有参数组合。

验收沿用现有回归，对恢复、scope 隔离等关键行为做少量定向故障注入；实网验证少量完整流程，不依赖真实 API 随机制造溢出。详细场景见 [04 C 组](./04-test-and-acceptance.md)。

## 2.4 接口、迁移与兼容

- **无数据库 schema 迁移**。摘要消息、原文、退场标记、`modelRequests` 的存储形状一律不变。
- **无新事件类型**。S1 只改读取；S5 沿用既有失败状态和结果交付，不新增通知或子代理事件向父聊天 notice 的转发。
- **回退**：本批不改变持久化数据形状，回退代码不需要恢复会话数据。配置清理不自动改写用户文件；用户按新契约移除旧字段后，旧版本仍能加载这些有效角色字段。
- 旧会话（含已退场的旧摘要与已标记 `time.compacted` 的 part）在本批之后仍按原样可读。
- **配置兼容性变化**：旧 agent 配置若含 `model`／`maxTokens`／`temperature`／`topP`，文件加载或自定义配置消费时明确报错，需要移除；LLM 层配置及运行时 `modelId`、reasoning 保留。不提供静默忽略、默认回退或自动迁移。

## 2.5 风险与验收重点

| 风险 | 验证方式 |
| --- | --- |
| 补页把兄弟 scope 的摘要拉进子代理视图 | 构造两个兄弟 scope 各自压缩，断言互不出现（04 A2） |
| 补页与父用户消息的既有处理重复 | 断言子代理历史里同一条消息不出现两次（04 A3） |
| 只补第一页，或把同 scope 的所有标记重复塞进每一轮 | 多页、多轮、多次压缩后逐页核对消息 ID 与归属；覆盖相同时间戳和旧 execution（04 A5～A7） |
| 只修 Web，CLI 仍漏标记 | 分别验证 conversation 与 execution reader，并在两个消费入口确认回放结果（04 A1／A8） |
| 收尾改动误改当前模型预算 | 主、子代理继承当前模型时，预算与实际请求输出设置保持一致（04 B2） |
| 补测写成「跟着实现走」的空断言 | 使用独立预期，并对关键行为做定向故障注入（04 §4.3） |
| 顺手扩大改动面 | 每阶段单独提交，diff 只含本阶段文件 |

## 2.8 后续独立议题

**子代理独立选模型与跨 provider**：2026-10-13 用户确认另开议题，本批只登记，后续再讨论完整方案。

- 起因：基线中的自定义运行时可以传入不同模型名，但预算 fallback 与共享客户端路由不能保证与目标模型匹配，见 [01 §2.3](./01-problem-analysis-and-current-state.md)。本批 X1 关闭静态 `AgentConfig.model` 入口，完整异模型能力仍待此后续议题设计。
- 后续需一起明确：可调用角色与模型选择入口、同 provider／跨 provider 的支持边界，以及普通请求和摘要请求如何共用正确的预算、路由与 reasoning 设置。
- 配置职责遵循本轮用户要求：模型参数归 LLM 配置层，agent 配置保留角色与执行约束，不预设在角色配置里重建模型参数覆盖机制。
- 后续验收必须检查实际请求的模型、地址和协议，不能只验证 `getBudget` 返回值。缓存身份与持久化按实际需要检查，不预设新框架或新存储。
- 本条是议题登记，不是方案批准；improve-6 不提前实现这些能力。
