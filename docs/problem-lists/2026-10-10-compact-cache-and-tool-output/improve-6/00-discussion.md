> 来源：用户提供的 Claude Code 专项审查，以及本轮对 improve-1～5 的代码、既有测试和历史回放探针的复核。外部报告与本轮验证的区别见 §5。

## 1. 先说清楚实例模型（后面所有结论都建立在这上面）

- 主代理与子代理共用同一个 runner、同一套 lifecycle、同一个 ContextManager。区别只在身份：`primary` **不允许**有 `contextScopeId`，`sub` **必须**有；两者都有硬校验（`packages/ohbaby-agent/src/core/agents/context-scope.ts:22-43`）。
- **同一父代理下的所有子代理共用一个 child session**：第一个子代理建会话，后面的复用 `existing[0].sessionId`（`packages/ohbaby-agent/src/agents/subagent-host.ts:858-868`），彼此只靠 `contextScopeId` 区分。单元测试把这条固化成预期（`subagent-host.unit.test.ts:2627`）。
- 因此对 Context 的进程内状态来说，**键必须带 scope**。只按 sessionId 分键，在兄弟子代理之间不安全；`packages/ohbaby-agent/src/utils/scoped-session.ts:14-19` 已经是这个口径。

## 2. 已确认：Context 自己的状态分键是对的

- `calibrationFactors`、`compactionFloors`（以及已删除的 `maskCutoffs`）全部走同一个键生成器，读写都带 scope（`core/context/context-manager.ts:284-286`）。
- `disposeScope` 的参数是必填字符串，不存在「传空把主代理的裸键误删」；`disposeSession` 用前缀精确匹配，`session_1` 不会误伤 `session_10`。
- 现有测试覆盖子代理历史隔离和 scope 清理；不能据此代替成功占用地板的隔离验收。本批 S3 会让兄弟 scope 都达到压缩条件，再验证各自的地板行为。

## 3. 已确认：运行链路与账本没有只接主代理

- Context 按本次 `modelId` 查询预算；当前普通 Web／CLI 子代理继承主模型。自定义运行时传入不同模型名，不代表 provider、地址和协议也会切换，见 [01 §2.3](./01-problem-analysis-and-current-state.md)。
- 摘要请求（材料同源、三行额度、按 session + scope 的缓存身份）、模式 A/B、20K 尾段、单滚动摘要、原子提交、遗漏记录**都没有 `isSubagent` 旁路**。
- `commitCompaction` 的 scope 围栏对子代理同样生效；摘要消息、`modelRequests`、遗漏 metadata 都落在子代理的 child session 和对应 scope 中。
- 子代理的用量被明确排除出父会话的统计（`packages/ohbaby-agent/src/adapters/ui-inprocess.ts:974-982`）；父会话占用不会被子代理的 run 刷新。
- 子代理压缩失败只终结它自己那一轮，不会带崩父代理；父模型通过前景工具结果或后台结果交付获知。

## 7. 边界

- 本批保持上下文收尾范围；子代理独立选模型与跨 provider 不作为本批交付或验收前置。
- 当前占用 UI 继续服务主会话；本批不扩展子代理占用查询、缓存或显示。
- 本批不改变归档、删除与资源清理行为，不新增 Context 归档回收。
- 本批不动「兄弟子代理共用一个 session」这个结构，修复读取，并验证既有 scope 隔离。
- 不给摘要消息伪造 `runId`——手动压缩本来就没有 run，这是已确认的契约。
- 不新增数据库 schema、不建新表、不引入第二套流程或永久锁。
