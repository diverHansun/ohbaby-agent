# Context 目标结构与数据流

> 投影自[议题 02](../02-optimization-plan-and-change-scope.md)。仅描述模块边界，具体类型和代码改动在各 improve 细化。

## 目标与职责边界

Context 让正常与摘要请求消费一致材料，并在需要时用一份滚动摘要替换精确旧段。它保留 LLM 使用工具和选择阅读范围的灵活性，不新增单条／批次输出配额或额度分配器。

同源配置先解析 thinking 与本次输出预算，再由计量和发送共同消费。模型窗口与输出上限不来自内置档位表：删除 `BUILTIN_PROFILE_RULES` 前缀匹配，能力来源为用户显式配置 > provider 探测 > 默认值三层，`maxOutputTokens` 只来自 `llmParams.maxTokens`（清理边界见 [02 §9.3](../02-optimization-plan-and-change-scope.md)）。普通请求输出上限 = `/connect` 的 maxTokens，不设时默认 8192（Anthropic `max_tokens` 必填，无法省略字段）；摘要输出上限独立，用 per-request override 发送、改摘要 maxTokens 不影响缓存身份。Context 负责选择历史与验证压后容量；LLMClient／provider 负责协议字段、请求及真实 usage；MessageStore 负责事务；调度器负责输入与运行状态。Context 不直接承接新的计费服务或通用工作流。

## 数据流

```text
历史 ToolPart／文本／原生状态＋输入投递记录＋同源配置
  → 准备请求、按实际回传内容计量
  → 无需维护则正常发送
  → compact 需要时固定临时计划
  → 正常材料末尾加指令，摘要客户端发请求，用量与终态写日志
  → 有效正文、覆盖关系和计划内压后容量验证
  → MessageStore 原子保存摘要（含 modelRequests）并退场旧 parts
  → 自动重建普通请求继续；手动返回结果
```

失败／Stop 在提交前保留旧历史。自动摘要在允许的内部重试后最终失败，或判定无收益，结束本次运行，等待用户明确重试或继续；若已经提交成功，后来的 Stop 不回滚或误报摘要结果。

摘要总共首次＋一次暂时性网络重试，是每次压缩调用一份的局部计数；三个 provider 建 client 显式 `maxRetries: 0`，把 SDK 隐式重试收进应用层。符合分类的流中断可用剩余机会，不因已有部分正文或 thinking 额外禁重试。两份结果不拼接，半成品不提交，消耗分次记录。SDK 隐式重试的关闭是全局的：普通请求同样不再经 SDK 重试、改由应用层既有策略接管，这是预期改变，普通请求的应用层重试次数与中断回归随 improve-3 更新；普通请求应用层重试策略本身不重新设计。溢出错误标为不可重试，只进 force compact 入口，不吃普通重试预算，与自动触发从结构上错开。

## 内部对象与接口方向

扩展现有 PreparedModelRequest 与请求配置的关系，携带已解析的非敏感发送字段，不复制密钥或完整 client。摘要接口接收 prepared 请求和停止信号，返回有效正文及对应 requestId。

现有 candidate 扩成一次选择的临时计划，含待退场 parts 快照、保留 IDs 与受保护输入；成功摘要请求读取范围、原样保留范围和退场集合分开表达。模式 A 的遗漏是未读且未原样保留的原文，其精确 part IDs 与容量原因挂在摘要正文 part 现有 metadata；复用 `time.compacted` 管退场，不增 `time.dropped` 或新表。仍使用已有摘要 kind 和 parts 标记，不新增历史版本树、摘要链表或 activeSummaryId。

usage 归属挂在摘要消息已有的`modelRequests`上，复用已有消息持久化，不新建用量表、不把 SQL 推入 Context。摘要保存与 parts 退场同事务；没有摘要消息可挂的失败只写日志；持久化或应用失败不重新付费生成。旧会话在首次成功 compact 自然合并全部活动摘要，原文继续留档。

## 选择与预算

近期原文按固定预算 20K 选取，切点对齐完整 LLM 交互边界；最新不可拆组超过 20K 时整组保留。实际回传 reasoning 参与同一预算；未闭合调用及新用户输入不被强行裁掉。

正文≤16K。输出上限分三种：无 thinking 为 16K 正文额度；fixed 为`16K＋已有 B`；effort／adaptive 为`16K 正文＋试行 thinking 预留`、合计 32K。三者都是发送时的输出上限，不是目标长度。真实模型能力与完整请求容量约束最终结果，发送与预留一致，不增加跨协议统一 32K 或半窗硬帽。自动默认 90%，必要时提前保护摘要容量。摘要独立上限用 per-request override 发送、不触碰普通请求，改摘要 maxTokens 不影响缓存身份；模式 B 容量检查里的“本次普通请求输出预留”取全量 config.maxTokens，不套半窗帽子。

生成后不再裁保留段，除非按下面两种容量失败分流需要收缩。摘要输入包含全部有效旧摘要并沿用七节内容要求，最终只有一份活动摘要；新输入按既有投递机制继续，不因摘要读过就被确认为普通请求已处理。

窗口超了分两种，处理不同：**摘要请求本身放不下**时只裁请求副本中的较老完整组再试（占用同两次额度，保护全部活动旧摘要和必留近期内容；成功后遗漏记录与退场同事务提交，未变前缀仍可能命中缓存）；**压完之后仍放不下**时一次按缺口算保留预算再向下收缩保留段，摘要额度不动，下限是最近一个完整交互组。两者都在后端内部完成、本地判定，只有最终失败才报错。详见[02 §5.4](../02-optimization-plan-and-change-scope.md)。

## 退出旧机制

移除常规 prune-only、mask、缩水输入却扩大退场范围、短 system 兜底、内容修正重试和每次运行的压缩进入次数上限。保留 parts 退场操作本身，作为成功摘要事务的一部分。

第三批完整摘要请求与 90%默认线、实际容量提前保护同时接通；同批取消共用入口的前置 prune／prune-only，沿引用链清理专属实现、配置／常量、事件／类型／导出、SDK／CLI／Web 消费和旧策略测试，不留手动专用旧分支、临时开关或无操作壳。保留 `time.compacted` 与摘要共用事务、工具配对、旧记录读取及有效的失败回归。准备到摘要发送期间的旧正文不被裁改，失败／提交前 Stop 不留 prune 退场；不能只比较两份已经裁过的请求。

第四批完成覆盖和事务，并同时接上自动最终失败终止运行、删除次数上限与抖动锁，以无进展地板替代：成功压缩提交后压后占用记为地板，自动触发仅在占用严格大于地板时允许再压，手动与溢出恢复不受地板限制；复用已有运行结束链路，不新增锁、计数器或开关。溢出恢复是 force compact 一次：一次性标志在调用压缩之前置位、失败也不回滚，compact 成功后重发的普通请求不挂恢复钩子、二次溢出直接结束运行；溢出学习窗口本轮不做。第五批贯通全部入口、回归失败终止并清扫剩余旧机制，不补交第三批的 prune 清理；不将不完整中间状态单独发布。阶段测试见[03](./03-test-criteria.md)。
