大多数情况就是 90%，只有 128K 这类小窗口会提前一点，保证分叉请求放得下。

### 我建议的自动压缩流程

```text
每个 step 发请求前估算占用
  │
  ├─ 没到触发点 → 照常发请求（不清理、不改历史）
  │
  └─ 到了触发点
       │
       ① 拿「下一次正常请求」+ 末尾总结指令 → 生成摘要（不先清理）
       │    失败：分叉重试 1 次 → 退回老路径
       │
       ② 新历史 = 系统和工具（不变）+ 摘要 + 最近一段原文（≤ 20% 窗口，按轮对齐）
       │
       ③ 检查压完的大小
       │    超过目标（比如 50% 窗口）→ 把保留段缩到「最新用户消息 + 当前这一轮」
       │
       ④ 用新历史发出这次请求，任务接着做
```

几个要点：

1. **去掉「只清理不摘要」这条路**：到点就摘要。清理不再作为单独的结局。
2. **压完要远低于阈值**：保留段最多 20%，加上摘要和系统工具，大约三四成，离 90% 很远，不会马上又触发。这就是「滞回」：触发线高，压完的线低，中间留一大段空间。
3. **防止反复失败**：学 claude-code，连续失败 3 次就暂停自动压缩，不要每一步都去试。ohbaby 现有的「每轮最多压 2 次」和「省得太少就锁住」可以留着当保险。
4. **压完还是放不下**：服务端报上下文超长时，走现有的强制压缩路径。
5. **工具调用中途也能压**：保留段里包含当前这一轮，摘要指令要求写清「正在做什么、做到哪一步、下一步是什么」，压完直接继续。

有一个数要你拍板：压完的目标上限定多少？我建议 50% 窗口，超过就缩保留段。也可以更松，比如 60%。你倾向哪个？
