# 整体方案与五批实施路线

> 更新：2026-10-11；依据[00 中的确认](./00-discussion.md)与[01 中的问题](./01-problem-analysis-and-current-state.md)。
> 本文给出整体规则和依赖。各 improve 后续按当时代码细化本批规划、实施和验收，不在本轮改业务代码。
> 模块视角见[context-design/02](./context-design/02-change-spec.md)，验收见[04](./04-test-and-acceptance.md)。

## 1. 总体流程

复用正常请求的准备路径。窗口需要整理时，用它的完整材料在末尾追加摘要指令；生成有效摘要后，一次性切换活动历史。工具结果使用既有存储和投影，不再随窗口压力改写旧正文。

```text
已有消息、工具结果、原生状态、待交付输入、同源模型配置
  → 准备本次请求材料，解析输出预算与 thinking
  → 正常容量检查／90%默认线／摘要容量保护
      无需 compact → 发送普通请求
      需要 compact → 固定覆盖范围和原文尾段
        → 同一请求材料＋末尾摘要指令
        → 摘要请求发送前先分清容量不够的病因（§5.4）：
             模式 A 摘要请求放不下 → 副本裁掉较老完整组再试，保护旧摘要与必留近期内容（同两次额度，成功后记录遗漏）
             模式 B 压后仍放不下 → 向下收缩保留段，摘要额度不动
        → 摘要请求（首次＋至多一次暂时性网络重试；成功那次的用量随摘要消息落库，失败／无结果只写日志）
        → 检查有效正文、覆盖范围与计划内压后请求
        → 同一事务：存新摘要（连同它的 modelRequests）＋旧 parts 退场
        → 自动：重新准备普通请求并继续；手动：报告完成
      失败或 Stop → 不切换历史；自动运行结束，会话与结果保留
```

摘要之后的模型输入是固定 system／tools＋一份新摘要＋保留原文，再加入待首次正常交付及压缩期间新到的用户输入。不能把“摘要＋尾段”误解为不再含系统、工具或新输入。

## 2. 减少重复机制

| 问题 | 采用 | 不引入 |
| --- | --- | --- |
| 摘要前缀改变 | 同源 prepared 请求，末尾追加指令 | 第二套短 system、无 tools 兜底装配器 |
| thinking／输出／输入口径不同 | 现有 resolver 和 TokenCounter，共享最终结果 | 独立 thinking 计数服务、effort 到 token 预测器 |
| 工具历史反复变形 | 现有 ToolPart、分页／限长和纯投影 | 新 8K／20K 配额、均分器、第二份预览生命周期 |
| 多份摘要与退场范围不一致 | 一份滚动摘要、临时计划、现有 parts 事务 | 摘要链表、activeSummaryId、历史版本服务 |
| 多层重复请求 | 一处重试所有者，失败终止本次运行 | 换提示词重试、自动升额重试、跨入口另获额度 |

## 3. 请求材料与缓存

### 3.1 准备一次，测量和发送共用

扩展现有 PreparedModelRequest 周边契约，复用 InterfaceProviderRequest 已有字段：messages、tools、model／来源、温度、ResolvedReasoning、最终 maxTokens、purpose、session／scope 和适用 cache 配置，保留 inputIds。具体类型组合在 improve-1／3 细化，不复制客户端、密钥或整份配置，不持久化完整请求体。

摘要与正常请求使用同源配置，但分别解析用途需要的总输出额度；不要先让普通`/connect maxoutput`限制摘要，再尝试补救。thinking 意图和已确定 B 保持一致，不能因摘要额度变化在底层暗中降档。发送层消费解析结果，避免再次读取变化中的配置重新算一遍。

“共享前缀”的基准是同一份材料将要发出的正常请求，不是要求与上一次已发请求完整相等。新增模型回复、工具结果和用户消息正常追加，原有共享部分不能被 prune／mask 改写。

**improve-3 接入完整摘要请求时，同批移除前置 prune 和 prune-only 返回。**准备普通请求到发出摘要请求之间，不先让旧工具结果退场，也不另做摘要专用正文截断。模式 A 仅作为 §5.4 已确认的容量兜底，不能成为日常裁剪入口。裁剪会改变第一处差异之后的旧前缀，之前未变的内容仍可能命中；缓存是否命中最终看接口规则与真实 usage。

不能只把“裁剪后的普通请求”和“裁剪后的摘要请求”相互比较就认定 C1 通过；还要证明准备与摘要发送之间的已有消息、工具正文及持久化退场标记没有被前置 prune 改动。该路径失去用途的实现和消费方在第 3 批一起清理，范围见 §9.2。

### 3.2 三协议与缓存策略

沿用已有 Chat Completions、Responses、Anthropic 转换器及已核实的端点能力。Chat 输出字段按模型／端点选择`max_tokens`或`max_completion_tokens`；Responses 使用其输出字段；Anthropic 使用对应总输出与 thinking 字段。不把不同兼容端点全局当成官方接口。

purpose 仍为 context-summary。共享适用的会话／scope 缓存身份与正常请求策略，保留 system、tools、消息及原生状态顺序。需要显式缓存标记的端点在稳定前缀、真实历史边界设置适用标记，不把最后追加的摘要指令误当既有命中边界；遵循既有顶层／分块策略和数量限制，不统一强加不支持的字段。

tools 和原 tool_choice 保持正常请求语义，由摘要指令要求只输出总结。摘要路径不接工具执行器；收到工具调用就失败。缓存验证比较最终请求体和真实 usage，不能用“我们传了同一个 key”代替验证。

压后首请求自然建立新缓存。没有预热、冷热分流或服务端 compact 新分支。

## 4. 预算、计数与触发

### 4.1 三种输出语义

最终摘要正文≤16K，包括确定性追加的文件操作信息。这个值是已确认的正文上限，不是目标长度，也不是所有协议的 API 总输出。

已知要由宿主追加的文字，在生成前就计入这份正文额度，为模型正文留出剩余空间，不能等模型写满后再追加造成确定性超限。复用同一计数和预算解析，不另设文件操作配额；具体接线在 improve-4 完成。

| 已解析 thinking 模式 | 摘要申请的输出上限 | 说明 |
| --- | --- | --- |
| 不生成 thinking | 16K 正文额度 | 受真实模型输出能力约束 |
| 已有固定 B | 16K＋B | 借鉴 Pi，再受真实模型输出能力约束；保持 B 不变，不叠加全局 32K 帽 |
| 只有 effort／adaptive | 16K 正文＋试行 thinking 预留，合计 32K | 不猜 B、不声称 thinking 占 16K；真实样本可用于后续调整，不自动升额重试 |

三行给出的都是发送时的输出上限（`max_tokens` 一类），不是要求模型写满的长度，也不是目标长度。摘要实际写多长由模型自己决定，宿主只保证不因此超限。32K 与上一行的 16K＋B 是同一个形状（正文额度＋thinking 额度），只是 B 已知、effort 下未知，所以用试行预留代替。

保留现有预算解析入口，分清真实模型能力、普通用户输出偏好和本次摘要额度。模型真实能力不应由`/connect`普通偏好冒充；能力未知或来源不可靠时沿用既有能力发现／验证路径并明确状态，不再造一套模型注册服务。

最终发送额度与容量预留必须来自同一结果，并满足协议与完整输入容量要求。现有“最多约半窗预留”不能继续造成只预留小值却发送大值，也不新增为产品硬限制。B 必须保持合法；例如实际能力不大于 B 时，发送前报告不兼容，不能默默降低 B。

不会因为 B 达到 32K 就拒绝请求。例：B=32K、模型与窗口允许时，摘要可申请 48K；正文仍不超过 16K。也不直接为所有模型申请其最大输出，避免无依据地占用过多预留空间。

### 4.2 计数

复用现有 TokenCounter 和最终消息投影。只有实际回传的 reasoning／原生状态进入请求及尾段估算；显示用 reasoning 不重复算。兼容内存文字路径、数据库原生状态和 opaque 估算使用同一来源口径，保留不确定性标记。

实际 usage 独立保存：reasoning 是 output 子项，cache 是 input 分类；缺失明细保持缺失，不能填 0 或与总量重复相加。摘要 usage 不能拿来校准另一份普通请求的输入估算。

### 4.3 自动触发与容量保护

90%按完整窗口占用计算。发送每次普通请求前，用已准备材料和实际输出预算做现有容量检查；为摘要追加指令及实际输出留出必要空间，确有需要时提前 compact。

90%不保证每次都等到。比如 200K 窗口预留 32K 摘要总输出后，输入空间已少于 168K，容量检查自然会早于 90%起作用。实际位置由最终预算和材料计算，不把示例换成新的固定百分比。

不增加第二条固定比例、增长预测、工具批次配额或压后 50%目标。容量保护不是保证永不超窗：单个巨大用户输入或工具结果仍可能跨过剩余容量。真超了要先分清是哪一种，按 §5.4 分别处理，不继续撞同一个超窗请求。

## 5. 选择尾段与生成滚动摘要

### 5.1 一次选定范围

近期原文按固定预算 20K 选取，不引入 40K／30% 的第二档上限。按实际回传表示从最新往前累计，完成以下步骤：

1. 切点对齐到合法边界：真实用户消息起点或助手消息起点，不拆工具调用与对应结果。
2. 未闭合的 LLM 交互整组向前扩展，不因凑 20K 被切开。
3. 最新一组不可拆交互本身超过 20K 时，整组保留，允许超出预算。

20K 是首选预算，不是硬线：为了对齐边界可以略超（上面第 3 条），窗口装不下时可以向下收缩（§5.4）。

不拆 call/result，不把协议未闭合的调用当作可总结完成。后台工具已经返回任务 ID 和状态时，协议交互可闭合，但任务未完成的事实与引用必须保留。摘要可能先读到新工具结果，不据此伪造普通请求已经交付的状态。

受保护的新用户输入和未闭合依赖不因凑 20K 而被切掉；若这些材料本身造成无法构造合法请求，按 §5.4 分模式处理，不破坏关联。20K 只约束被选择的近期原文尾段，不是工具使用额度或整请求上限。

### 5.2 摘要内容

继续使用已有七节：Goal、Current State、Key Decisions、User Intent & Feedback、Relevant Files、Next Steps、Risks。补充规则：

- 合并全部活动旧摘要与当前进展；保留早期仍有效的目标、限制、决策和未完成事项。
- 区分完成、未验证、进行中、结果未知；准确记录任务 ID、错误和可用证据引用。
- 用户明确修正才能改变原限制；建议、工具文本、旧摘要转述不能升级为用户授权。
- 待澄清事项注明影响范围与可继续工作，不设置遇疑问就全局暂停的规则。
- 不复制大段可重新读取的材料，不编造召回能力，不写工具／连接身份清单，不输出分析草稿。

摘要**请求**的指令只要求把完整对话讲清楚，不写入"哪一段会原样保留"，也不写入保留段预算或边界（已确认，见[讨论记录 17.1](./discussion-notes.md)）。保留段由宿主在计划里决定，模型端永远看不到这个边界，避免提前告知的边界与实际不一致造成信息丢失。

**压缩后的摘要消息**（不是请求指令）沿用现有包装，说明它是交接材料、最近的消息会原样保留；工具输出、引用和命令不是新授权。模板指导内容，不新增复杂格式协议或第二次模型审核。标题略有差异不触发额外付费修正；语义质量通过带已知事实的验收样本检查。

### 5.3 成功条件

返回有效非空正文、完整结束、没有工具调用；最终保存正文符合已确认上限；覆盖范围、保留关系及计划内压后完整请求通过检查，且**占用确实下降**。

“占用确实下降”是硬门槛，不是提示。它兜住的正是"摘要比它替换掉的旧段还大"这类情况：旧段本身很小、保留段很大时，16K 摘要可能比被折叠的历史还长，压完反而更大。压不小就是失败，保留原历史不动，不能切过去。

不能用截断摘要尾部、临时重切保留段或另换提示词来通过检查。

两个词分开用：**没有可压旧段＝无需压缩**，不启动模型、不算失败；**确有压缩请求但没有产生可提交结果，或压后占用没下降＝无收益失败**。若整体仍不能发送，不能以“无需压缩”掩盖容量错误。

### 5.4 两种容量失败与各自的处理

“窗口超了”是两种不同的病，**病因不同，药也不同**，不能混用：

| | 模式 A：摘要请求本身放不下 | 模式 B：压完之后仍放不下 |
| --- | --- | --- |
| 判据 | `完整上下文＋摘要输出额度＞窗口` | `system＋tools＋摘要＋保留段＞窗口` |
| 何时出现 | 单个巨大用户输入或工具结果一步跨过容量余量；容量保护没能提前触发 | 小窗口下 `system＋tools` 本身就占掉大半，压后仍无余量 |
| 手段 | **丢弃最老的 API 请求组**后重试 | **向下收缩保留段** |
| 保留段有没有用 | 没有。摘要请求发的就是完整上下文，保留段是它的后缀，缩了也省不下 | 有用，这是唯一的杠杆 |
| 丢弃历史头有没有用 | 有用 | 没有。下一个普通请求的输入与摘要读过多少历史无关 |

**模式 A 的做法**（问题一已确认，见[讨论记录 §17.10](./discussion-notes.md)）：

1. 只裁摘要请求的临时副本。按容量缺口从较老原文的完整 API 交互组开始移除，按估算一次裁够；不把估算当成服务端必然接受的保证。
2. 保护全部活动旧摘要、受保护的新输入、未闭合依赖和必须留下的近期内容；工具调用与结果整组处理。旧摘要必须进入本次摘要请求，成功后由新摘要接替，不永久累积。受保护内容之外已无可裁材料而请求仍放不下，直接失败。
3. 后端内部重试，占用 §7 的两次实际请求总额度，不单开 PTL 额度。裁剪后的请求仍走既有协议合法性检查；必要的开头标记不能替代工具配对检查。
4. 区分成功请求实际读到的范围、压后原样保留的范围和最终退场范围。**遗漏＝未进入成功摘要请求、压后也未原样留下的原文**；不能把“从摘要请求移除”直接等同于“最终遗漏”。退场的未读 parts 必须全部有模式 A 的遗漏记录，不能沿用原范围静默退场。
5. 复用 `time.compacted` 作为活动上下文退场标记。遗漏的精确 part IDs 和容量原因写入新摘要正文 part 的现有 metadata，不增加 `time.dropped`、新表或第二套退场状态。宿主附加一句“部分较早原文因容量限制未纳入本次摘要”，与其他追加内容一起计入正文上限；完成提示也简短告知。原文仍存数据库，不承诺模型已有回查能力。
6. 摘要成功、压后完整请求与覆盖关系检查通过，才在同一个 `commitCompaction` 事务里保存新摘要、遗漏记录并标记精确 parts 退场。失败、取消或提交冲突不应用本次裁剪。
7. 裁剪点之后的旧对话前缀无法照原样复用；此前未变的 system／tools 和旧摘要仍可能命中缓存。实际结果依接口规则和 usage 判断，不写“必然全部 cache miss”。

**模式 B 的做法**（借鉴 Pi 的固定预算、Reasonix 的 `planCompaction` 重测量循环；Kimi 的 `preShrinkHistoryToWindowBudget` 裁的是摘要输入，不能作为模式 B 的依据）：

1. 保留段按同样三步从最新往前选取，但预算从 20K 起**向下收缩**，直到 `system＋tools＋摘要＋保留段` 装得下。
2. 收缩仍守边界规则：对齐到真实用户消息起点或助手消息起点，不拆工具调用与结果配对。
3. **摘要额度不动**。16K 正文是新摘要的质量底线，宁可少留原文也不压正文。
4. 收缩有下限，不能缩到没有原文尾段——那等于变相把最近的消息也交给摘要。到下限仍装不下则走失败。
5. 收缩是事后决定保留多少原文，摘要请求体一个字节都不变（保留段边界本来就不进请求），**因此不影响缓存命中**。

两条路都在后端内部完成；只有最终失败才让前端报错。失败时按 §7 结束本次自动运行、保留会话与已完成工具结果，并给出可执行的提示（清理当前会话或新开会话），不是干巴巴一条错误。

## 6. 数据流、事务与用量归属

### 6.1 临时计划与记录

复用现有候选对象保存一次压缩的 compactionId、prepared 请求、待退场 parts 快照、保留 IDs 和受保护 inputIds。成功摘要请求实际读取的材料、压后保留集合与真正退场集合分开表达；模式 A 的遗漏 IDs 从这些集合计算，随摘要正文 part 的 metadata 保存。生成、压后检查和提交都消费同一选择，不各自重新选边界。

保留段由这个计划对象在生成前选定一次，作为唯一来源被生成、压后检查和提交共用。若因超窗、无收益等原因必须调整，由同一计划对象更新并记录，不新增第二处选择。指令从未把该边界告知模型，所以调整不会造成"模型按错误边界省略信息"——这正是保留段不进摘要指令的原因。提交时不再临时重切。

摘要客户端从“history 到 string”改为消费 prepared 请求，返回有效正文及产生它的 requestId。

摘要用量不新建表，也不写 SQL。成功的摘要在数据库里就是一条已有 kind 的 AssistantMessage，复用它已有的`modelRequests`记录这次`context-summary`请求（requestId、purpose、attempt、起止时间、outcome），与摘要正文同一个事务落库。现有`ModelRequestRecord`没有 usage 字段；确实需要时只在既有记录类型上补一个可选 usage，不新建计费服务，不伪造普通 run 或对话消息，也不把普通请求必填所有权改成可选。

请求失败、被停止或判定无收益而没有摘要消息可挂时，只写一行日志（requestId、可用 usage、结束原因），不为留档单独造记录容器。

### 6.2 提交顺序

通过候选检查后，在现有 commitCompaction 事务内同时保存新摘要（连同它的 modelRequests、正文 part metadata 中的遗漏记录）并标记精确旧 parts 退场。

“请求完成”与“摘要应用”仍是两个事实，但两者都落在同一条摘要消息上，不再单独关联一张尝试表。数据库写失败不能触发重发模型；应用失败保留旧历史，记录失败也不能编造零用量。会话删除沿用外键／现有清理，不能用迟到回调重建已删除会话。

事务复用已有 parts 比较，并核对相关完整组与旧活动摘要未改变。不引入全会话版本号锁住新增输入，也不按某个时间点之前的所有消息批量退场。

### 6.3 新输入、Stop 与旧会话

压缩期间的新输入留给现有调度器。摘要读过准备时的受保护输入不代表普通请求已处理，不调用普通请求的交付确认；提交只作用于计划中的精确 IDs。

成功切换后重新读取历史和待交付输入，准备下一份正常请求并再次检查容量。若新输入随后导致容量不足，报告该次请求的问题；已成功提交的摘要不能被误报为从未成功。

提交前 Stop 不应用候选；提交后 Stop 保留已经成功的事实并停止后续运行。继续使用现有停止信号，不增加 compact 专用取消系统。未完成工具继续按已有生命周期处理，不因摘要改写其执行状态。

旧会话第一次成功 compact 时读取全部活动旧摘要，将其与覆盖的旧段一起退场，只留新摘要。原记录继续存库，hasSummary 依据活动摘要判断；无后台全文迁移或摘要链表。

### 6.4 压缩完成后的界面

复用现有组件，不新做用量界面，也不新建统计。进行中沿用现有 spinner 文案加`Compacting`，不照搬参考项目的渐近进度条。完成后在消息流插一条暗色单行，手动与自动统一都给压前／压后占用。ohbaby 的占用本来就是本地估算口径，所以提交后立即刷新 footer 与占用面板，不必像参考项目那样等下一轮真实 usage；但要写明这是估算值，下一轮真实响应回来后按既有路径校正。若本次模式 A 有遗漏，完成提示补充“部分较早原文未纳入摘要”，不新增界面。摘要请求自身的消耗不进占用显示，也不混进下一份普通请求的输入估算，只在日志里。

现有落点已经齐了：`core/context/context-window-usage.ts`的`updateFromContextUsage(sessionId, usage, composition)`就是入口；`composition`里的`summarized-conversation`已经在`core/context/token-estimation.ts:183`计算，并经`adapters/ui-runtime/run-stream-adapter.ts:595`送到 SDK。所以这一步是“提交后按新投影再调一次，并把结果送到已有渲染组件”，不是新建统计口径。

参考做法见[03 §5.1](./03-reference-projects.md)：claude-code 只在手动`/compact`的完成消息里给`Context: ~X → ~Y tokens`，自动路径只插`✻ Conversation compacted`；opencode 只留一个` Compaction `分隔框，既无进行中提示也无完成 toast。两家压缩后都不立即重算占用，都在等下一轮真实 usage。

## 7. 手动、自动、重试与失败

后端通过已有会话／scope 运行状态与独占机制判断 busy 和重复请求，不只依赖按钮禁用。手动仅空闲执行，不暗中停止正在工作的工具，不新建等待队列；自动在安全的模型请求边界进入同一过程。

保留现有暂时性错误分类和退避，摘要至多首次＋一次网络重试。流中断若确定属于可重试网络故障，即使已收到部分正文或 thinking，也可用剩余的一次机会按相同材料和配置重试；前一次半成品不拼接、不提交，两次消耗分别记录。Stop、length、工具调用或协议错误不因此变成可重试故障。

**模式 A 的丢弃历史头重试占用同一个两次总额度**，不单开 PTL 重试额度。理由：按 §5.4 一次丢够即可，不需要多轮试探，也就没必要为用户已确认的两次上限开例外。若这次机会用掉后仍失败，直接走下面的最终失败，不继续撞同一个超窗请求。

SDK 对摘要请求不得另行重试；improve-3 要将用途对应的重试设置传到实际 provider 调用，不能只约束外层循环。现有普通流在收到内容后禁止重发的规则，不全局改动；摘要按自身“没有提交历史、不会执行工具”的语义收拢重试。

空正文、length、意外工具调用、协议错误、容量不足、无收益（产生了摘要但没缩小）或提交失败，均不得走“更简短提示词”、无工具旧摘要路径或自动升额恢复。

用户已确认最终失败后结束本次自动运行，保留会话、历史与已完成工具结果。自动／overflow／force 不能在同一运行里再开新摘要额度；用户明确重试或继续后才进入新的运行。普通请求已经被服务端判超窗时，只有 compact 成功、请求有实质缩小且容量检查通过，才能重发普通请求。

删除压缩次数上限（现有代码是每次运行内的“进入次数”上限，不看该次成败）与无收益抖动锁，不增加永久失败锁、定时解锁或输入指纹系统。无收益判定为最终失败并结束本次自动运行，不通过重复成功计数来控制失败。**上述失败终止与删除次数上限、抖动锁在 improve-4 同批完成**，复用已有运行结束机制，不新增锁、计数器或开关。improve-5 负责各入口贯通与回归，不再首次补上失败终止。

## 8. 工具结果的稳定性

复用现有 ToolPart 正文与 metadata、工具分页／必要限长和 serializer。工具完成后照常持久化与更新 UI；后续投影不按窗口比例再截断、遮罩或省略已发送结果。正常请求和摘要共用同一投影。

不新增统一单条／批次 token 额度，不均分并行结果，不新增预览的创建／发送／冻结状态。已有工具原始捕获不完整时如实标注；已有可读结果文件继续使用，不强行让所有工具建立新落盘服务。

Read 继续位置与实际交付一致；子代理只将实际回传给主代理的结果计入主上下文。稳定性缺口以测试和实际代码为依据修复，不扩大到独立 Shell／Bash 执行改造。

### 9.2 improve-3 的 prune 清理边界

取消共用压缩入口的前置 prune 及 prune-only 返回，不另留手动专用副本或临时开关。第 3 批顺着引用关系清理，不把已失用代码留给第 5 批：

- 配置与事件：`PRUNE_*` 常量、`core/context/index.ts` 再导出、`ContextEvent.Pruned` 及 `bus/event-catalog.ts` 登记；确认读取用途后同步调整类型和 schema。
- 消费方：`adapters/ui-runtime/prompt-context.ts`、SDK 的 compact 返回类型与导出、CLI／Web 的 `pruned` 渲染分支，同批更新协议契约和相关测试，避免仅删生产方却留假状态。必要的旧数据读取兼容按真实读取链保留并说明理由，不保留可执行的旧 prune 路径。

测试随语义改写：删除仅证明旧 prune 策略的用例，将仍有效的原子性、停止、scope、配对和恢复断言移到新流程。核对手动／自动／overflow 及子代理 scope 的调用链，执行受影响的类型检查、契约和回归测试。mask 是另一条机制，按 §3.1 保证新请求不经过压力改写；不借本条扩大为无关清扫。第 5 批只做剩余机制清理与整体复核。

## 10. 迁移、回退与范围

业务消息保留已有 kind 和 parts 标记。本轮不新增用量表；若后续为`ModelRequestRecord`补可选 usage，按已有 metadata 结构做兼容读取，原历史不物理清除。具体迁移与回退命令由相应 improve 按实际变更写明，不能沿用旧草案“没有数据库迁移、直接退代码就行”的断言。
