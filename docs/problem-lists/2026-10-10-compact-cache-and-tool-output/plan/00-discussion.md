# 讨论结论与已确认边界

> 更新：2026-10-11。来源为本会话用户确认；过程见[讨论记录](./discussion-notes.md)，方案见[02](./02-optimization-plan-and-change-scope.md)。
> 本文记录整体方向，后续 improve 文档细化实施。业务代码尚未改变。

## 1. 目标与设计取向

用户要求摘要发生在接近满窗口时，尽可能复用正常请求已有缓存；同时让压缩真正腾出空间，保留任务连续性，避免未读信息被错误移除。

用户明确纠正：

> 精细化是指问题和需求的精细化。

> 尽量不要做过多上下文大小/token 的具体限制，避免把 context 管理模块变得过于机械化。

落实为：复用已有工具、请求准备、计数、原生状态、调度和数据库事务；保留 LLM 选择工具与阅读范围的灵活性。数值仅保留已确认的摘要／保留段策略及真实模型、接口容量所必需的约束，不再增加分配器、增长预测或多套降级规则。

## 2. 摘要与缓存

- 摘要基于同一份材料将要发出的正常请求，保持 system、tools、既有消息顺序、原生状态、模型／端点、已解析 thinking 和适用缓存身份，在末尾追加摘要指令。
- 仍使用`context-summary`用途，独立记录消耗，不伪装成普通请求。不得为了摘要临时换短 system、去掉 tools 或降低 thinking。摘要输入默认完整，仅在 §6 模式 A 的容量兜底中允许裁剪。
- improve-3 接入完整摘要请求时，同批取消前置 prune 和 prune-only 返回；不在摘要前改写已发送的旧工具结果。改动位置之后的原前缀复用会被破坏，此前未变的前缀仍可能命中，不能把裁剪说成整份请求必然 miss。失去用途的调用、配置、导出、事件、消费分支和旧测试同批清理，不留临时开关或无操作兼容壳；保留共用退场事务、旧会话读取与仍有效的失败回归。
- 摘要路径只接收摘要，不执行模型返回的工具调用。有效摘要成功提交后才替换活动历史。
- 压后第一次正常请求自然建立新缓存，不额外预热。旧历史被摘要替换后，不要求旧历史缓存完整复用。
- 缓存只能省重复输入费用，不能减少上下文占用；命中受提供商能力、写入边界和有效期影响，不保证每次命中。

## 3. 一份滚动摘要与原文保留

- 模型上下文只保留一份更新后的摘要；旧摘要和原始记录继续存在数据库中。本轮不建设旧信息召回系统。
- 首次迁移时合并全部仍有效的旧摘要，而非只取最后一份。新摘要继承早期仍有效的要求、决策、证据、进展和未完成工作。
- 新信息可修正旧事实，不能无依据改写用户限制或授权。保留冲突、未知和受影响事项，不统一要求恢复后的 agent 停止工具调用或立即发问。
- 摘要正文不超过 16K，且包含宿主追加的文件操作信息；这是上限，不是必须写满的长度。不再要求摘要占原历史 15%～30%。
- 最近原文按固定预算 20K 选取，不按窗口比例，不设 40K／30% 的第二档上限；需要回传的 reasoning 一起计入这段预算，不额外赠送 thinking 额度。
- 从最新往前累计到约 20K，切点对齐到合法边界（真实用户消息起点或助手消息起点），不拆工具调用与对应结果；未闭合的调用整组向前扩展。不另造档位。
- 最新一组不可拆交互本身超过 20K 时，整组保留，允许超出预算；不整组交给摘要，也不保留空的原文尾段。未完成调用和未首次正常交付的新用户输入仍受保护。
- 20K 是**首选预算，不是硬线**。窗口实在装不下时（`system＋tools＋摘要＋保留段＞窗口`），按同样的边界对齐规则**向下收缩保留段**，直到装得下或到下限为止。收缩只动保留段，**不动摘要额度**。见 [02 §5.4](./02-optimization-plan-and-change-scope.md)。
- 未进入成功摘要请求的历史不能冒充已被总结；模式 A 允许较早原文因容量退场，但必须显式记录遗漏。复用现有 `time.compacted` 表示退场，不以该字段证明摘要覆盖。除上述装不下的收缩外，确定保留段后不再为了通过压后检查重新裁剪它。

## 4. 输出预算、计数与用量

- reasoning 与正文复用现有计数模块，按实际会回传的内容计数；显示文本不等于必然回传，opaque 估算不能冒充精确用量。
- 摘要的实际 usage 和 cache 结果挂在摘要那条消息的`modelRequests`上，与摘要同事务提交，复用已有结构，不新建用量表、不为其写 SQL。失败、被停止或判定无收益而没有摘要消息时，只写一行日志，不为留档单独造容器。
- 摘要总输出独立于`/connect`普通输出偏好；thinking 控制与总输出分开，数字预算由内部配置处理，不新增用户设置。
- 最新接受的路线：无 thinking 以 16K 正文额度为申请基础；fixed thinking 按`16K＋既有 B`申请，再受真实模型输出能力约束；effort／adaptive 用`16K 正文＋试行 thinking 预留`，合计 32K，不将 32K 套成所有协议硬帽。这三个都是发送时的输出上限，不是目标长度，摘要实际写多长由模型自行决定。
- 保持已解析 thinking 不变，不把固定 thinking 统一限制为 16K。发送参数与容量检查用同一个最终预算结果。32K 是本项目试行值，没有参考项目共同最优值的含义。
- 前端只做必要的轻量调整，全部复用现有组件：压缩中沿用 spinner 加`Compacting`；完成后在消息流插一条暗色单行给出压前／压后占用（手动自动一致）；提交后立即刷新 footer 与占用面板的比例，`composition` 里已有的`summarized-conversation`自然生效。立即刷新用的是本地估算，下一轮真实 usage 回来后按既有路径校正。不新做用量界面，摘要请求自身消耗不进占用显示，也不混进下一份普通请求的输入估算。

## 5. 工具结果

- 调用关系不变，错误与未完成状态不丢，已发送正文及引用保持稳定。
- 复用工具本身已有分页／必要限长、ToolPart 持久化及现有模型投影。正常请求和摘要请求使用同一条路径。
- 撤回新增统一单条 8K／批次 20K 额度、共同上限分配算法以及为此新增的预览状态。批次变大由完整容量检查和 compact 处理，不把保留段预算误当工具使用额度。
- 不承诺所有工具都保存了完整原始输出。引用必须真实可读，分页必须符合实际返回内容；不虚构数据库召回能力。

## 6. 触发、重试和失败行为

- 自动压缩默认 90%完整窗口占用；复用容量检查，在输出预算与摘要指令确实需要时提前。较小窗口可能通常由容量检查提前触发，90%不保证每次都会等到；不另设固定 80%线或增长预测。
- 手动和自动共用压缩过程，仅触发方式不同。手动仅空闲时执行，运行中简单提示忙碌，不自动停止 Bash 或加入新维护队列。
- 压缩中不能重复发起，也不能自动取消；只有会话已有暂停／停止操作可以中断。自动成功后继续原任务；手动成功只报告结果，不额外发起普通请求。
- 窗口超了要**先分清是哪一种**，两种情况处理不同（详见 [02 §5.4](./02-optimization-plan-and-change-scope.md)）。**模式 A：摘要请求本身放不下**（完整上下文＋输出额度＞窗口）→ 在请求副本中裁掉较老的完整交互组后重试，保住活动旧摘要和必须留下的近期内容。**模式 B：压完之后仍放不下**（`system＋tools＋摘要＋保留段＞窗口`）→ 向下收缩保留段。
- 总共最多两次实际请求：首次＋一次暂时性网络故障重试。**丢弃历史头后的重试属于这两次之内**，不单开额度；丢掉历史头、按超出量一次丢够，一次即可。流中断若属于这类网络故障，仍可使用剩余的一次机会；部分正文或 thinking 不作为额外禁重试条件，半成品不提交。各层共享上限。丢弃历史头及收缩保留段都在后端内部完成，未走到最终失败之前不在前端报错。
- 模式 A 是**有损兜底**：只在摘要请求放不下时使用，保护全部活动旧摘要、受保护的新输入及必须留下的近期内容，不拆工具调用与结果。可裁原文耗尽仍放不下则失败。只有摘要成功且压后检查通过，才原子提交新摘要、精确退场范围及遗漏记录；原始记录留库。
- 遗漏指“未进入成功摘要请求、压后也未原样保留”的原文；其 part IDs 和容量原因写入新摘要正文 part 现有 metadata，不新建表或 `time.dropped`。宿主附加一句遗漏说明，完成提示也简短告知；不承诺尚未建设的召回能力。
- 模式 A 改变裁剪位置之后的对话前缀；此前未变的 system／tools 和旧摘要仍可能命中缓存，按真实 usage 记录，不宣称必然全部 miss。
- 用户最新确认：自动摘要在允许的重试后仍失败，结束本次自动运行，保留会话、全部历史和已完成工具结果，等待用户重试或继续。不会把已经完成的工具重新当成未执行。
- 成功后才一次性切换历史。失败、停止或提交冲突不能留下前置 prune 已生效的半成品。若事务已经成功提交，后来的 Stop 不倒退成“未压缩”。
- 删除压缩次数上限。现有`MAX_COMPACTION_PER_TURN = 2`是**每次运行内允许进入压缩流程的次数**：进入时就自增，不看这次最后是成功、无收益还是失败，每次运行开始时重置。所以它既不是“整个任务最多成功两次”，也不是成功次数。该上限与无收益抖动锁一并去掉，成功次数不设总帽。**第 4 批必须同时接上自动压缩最终失败终止当前运行**，不能先删限制、第 5 批才补失败保护；第 5 批做各入口贯通与回归。复用现有运行结束机制，不新增锁、计数器或开关。
- 两个词要分开：**“没有可压旧段”＝无需压缩**，跳过、不启动模型、不算失败；**“发了摘要但压后占用没下降”＝无收益**，算失败。不强行制造收益，也不用重复成功计数来终止失败。

## 7. 文档、实施与范围

- 整体规划位于`plan/`。后续逐一建立 improve-1～5，写当批精细化规划、实施和验收记录。按"错法"分批：请求发错、本地切错、计量算错、投影不稳是四种不同故障面，不合并。
- 第 1 批含独立的 bug 修复，可最快单独合入，不受其他批次进度阻塞。
- 每批完成定义的共同一条：不允许留下只能靠后续批次拆除的脚手架。
- 压缩提示与压后占用刷新随第 4 批一起做，与压缩同批验证。
- 第五批包括入口贯通、旧机制／无用配置／冗余代码清扫及 SWE 检查；确有额外流程或规模过大时才考虑第六批。
- `docs/core/context/improve-7/`是模块记录编号，不与实施批次一对一绑定。模块规划暂集中于[context-design](./context-design/README.md)。
- Shell／Bash 独立议题与本轮无关，不作前置。服务端 compact、旧信息召回、自动升额重试、缓存预热、大规模 Web／TUI 重设计均不在本轮。
- 实网测试不是某一批的交付物，而是每批的收尾动作。每批完成时由 agent 启动独立 ohbaby 服务，用`tests/models-4-tests.md`中的模型和真实 api-key 发真实请求做本批的字段与上下文探测。凭据不写进规划、命令行参数或审查提示。
