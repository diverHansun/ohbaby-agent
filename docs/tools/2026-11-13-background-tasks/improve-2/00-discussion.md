## 3. 已确认的执行语义

用户确认：

> 认可！等待阈值和硬超时分开，转后台不取消、不重置显式 timeout。继续讨论默认等待阈值和是否默认开启自动转后台，先看看优秀项目的做法，再说你的建议。

| 编号 | 结论 |
| --- | --- |
| I2-D01 | 工具的前台等待阈值与进程硬超时分开。等待阈值控制这次工具调用等待多久，显式 `timeout` 控制命令从启动起最多运行多久。自动转后台不取消、不重置显式 `timeout`，沿用原截止时间。等待阈值到点本身不代表任务执行超时。 |
| I2-D02 | 用户指定默认前台等待阈值为 120 秒（120000 毫秒），取代此前建议的 10 秒。这是等待阈值，不是新的进程硬超时。 |
| I2-D03 | 用户确认默认开启自动转后台，保留配置关闭能力。开关针对自动转换，不撤销 improve-1 已确认的显式后台能力；具体默认时间行为见 I2-D04。 |
| I2-D04 | 自动转换开启且未传 `timeout` 时，不隐式添加旧的 120 秒硬超时；在后台能力可用、额度充足时，等待 120 秒未完成则转后台，默认不限时。自动转换关闭且未传 `timeout` 时，保留原前台 120 秒硬超时。显式后台立即启动，不受自动转换开关影响，未传 `timeout` 默认不限时。显式 `timeout` 始终从命令启动起计算，转换不改截止时间。 |
| I2-D05 | 显式硬超时与等待阈值同时到达时，执行硬超时终止，不先转后台。例如两者同为 120 秒时，任务按超时结束。 |
| I2-D06 | 用户确认：自动转换时后台名额已满，停止当前命令并明确报告容量限制，不杀旧任务、不超额。返回已有输出及真实清理状态；停止请求已发出不等于清理完成，不能把容量限制伪装成 `timeout`。不自动重新执行命令。该规则针对转换时申请后台名额失败；显式后台启动仍按 improve-1 的准入规则在启动前拒绝。 |
| I2-D07 | 用户确认单次调用可调整等待时间、可关闭自动转换。全局配置关闭时，模型不能用单次参数绕过；参数名称与具体校验契约在正式方案中细化。 |
| I2-D08 | 显式硬超时上限按执行方式确定：显式后台和允许自动转后台的命令最多 24 小时；禁止自动转换的纯前台命令最多 10 分钟。上限不是默认寿命，未传值仍按 I2-D04。 |
| I2-D09 | 用户手动转换本轮不做，不新增对应公开工具或 API；保留显式后台启动和自动转换两条路径。 |

## 4. 讨论收尾与后续议题

本轮已列出的产品行为均已确认。正式方案、接口参数和竞态验收已写入 [02](02-optimization-plan-and-change-scope.md)、[design](design/dfd-interface.md) 与 [04](04-test-and-acceptance.md)，文档完成不等于实施完成。默认等待、硬超时及容量拒绝必须按上述规则分别表达。

Stop 与转换竞态、转换失败回滚、额度原子申请、资源保留及通知去重需要写入实施契约和测试；先按已确认的停止、归属和回收规则推导，不把实现正确性拆成重复的产品确认。

用户随后确认：`bash` 负责启动，`task` 统一提供 list/output/stop 并保留等待，不合并子代理运行时；已正式纳入 [improve-3](../improve-3/00-discussion.md)。本轮的自动转换继续在 Bash 内完成，不额外增加 task 启动或手动转换动作。

状态衔接：按用户在 improve-3 中提供的六状态表，硬超时为 `timed_out`，受控取消为 `cancelled`。I2-D06 转换额度不足触发当前命令停止，工程原因取 `capacity-limit`，状态为 cancelled，不伪装成 timed_out；等待阈值到点或单纯取消读等待不改变任务状态。
