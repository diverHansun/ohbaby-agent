## 已实施的核心行为

- `ShellJobStore` 保存任务与输出事实，启动先提交占位和配额检查，再创建进程。公共六状态、停止原因、输出完整性、资源确认与结果投递各自保存，不用一个“完成”字段覆盖不同事实。
- 显式后台默认不限时；主代理和各子代理独立计数。主代理当前轮停止保留后台任务，子代理本次执行结束清理该执行的任务。
- 后台保存有界尾部和检查点；纯前台不周期复制尾部。Registry 对进程、输出、最终写入和资源释放完成后才释放内存责任，异常清理不伪装成功。
- 后台结果与子代理结果共用既有轮次输入协调入口，业务来源仍独立。冻结正文、输入认领、请求成员关系和成功消费互相关联；任务读取不消费通知。
- 使用原生进程出生身份恢复已登记任务。按需查询只观察，不越权发信号；未确认清理继续保护相关工作区，用户明确放弃只解除追踪责任。

本次针对并发和回收修正了三类边界：资源排队期间重新检查其他后端的清理状态；服务退出等待真实 close 和最终持久化而非提前报告成功；限时读取注销自己的等待观察者，保留真正承担子代理资源释放责任的长期观察。

## 审查建议的取舍

Pi 建议删除内存版任务存储，但 `createInProcessUiBackend`、运行时组合和 Registry 的默认入口仍使用它，因此本轮保留并检查语义一致性。放弃追踪的本地责任检查属于已确认的 D29，应接通实际 Registry，不能仅因尚未接线而删除。旧 `task_output/task_kill` 仍有当前消费者，统一迁移前保留。独立探针还确认：恢复写入失败时，数据库可能仍是 running/cleanup=null，但已知的清理风险必须继续阻挡相关资源操作，因此不能只查持久 unconfirmed 行来替代恢复保护。内存存储虽保留已消费的批次候选，实际输入协调器不会重复投递或唤醒，不增加第二份消费缓存。没有必要为列表查询的单次耗时另建一套数据投影，也不引入跨进程控制转发或后台轮询服务。

`shell.json` 的配置在运行时创建时读取，本轮修改后需重启后端。前台命令自行留下的后台子进程仍属于这次前台执行；主轮结束会回收，长期服务应显式使用后台模式。运行时结果输入的前端显示方式属于后续前端交接内容。
