# 讨论记录与已确认要求

日期：2026-11-12。来源：本次用户对话、所附模型设置截图、指定历史会话，以及上一轮只读调查和接口实测。

## 1. 背景

用户希望配置模型时只填写必要连接信息，其余尽量自动处理。此前已经确认：主、子代理使用同一模型请求上限；留空仍会在后端补成 8192；保存后只有元数据探测，不一定触发完整 effort 探测。

用户最初还要求处理达到输出上限后直接失败的问题。最新讨论聚焦下面三个模型配置事项；自动接续另行保留，不宣称已经解决。

## 2. 用户原话摘录

> Max output变大改为32768也就是32k，这是后端的字段(我们是否要做根据effort来定？我认为不需要，先避免规则复杂)，实际在前端留空，用户自行选择

> Reasoning Effort 需要把完整探测接到 Save 后面，和context window的probe条件一样，允许用户手动，但是现在都默认自动。

## 3. 已确认约束

| ID | 要求 |

| U5 | 保存具备探测条件的模型后，自动执行 Context window 与完整 Reasoning Effort 发现流程；保留手动操作。 |

## 4. 方案补充，尚不是用户逐项确认的决策

02 提议增加明确的“清空恢复自动”语义、停止混合格式残留顶层输出值的继承、复用现有探测协调机制、保护用户覆盖和未保存表单。这些是完成 U1–U8 所需的设计细节，供本次文档审查和后续用户讨论。旧配置迁移已在审查后确认，见 §6。

填写 model、base URL、有效凭证和协议后，可以发起探测；这不保证服务商返回上下文窗口或完整推理能力。上一轮真实 metadata 请求只有 10/18 识别出上下文，不能把“连接信息完整”写成“探测必然成功”。

## 5. 本轮交付边界

只写文档、收集证据、执行文档审查。不会修改产品代码、真实模型配置、历史会话，也不提交或发布代码。一次性验证脚本及结果留在被 Git 忽略的 `.ohbaby/max-output-investigation/`。

本方案不引入按 effort 改变 max output、不做统一省略请求输出参数、不进行巨量输入的上下文极限压测、不扩展到运行时自动接续。后者仍是待解决需求。

| D1 | 2026-11-12 | 旧配置迁移 | context 旧值一律转为检测值；max output 恰好等于 8192 的视为旧默认，删除后改用自动 32768，其他数值保留为用户覆盖。不加“context 放不下 32768 就保留 8192”的保护规则。 |

D1 的背景：旧代码在创建条目时把 context 写成 128000，探测结果也写回同一个字段，因此无法区分默认值、检测值和手填值。connect 路径则每次都把 8192 写进 max output。如果全部当作覆盖保留，老用户升级后表单仍然填满，自动探测也不会生效。

用户对不加保护规则的理由：本地模型的最大输出通常由用户自己配置，LM Studio 这类推理客户端也能自行设置，这不是 ohbaby 的职责。结果是，context 很小的旧条目升级后可能触发 `tokenBudgetIssue`，用户按提示调小 max output 即可。

D2 的理由：上下文窗口大小与 key 无关；通过设置 API 改 key 时，现有代码已经会清掉自动 reasoning 能力并重新探测；手改 env 文件换 key 很少见，后果也只是 reasoning 档位暂时显示旧值。参考项目都没有把凭证指纹持久化到配置里。去掉指纹后，凭证摘要的计算与保密约束、“同路由 stale 历史值”这一级优先级、env 遮蔽判断，以及 context 和 reasoning 两套独立身份都不再需要。

D3 的理由：等待 45 秒和启动恢复队列，原本是为了解决“迁移后旧证据没有身份、不可信”的问题，D2 之后这个前提已经不存在。剩下的“有偏好但能力未知”只出现在刚改完连接的几秒内，或探测失败时。现有代码在这时按 service-default 发送，偏好不丢，不算回归。如果改为直接报错，探测失败的模型一设偏好就无法使用，代价更大。

D4 的理由：用户只需要知道用的是哪个值，以及刚才那次重新探测失败了，`reason` 已经能表达后者。去掉 stale 后，状态从“三种状态 × 是否 stale”减回三种，前端、SDK 和测试都少处理一种组合。

D5 的理由：源码里有 4 份 context 默认定义和 5 处字面量 8192，原方案只列了其中一部分。更要紧的是，有 4 处会把默认值直接写进条目；新语义下这个字段代表用户覆盖，照旧写入就会让自动探测永远不生效。

D6 的依据：用户要求对照测试清单实测。现有 probe 识别了 18 条路由中的 12 条，未识别的 6 条里有 5 条是 probe 自身的问题（4 条 Chat 用错参数格式，1 条超时），只有 1 条是网关确实忽略字段。按实测推算，5 项修复后可识别 17 条。详见 [01 §5](01-problem-analysis-and-current-state.md)。

D8 的来由：文档审查发现，原方案用备份目录判断“是否已迁移”站不住。现有备份只在旧顶层格式时生成，没有标记文件；而且用户删掉 `backups/` 或拷走 model.json 后，迁移会重跑，把用户手填的 8192 删掉。这一批本来就要把条目 context 改为可选，旧版本程序读不了新文件，用版本号标出格式变化最直接，标记也跟着文件走。

## 7. 本轮复核后的补充决定

Responses 的 probe 候选和部分内置能力包含 `max`，但正式请求在本地拒绝它，见 01 §4 的无网络复现。用户已明确选择 D9：同步修正正式请求，让经能力校验的 `max` 能发送，并补探测到请求的闭环测试。当前内置的 Zenmux luna Responses 也存在这个冲突，且已安装的 OpenAI SDK 类型包含 `max`，因此不再采用过滤 Responses max 的方案。

Anthropic `minimal` 已由用户确认 D10：按正式请求支持范围处理，清理不兼容旧偏好并通知用户。本次修正的是探测与正式请求不一致，不是“读不出字符串”：当前 probe 的跨协议候选表包含 minimal，直接用 fetch 测试；正式 Anthropic 的 output_config.effort 校验和 SDK 类型没有该值。第三方网关接受它，并不表示当前正式请求路径支持它。官方 effort 文档也未列出 minimal，见 01 §4。

D9、D10 均已确定；此前文档审查发现的设计缺口已补齐，目前没有已知的开工前行为决策阻塞。这里的结论是文档具备实施条件，不代表实现或验收已经完成。

验收必须覆盖能力结果 → 落盘重读 → 用户选择 → 正式请求构造，不能只检查 probe HTTP 成功，也不能只改新 probe 而遗漏旧数据。具体契约见 02 §6.4。
