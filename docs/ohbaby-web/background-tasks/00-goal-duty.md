# 00 目标与职责

## 1. 产品目标

agent 用 `bash` 启动后台任务（dev server、长构建、测试套件）以后，用户在 Web 上能看到这个会话里有哪些任务在跑、跑了多久、输出到了哪里；看到跑飞或不再需要的任务，可以自己取消，不用再去求模型。

这个面板是给用户“看一眼、必要时叫停”的，不是任务管理器。任务由 agent 启动、等待和收尾，用户平时不需要关心它，所以界面要做到：

- 没有任务的会话完全看不到这个功能。
- 有任务时，入口就在用户已经在看的地方（bash 工具卡、右侧栏 `[+]` 菜单）。
- 列表一眼能分清在跑的和已结束的，并且不用读一堆状态标签。

## 2. 用户角色

使用阶段：

| 使用阶段 | 说明 |
|---|---|
| 旁观者 | 让 agent 干活，偶尔想知道“它起的那个服务还在不在、输出了什么” |
| 排查者 | 任务失败或卡住，打开详情看输出尾部、退出码，决定要不要取消 |

权限身份：单一身份。用户在当前主会话及其所有子代理的任务上权限相同。是否能取消由后端的 `canStop` 决定，前端只负责表达。

## 3. 核心任务

- T-01 查看当前会话的后台任务：哪些在跑、哪些已结束、各跑了多久
- T-02 查看单个任务的命令和输出尾部
- T-03 取消一个运行中的任务
- T-04 从对话里的 bash 工具卡直接打开它启动的那个任务

## 4. 职责边界

前端负责：

- 按会话是否有过任务，决定入口出不出现
- 把后端的状态、停止原因、清理事实翻译成很少的几种界面表达
- 详情页打开且任务在跑时，定期拉输出尾部
- 发出取消请求，并在请求进行中表达“正在取消”
- 在主会话里隐藏 `background-task-result` 消息

前端不负责：

- 判断能不能取消（以后端的 `canStop` 为准）。前端只多加一条展示规则：Cancel 只给 `running` 的任务显示。后端对“已结束但清理未确认”的任务也给 `canStop`，此时再停一次是重试清理，不是取消，本轮不为它提供入口
- 判断任务是否真的停了（以后端的 `status` 和 `cleanup` 为准，前端不在请求成功后直接把行改成已取消）
- 通知模型任务结束（后端投递）
- 任务额度、回收、崩溃恢复等生命周期规则（后端 improve-1～3）
- 读取完整日志文件（后端只给日志路径和分段读取接口，本轮只用尾部）

## 5. Non-goals

本期不提供：

- 暂停、继续、重新运行任务（后端没有这种语义）
- “放弃追踪”入口（后端已有 `abandonShellJob`，太少用，本轮不做 UI）
- 对清理未确认的任务重试清理（只显示说明，不提供操作）
- 一次取消全部
- 按启动时间筛选、按单个子代理筛选
- 完整日志分页阅读、搜索输出
- 任务结束的对话通知、Toast、未读标记
- 主区顶栏的任务图标或运行数徽标
- 清空已结束任务（后端没有删除接口，只在前端隐藏会造成“刷新后又回来了”）
- 手动把前台命令转到后台
- TUI（另开议题，见 README）

取舍：

- 学 Claude 桌面端“有任务才出现”和 Running 分组的克制写法。
- 学 pi-background-tasks 和 ZCode 的“进详情才拉输出、往上滚就暂停跟随”。
- 单个取消不确认，和 pi-background-tasks、ZCode 一致：取消只影响一个任务，模型会收到 `user` 停止原因的通知。
- 卡片跳转是我们自己的做法，沿用 Subagents 的入口行（redesign-2026-10 D35）。
