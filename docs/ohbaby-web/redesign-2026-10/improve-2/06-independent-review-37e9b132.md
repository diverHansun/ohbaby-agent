## 2. Standards：实现质量

### R1 · P1：项目连接失败后，选择器与实际发送目录不一致

位置：`apps/ohbaby-web/src/runtime/index.ts:169–174`，`runtime/instance-layer.ts` 的 `connect()` 失败回滚分支。

复现步骤：

1. 默认草稿已连接 `/default`。
2. 选择项目 `/b`，仅让 `/b` 的 `POST /v1/clients` 返回 500。
3. 连接回滚后发送第一条消息。

实际记录：

```text
pickerProject: /b
connectedDirectory: /default
promptDirectories: [/default]
```

`openDraft()` 提前更新项目状态，连接层失败时只恢复连接。用户看到项目 B，却可能让 agent 在默认目录执行。选择器又忽略对同一值的重复选择，直接重选 B 也不会重试。

最小修复方向：失败时只允许仍有效的那次选择回滚项目，并让项目与实际连接一致；沿用已有选择代次。补普通失败、连续失败和同值重试的测试，无需新增状态框架。

SWE 依据：状态不变量、错误恢复的一致性、最小惊讶原则。

### R2 · P2：延迟的 SESSION_MOVED 覆盖用户的新选择

位置：`apps/ohbaby-web/src/runtime/index.ts:154–159`。

复现步骤：s1 在 `/a` 提交，挂住其 409 响应；用户打开 s2(`/b`) 并同步完成；随后释放 s1 的 `SESSION_MOVED`，目标为 `/c`。

实际记录：当前会话变回 s1，连接变为 `/c`，提交请求目录依次为 `/a`、`/c`。旧请求不仅抢回选择，还在后台触发了重发。

最小修复方向：把自动跟随与用户主动打开区分开；发送开始时记住选择代次，代次改变后停止自动切换。不应通过一次旧响应再次产生“用户选择”。

SWE 依据：异步操作的有效期、显式副作用、职责边界。

Standards 共 2 条；最严重的是 R1。没有发现值得单列的规范硬违规，不建议为了行数或抽象纯度继续拆文件。

## 3. Spec：需求完成度

### R3 · P2：同目录 New chat 会被首发晚回执重新选回

验收原文：B15“晚到响应不抢回选择或清空新输入”。

位置：`runtime/instance-layer.ts:103–109`、`api/daemon/client-prompts.ts:204–212`；UI 的首发选择守卫在 `ui/session/usePromptSubmission.ts`。

复现：No project 首发 POST 尚未返回时再次执行 New chat；随后放行旧回执。实际 `reusedClient=true`，绑定从 `null` 变为 `created-1`，新草稿被旧会话取代。

现有 App 测试直接替换 fake client，覆盖了换 client 的场景，但漏掉了同目录复用 client 的真实路径。本轮确认了抢回选择，未额外声称已复现新输入被清空。

建议：首发回执、会话绑定和 UI 选择都服从同一选择代次；补通过真实 runtime 调用 New chat 的测试。

### R4 · P2：运行中迁移后追加消息，会提前切断原 SSE

设计原文：02 §3.2“保留当前执行目录的 client、SSE 和审批绑定直到本轮结束”。

位置：`runtime/index.ts:154–159`、`runtime/instance-layer.ts:171`。

复现：会话在 `/a` 运行，外部将下一轮目录改成 `/b`；旧轮未结束时发送 follow-up。服务端路由会根据待生效目录拒绝旧目录请求，runtime 随即自动切到 `/b`。

实际记录：`running=true`、`clientChanged=true`、`abortedStreams` 包含 `/a`，当前目录变为 `/b`。这已违反“保留本轮连接”，并使审批和 Stop 绑定失去原连接基础。

原有移动用例处于 idle，`pending-move` 则是静态展示，都不能证明运行中的连接保留正确。

验证边界：本轮用真实 runtime 加受控假 HTTP/SSE，保持 running 且不发送结束事件；确认的是旧流确实被关闭。fake `/control` 仍返回 `runId: null`，未完成真实 daemon 的运行中换项目、审批与 Stop 全流程，因此不声称实际审批已丢失。

建议：本轮未结束时保持旧连接，明确处理这次未接纳的提交；结束后再用目标目录。用运行中场景补回归，再补真实 daemon 的审批/停止走查。

Spec 共 2 条；最严重的是 R4。05 中 D1–D3 的做法有合理的 KISS 依据：草稿连实例但不创建会话、复用原首发路径、删除无人使用的 settings 客户端，本轮不要求恢复原先更复杂的方案。

## 6. 未提交修补的中间状态

这部分是给继续实施者的线索，不替代固定版本审查。工作区持续变化，需在修改稳定后重新验收。

- 普通项目连接失败、延迟 SESSION_MOVED 两条，在观察到的补丁里已有针对性修补；子代理的内存验证通过。
- **同值选择仍可能错位**：B1 注册挂起，再发起同目录 B2；让 B1 失败、B2 成功。观察到 picker 为 No project，实际连接与首发为 `/b`。仅比较项目字符串会把后一次同值选择当成前一次，宜比较选择代次。
- **归档新回归**：归档 s1 的响应挂起期间打开 s2；释放旧响应后，观察到 s2 被切回默认草稿。中间补丁的 `if (wasOpen) openDraft(null)` 缺少用户选择代次检查。固定 `37e9b132` 原有绑定检查，不存在这条新回归。

上述两条中间态问题由 Standards 子代理用内存 fakeDaemon 实测，主审核对了补丁；主审没有将它们混入固定源码的 4 条失败数量。相关位置是 `runtime/index.ts` 的 `openDraft()` catch 与 `archiveSession()` 成功分支。

## 7. SWE / KISS 建议与交接

保留目前的全局层、实例层和 store 切片划分。真正需要补的是“谁有权改变当前选择”以及“失败后哪些状态必须一致”，无需换框架、加通用状态机或继续机械拆文件。

建议修复顺序：先对齐草稿项目与连接，再统一晚到结果的选择代次保护，最后处理运行中迁移并补真实 daemon 走查。修补还应覆盖归档完成和同值重试，避免修一个异步路径又遗漏另一个。

本轮没有产品代码、CSS 或提交操作；审查记录单独保存，未覆盖已有 README/05。临时服务、隔离源码、复现脚本和日志在核对后清理；仓库外仅保留最终桌面预览作为本次报告附件。
